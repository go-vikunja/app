# Releasing

How a release of the app is cut ([D86](decisions.md#d86-ci-and-releases-on-github-actions)). Every Android build that is distributed comes from the workflow "Release" (`.github/workflows/release.yaml`) of a `v*` tag in go-vikunja/app on GitHub Actions; no Android build is signed on a laptop. Its job `build` makes the Play bundle, a universal APK and one APK per ABI unsigned, without any secret. Once a reviewer approves, its job `publish` in the protected environment `release` signs them with Vikunja's keys, checks them, and publishes the bundle to Google Play (a beta to the `beta` track, a final release to production as a staged rollout), the APKs on dl.vikunja.io, and a GitHub release with the APKs, `SHA256SUMS` and the desugar_jdk_libs source. Everywhere else a release is only rehearsed with throwaway keys, on a Mac with `tool/ci/release.sh --dry-run` or in a test repository on GitHub ([the dry run](#the-dry-run)). The iOS build of the same tag is signed on the owner's Mac and uploaded to App Store Connect for TestFlight ([iOS](#ios-testflight-from-the-mac)). The app's privacy policy, help page and legal notice are part of vikunja.io, which Vikunja's maintainers publish; those pages and both stores' consoles need their work and the owner's ([below](#the-website-and-the-store-listings)). The beta itself, from the first push to 1.0.0, follows the owner's runbook in [beta.md](beta.md) ([D77](decisions.md#d77-beta-preparation-new-app-id-own-signing-key-public-group-testers)), which links the steps here.

*Step 41, in review ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry)): the opt-in crash reports' Sentry DSN comes from the repository variable `VIKUNJA_APP_SENTRY_DSN` ([crash reports](#crash-reports)); Sentry's SDKs are in Gradle's dependency verification and the licence notices, and Runner's privacy manifest declares system boot time for them.*

## Once, in go-vikunja/app

Vikunja's maintainers set these up after [the move](beta.md#the-move) (step 38d) and before the first tag. The workflows need nothing else; they use no personal token, only the workflow's own `github.token`.

1. **The environment `release`** (Settings > Environments > New environment):
   - **Required reviewers:** the owner and kolaente; one approval is enough, and either may approve a release of their own tag, so "Prevent self-review" stays off ([D86](decisions.md#d86-ci-and-releases-on-github-actions), owner, 2026-11-14). "Allow administrators to bypass configured protection rules" is off.
   - **Deployment branches and tags:** "Selected branches and tags", with one tag rule, `v*`, and no branch.
   - **Environment secrets,** under the old app's names. A secret's value can be neither read back nor moved, so each is entered again here:

     | Secret | Value | Needed |
     |---|---|---|
     | `KEYSTORE_BASE64` | the upload keystore (the old app's `keystore.jks`; JKS or PKCS12): `base64 < keystore.jks \| tr -d '\n'`, a wrapped value works too | yes |
     | `KEY_PROPERTIES` | its properties, as in the old app's `key.properties`: `storePassword=…`, `keyAlias=…` and `keyPassword=…`, one per line; a `storeFile` line is ignored | yes |
     | `APK_KEYSTORE_BASE64`, `APK_KEY_PROPERTIES` | a separate key for the APK, the same way | both or neither |
     | `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` | the Play service account's JSON key | yes |
     | `S3_ACCESS_KEY`, `S3_SECRET_KEY` | the access key of the storage behind dl.vikunja.io | yes |
     | `S3_ENDPOINT` | the storage's https URL or host name; only its host and port are used | yes |
     | `S3_BUCKET` | the bucket that dl.vikunja.io serves | yes |
     | `S3_REGION` | the bucket's region; `us-east-1` when unset, which Cloudflare R2 takes as `auto` | no |

     Without an APK key the upload key signs the APK too, as in the old app, so installs of the old app's APKs from dl.vikunja.io and GitHub keep updating. The key that signs the APK must be RSA: the job signs the APK twice and fails when the two files differ, as they do with an EC or DSA key, because a re-run must reproduce an APK already published. Without `KEYSTORE_BASE64` and `KEY_PROPERTIES` a tag signs with throwaway keys, publishes nothing and fails; a partial set fails before signing, naming what is missing.
2. **No copies outside the environment:** delete any repository secret of these names (Settings > Secrets and variables > Actions), and remove go-vikunja/app from the access list of every organisation secret named `KEYSTORE_BASE64`, `KEY_PROPERTIES`, `APK_KEYSTORE_BASE64`, `APK_KEY_PROPERTIES`, `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`, `S3_ACCESS_KEY` or `S3_SECRET_KEY`. A job outside the environment, which any workflow on any branch can start, reads such a copy without the reviewers; the job `secret-scope` fails every tag while one exists. `S3_ENDPOINT`, `S3_BUCKET` and `S3_REGION` may stay organisation secrets.
3. **The certificates,** in a reviewed pull request: `tool/ci/release_certificates.txt` gets `upload=` with the SHA-256 of the upload certificate, as the Play Console shows it under Test and release > App integrity > Upload key certificate, in lowercase hex without colons, and `apk=` only with a separate APK key, with that key's certificate. A real release fails while `upload=` is empty or names another key than `KEYSTORE_BASE64` holds (why: a swapped secret would otherwise sign the public APK with a stranger's key). The jobs read the file from the tag, so it is committed before the tag.
4. **The rollout (optional):** the repository variable `VIKUNJA_APP_PLAY_ROLLOUT` (Settings > Secrets and variables > Actions > Variables), the share of users a final release reaches first, a fraction such as `0.2`; 0.1 when unset.
5. **Rulesets** (Settings > Rules > Rulesets): one for the tags `v*` that restricts creations, updates and deletions to the maintainers in its bypass list, so a release tag is never moved; the old tags `v0.0.7-alpha` to `v0.0.26-alpha` match it too. The ruleset "main protect" for `main` requires the status checks `checks`, `editor`, `contract`, `android`, `osv` and `ios` instead of the old app's `Test / lint`, `Test / test` and `Test / build`. For the import it allows merge commits without linear history; afterwards it goes back to linear history, and squash only is recommended ([the move](beta.md#the-move)).
6. **Actions** (Settings > Actions > General): workflow permissions "Read repository contents and packages permissions", with "Allow GitHub Actions to create and approve pull requests" off; fork pull request workflows "Require approval for all external contributors". Once the import has removed the old app's workflows (step 38d): "Allow actions created by GitHub" only, and "Require actions to be pinned to a full-length commit SHA"; the workflows use only GitHub's own actions, pinned that way. The tag rule of the environment also keeps the Copilot coding agent away from it.
7. **Optional:** release immutability (Settings > General > Releases). The workflow creates each release with its files at once, which works with it.
8. **Google Play:** the service account keeps its release rights for `io.vikunja.app`, to production and to the testing tracks. The old pipeline's upload of every push to `main` stops with the import, which removes its workflow (step 38d). With managed publishing on, Play holds a committed release until a maintainer publishes it. **Developer verification:** an APK installed outside Play must be signed by a key registered to a verified developer ([Android developer verification](https://developer.android.com/developer-verification/guides); certified devices in a few countries since 2026-09-30, everywhere from 2027). Play knows its app signing key; the key that signs the APK, the upload key unless an APK key is added, has to be registered in Vikunja's Play Console too.
9. **dl.vikunja.io:** the bucket serves `app/<name>/vikunja-app-<name>.apk` with the content type the job sets. The old `/app/unstable/` is no longer updated (owner, 2026-11-14).
10. **The written offer** for the desugar_jdk_libs source: the Vikunja project makes it, and `WRITTEN_OFFER_CONTACT` in `tool/build_android_notices.py` is `hello@vikunja.io` ([D89](decisions.md#d89-store-listing-and-web-pages-of-the-official-app)), so `app/assets/legal/android.md` says "Ask the Vikunja project at hello@vikunja.io.", which `app/test/core/legal/app_licenses_test.dart` checks. GitHub releases carry the source itself; Play and dl.vikunja.io rely on the offer. After a change, run `python3 -I tool/build_android_notices.py` and commit `app/assets/legal/android.md`. The release build fails while the contact is empty.
11. **Cronet:** done on 2026-10-29: `cronet-bundled` 500.1.0, Chromium 155.0.8059.16 (D73). Keep it current as [Raising Cronet](#raising-cronet) says.
12. **Security reports:** an admin turns on private vulnerability reporting (Settings > Advanced Security > Private vulnerability reporting), with the owner as a security manager. `SECURITY.md` and the issue forms' link to the security policy depend on it. The issue forms set the organisation's issue types Bug and Feature.
13. **Updates of the pins** (step 40h): `.github/dependabot.yml` has Dependabot open one pull request a week for the GitHub Actions, each still pinned by its full commit SHA with the version in a comment, after a week's cooldown; it needs no setting, and its pull requests are reviewed like any other (`test_github_workflows.py` keeps the rules of [D86](decisions.md#d86-ci-and-releases-on-github-actions)). The workflow "Upstream versions" (`.github/workflows/upstream.yaml`, Mondays 05:41 UTC, or by hand under Actions) has no secret and only reads the repository; it fails when Flutter's stable release is newer than `FLUTTER_VERSION` in `tool/ci/pins.sh` or Google Maven has a newer `cronet-bundled` than `app/android/app/build.gradle.kts`, naming what to raise ([raising Cronet](#raising-cronet), [raising Flutter](#raising-flutter)). GitHub emails a failed scheduled run to whoever last changed the workflow's schedule, so a maintainer who watches the repository's Actions also checks it each week; GitHub turns scheduled workflows off after 60 days without activity in a public repository.
14. **The German override** (optional, step 40h): the repository variable `VIKUNJA_APP_ALLOW_INCOMPLETE_GERMAN`, set only for [a hotfix](#a-hotfix) and deleted after it.
15. **The crash reports' DSN** (step 41): the repository variable `VIKUNJA_APP_SENTRY_DSN`, which the owner sets, with no spaces or line breaks ([crash reports](#crash-reports)).

## The website and the store listings

The app's pages are part of vikunja.io ([D89](decisions.md#d89-store-listing-and-web-pages-of-the-official-app)): the section "Mobile app" of Vikunja's privacy policy, the help page `/help/mobile`, which also says how to delete an account, and Vikunja's imprint as the legal notice, in English only, the same for every language. Vikunja's repository go-vikunja/website builds them, and kolaente puts the texts into it from the drafts in [vikunja-io-drafts.md](vikunja-io-drafts.md); nothing here is a pull request for that repository. This repository only links them: the About page through `WebsitePage` in `app/lib/app/legal.dart`, the store metadata in `fastlane/metadata/`, which `tool/check_store_metadata.py` checks against the same addresses. `hello@vikunja.io` is Play's developer email and the written offer's contact; App Review and the testers get an address that kolaente sets up for the app's maintainers, `hello@vikunja.io` until it exists. [store-listing.md](store-listing.md#the-website) lists every address and what uses it, and every form of both consoles with its answer and the reason. Once, in this order:

1. **The pages are published:** kolaente puts the privacy section, the help page and the imprint's scope sentence into go-vikunja/website. Then open, signed out: `https://vikunja.io/privacy/#mobile-app`, `https://vikunja.io/help/mobile` and its `#delete-your-account`, and `https://vikunja.io/imprint/`, which names the apps. Until then these addresses, compiled into every build, lead to a policy without the app's section and a missing page, so no build is distributed before. Once they are in the stores they must not change; the anchors come from the headings "Mobile app" and "Delete your account", and the help page's address from its slug `mobile`, so these keep their words. A change would have to go into `legal.dart`, `check_store_metadata.py`, `RELEASE_WEBSITE_PAGES` in `tool/ci/release_lib.sh`, `fastlane/metadata/`, [store-listing.md](store-listing.md#the-website), the drafts and both consoles at once; `tool/ci/test_website_pages.py` fails until they agree.
2. **The contacts:** the address for App Review and the testers, once kolaente has set it up, goes into `fastlane/metadata/review_information/email_address.txt` and `FIXED` in `tool/check_store_metadata.py`, TestFlight's test information, the open test's feedback channel and [beta.md](beta.md#texts-for-testers)'s tester texts.
3. **The Play Console and App Store Connect forms,** as [store-listing.md](store-listing.md#google-play-console) answers them, with the texts of `fastlane/metadata/` copied in by hand: in the Play Console, with the permissions kolaente grants or by kolaente himself, the store settings and contact details, the main store listing in both languages with the graphics of `branding/png/`, the privacy policy, App access, Ads, Content rating, Target audience, News, Data safety, Government, Financial features, Health and Advertising ID, and a check that App content asks for no foreground-service or exact-alarm declaration; in App Store Connect, once the Apple account is decided, the app information, the category, content rights, the age rating, App Privacy with the privacy policy address and the label decided with the account, pricing and availability, the version's texts and addresses, App Review information with a phone number (never in the repository) and TestFlight's test information.
4. **The trader status** is that of the account that publishes: Vikunja's on Google Play, and on the App Store that of the Apple account, which is open.
5. **The screenshot session:** start the test server with both test users, seed the demo data with `python3 -I tool/seed_demo_data.py --lang en`, sign in once on each device (the Android phone and tablet emulators, the iPhone 17 Pro Max, iPhone 17 Pro and iPad Pro 13-inch simulators), then run `tool/store_screenshots.sh` for each device and language, with `--reset --lang de` for the German data ([store-listing.md](store-listing.md#screenshots) has each step). Then `python3 -I tool/check_store_metadata.py --strict` must pass; run it again before every submission.

The release scripts wait for the pages ([D90](decisions.md#d90-fixes-from-the-code-review-before-beta1)): `tool/ci/release_build.sh` (job `build`) and `tool/ci/ios_release.sh` fetch each address of `RELEASE_WEBSITE_PAGES` in `tool/ci/release_lib.sh` signed out, and it must answer 200, end on vikunja.io after redirects over https only, and have the element its fragment names. A real release refuses until then, naming the first page that fails ("… answered 404", "… has no element with the id mobile-app"); a dry run on GitHub lists every failing page as a reason; a local dry run and the iOS dry run only print what they would check. They cannot see whether the imprint's scope sentence names the apps; open it yourself. The About page links the addresses in every build, and `python3 -I tool/check_store_metadata.py --strict` fails only while a store's minimum set of screenshots is missing. An empty or changed URL, email or copyright file fails the check without `--strict` too, and so does British spelling in the English texts or the review notes.

## Cutting a release

1. **Bump the version** (after [raising Cronet](#raising-cronet) if Google has a newer one) in `app/pubspec.yaml` to the release's name, for example `version: 1.0.0-beta.1+1`. Only the part before `+` counts; the build number comes from the tag. Run the [dry run](#the-dry-run) for the tag, `tool/ci/release.sh --dry-run --tag v1.0.0-beta.1`: it must end with only the expected reasons, `not a tag run of go-vikunja/app on GitHub Actions`, `placeholder source URL` and `throwaway keys`, and `no committed certificate fingerprints (tool/ci/release_certificates.txt)` while the certificates of [step 3 above](#once-in-go-vikunjaapp) are not committed; `no written-offer contact` means that the contact of step 10 above is empty, and the release would fail. `German incomplete` means that German lacks English texts, and the release would fail too: German must be complete on Crowdin and its pull request merged ([the translations](#the-translations)). The build also prints each shipped language's share (`python3 -I tool/l10n_progress.py --shipped-list`) and warns when one is below 50 %; that does not stop a release. The contract tests against the older releases run in the workflow "Contract matrix" ([D28](decisions.md#d28-contract-tests-against-the-latest-vikunja-release-only)): every night on `main`, by hand under Actions, and for the tag ([step 3](#cutting-a-release)); its run on the tag replaces a local run against the previous minor version before tagging. To see an older release before you tag, run the workflow by hand on `main`, or locally: `VIKUNJA_APP_TEST_VIKUNJA_IMAGE=vikunja/vikunja:2.7.1 tool/ci/contract.sh` starts the local test server again, empty, with that image, and the tests expect its version; against 2.3.0 also set `VIKUNJA_APP_TEST_DATABASE_PATH='/tmp/vikunja.db?_busy_timeout=30000&_x='`, as 2.3.0 stops under immediate transactions. The script runs both suites before it fails and names those that failed. Fix what fails or record it in [D28](decisions.md#d28-contract-tests-against-the-latest-vikunja-release-only). Then `docker compose -f test_servers/docker-compose.yaml up -d` brings back the latest release with the default database path, and `tool/seed_e2e_user.sh` and `E2E_USER_ENV=test_servers/seed/e2e-user-2.env tool/seed_e2e_user.sh` the two sign-in test users.

   **Write Play's What's new** with the bump, before its dry run ([D90](decisions.md#d90-fixes-from-the-code-review-before-beta1)): `fastlane/metadata/android/en-US/changelogs/<version code>.txt` and the same file in `de-DE`, with the version code of the table below (1000001 for `v1.0.0-beta.1`), at most 500 characters each, in US English and in German with du, worded by the [glossary](glossary.md). `python3 -I tool/check_store_metadata.py` checks them like the other store texts and wants each in both languages. The publish job sends every language that has one with the upload; a final release refuses without the en-US text, in the dry run too ("production needs Play's What's new in en-US …"), and a tag without it fails at the Play step, after the approval and the signing, and needs a new tag. The texts of 1.0.0-beta.1 and 1.0.0 exist; look at them again before their tags.

   **Check the reminders after a force stop** on an Android emulator, with a build of the commit you will tag ([D90](decisions.md#d90-fixes-from-the-code-review-before-beta1)): give a task a reminder a few minutes ahead, then

   ```sh
   adb shell am force-stop io.vikunja.app
   adb shell dumpsys alarm | grep io.vikunja.app   # the reminder's alarm is gone
   ```

   Open the app: `adb shell dumpsys alarm | grep io.vikunja.app` lists the alarm again, and the reminder fires at its time.

   **Run the smoke test and the update test** on the emulator `Vikunja_Screens`, with a build of the commit you will tag ([D85](decisions.md#d85-update-from-the-old-app-server-prefill-one-session-try-leftovers-cleared-widgets-kept), [developer guide](development.md#update-and-smoke-tests-on-an-emulator)): `tool/e2e/smoke_test.sh` with this app's APK, and `tool/e2e/update_test.sh` with the old app's APK and this app's. The update needs both APKs signed by one key, so both are signed again with one throwaway key, and the old app is built from `legacy-final` for it too. Both scripts wait for your sign-in; a failed check is fixed before the tag.

   Merge the bump into `main` and wait for its green CI run before you tag.
2. **Tag and push the tag,** as a maintainer whom the tag ruleset allows:

   ```sh
   git tag -a v1.0.0-beta.1 -m "Vikunja app 1.0.0-beta.1"
   git push origin v1.0.0-beta.1
   ```

   A release tag is `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-beta.N`: no leading zeros, major at most 2099, minor and patch at most 99, N from 1 to 98. The version code is major × 1,000,000 + minor × 10,000 + patch × 100 + N, with 99 for the final release, so every beta comes before its release:

   | Tag | Build name | Version code |
   |---|---|---|
   | `v1.0.0-beta.1` | 1.0.0-beta.1 | 1000001 |
   | `v1.0.0-beta.2` | 1.0.0-beta.2 | 1000002 |
   | `v1.0.0` | 1.0.0 | 1000099 |
   | `v1.0.1-beta.1` | 1.0.1-beta.1 | 1000101 |
   | `v1.2.3` | 1.2.3 | 1020399 |

   `python3 -I tool/ci/release_version.py v1.0.0-beta.1` prints the name and the code, and fails for another tag or when the pubspec's version name differs. A tag that starts with `v` but is malformed fails the job `build`; any other tag runs no release. Never move or delete a release tag: the job publishes nothing once the tag no longer points at the commit it built, and a fix is the next tag.
3. **The release workflow** runs `ci` (every CI job, `ios` included), `build` and `secret-scope`. Then `publish` waits: a reviewer of the environment `release` other than the person who pushed the tag opens the run and approves it under "Review deployments". The tag also starts the workflow "Contract matrix", which does not hold `publish`: the reviewer approves only once each release in it is green or each failure is recorded in [D28](decisions.md#d28-contract-tests-against-the-latest-vikunja-release-only). `publish` then:
   - checks that the tag still points at the built commit and that the environment holds every secret the release needs;
   - signs the bundle and the four APKs, compares both certificates with `tool/ci/release_certificates.txt`, and checks the signatures (never the debug key), each APK's alignment, version and ABIs;
   - uploads the bundle to Google Play with its What's new, the committed `changelogs/<version code>.txt` of each language: a beta to the `beta` track, to all its testers at once; a final release to production as a staged rollout to the share `VIKUNJA_APP_PLAY_ROLLOUT` (0.1 when unset);
   - puts the APKs on dl.vikunja.io: the universal one at `app/<name>/vikunja-app-<name>.apk`, which every device takes, and beside it `vikunja-app-<name>-<abi>.apk` for `arm64-v8a`, `armeabi-v7a` and `x86_64`. They share the tag's version code ([D73](decisions.md#d73-ci-from-local-scripts-versions-from-the-tag-gitlab-until-the-move)), as the build sets `force-version-code-ignoring-abi`, so a device can move between the universal APK and its own;
   - creates the GitHub release "Vikunja app <name>" with the four APKs, `SHA256SUMS` and `desugar_jdk_libs-<version>-src.tar.gz`, a beta as a prerelease, a final release as the latest unless go-vikunja/app has a higher final release tag (`git ls-remote --tags`): a patch of an older line never becomes "Latest". Its notes give each APK's SHA-256, the SHA-256 of the signing certificate, the link to the source at the tag, which the About page of this build links too, and that an APK installed by hand gets no updates by itself.
4. **Check the release:** on the GitHub release, the six files open signed out, `SHA256SUMS` matches the APKs, and the certificate's SHA-256 is the committed one; the APKs on dl.vikunja.io have the same SHA-256; the Play Console shows the release on its track with its What's new in English and German.
5. **A final release's rollout:** as [the rollout](#the-rollout) says, on Play and in the App Store. The workflow never changes a rollout after its upload.
6. **Upload the iOS build** from the Mac: [each TestFlight build](#each-testflight-build).

## The rollout

A final release reaches users in stages on both stores; betas go to all testers at once. Before each raise, compare the new version with the one before it: the Play Console's Android vitals (Monitor and improve > Android vitals, filtered by version code), App Store Connect's crashes (TestFlight > Crashes, and Xcode's Organizer for the App Store build), the reviews of both stores and the issues of go-vikunja/app.

**Abort thresholds:** halt the rollout as soon as one of these holds for the new version (Play's thresholds are its own [bad behaviour thresholds](https://developer.android.com/topic/performance/vitals#bad-behavior)):

| Signal | Halt when |
|---|---|
| Crashes | Play's user-perceived crash rate above 1.09 %, or twice the previous release's; on iOS, crashes in App Store Connect from more than 1 % of the sessions it reports, or a crash on start |
| ANRs | Play's user-perceived ANR rate above 0.47 %, or twice the previous release's |
| Reviews and reports | three one-star reviews or reports that describe the same regression; at once for lost or wrong data, changes that never reach the server, a sign-in that fails where it worked, or a security problem |

**Google Play:** the release starts at the share `VIKUNJA_APP_PLAY_ROLLOUT` (0.1 when unset). Raise it to 0.5 after two days and complete it after two more (Test and release > Production > Manage rollout), each time only when the vitals show the version's sessions and no threshold holds. **Halt rollout** stops new installs and updates of the version; devices that have it keep it. Resume it if the cause was not the app, or replace it with [a hotfix](#a-hotfix): a higher version code takes over the halted release.

**App Store:** before submitting the version, choose "Release update over 7-day phased release" under Phased Release for Automatic Updates: automatic updates reach 1, 2, 5, 10, 20, 50 and then 100 % of the users over seven days, while anyone can still update by hand from the App Store. Pause the phased release (up to 30 days) when a threshold holds; there is no rollback, so the fix is the next version, for which App Review can be asked to expedite the review.

**The APK** on GitHub and dl.vikunja.io has no stages and cannot be withdrawn from devices. When a threshold holds, put a warning at the top of the GitHub release's notes with the release to stay on, and pin the issue ([communication](#communication)); leave the files, so a re-run still matches them.

## A hotfix

A fix that cannot wait for the next minor release ships as the next patch of the line in the stores, from a branch at its tag (`v1.2.0` → `v1.2.1`):

1. **The branch:** `git fetch --tags && git switch -c release/1.2 v1.2.0`, or the existing `release/1.2` of an earlier patch. Bring the fix over from `main` with `git cherry-pick -x <commit>`; when `main` has moved too far, fix it on the branch and bring the fix to `main` afterwards in a pull request.
2. **The release commit** on the branch: `version: 1.2.1+1` in `app/pubspec.yaml` and Play's What's new for its version code (`1020199.txt` in `en-US` and `de-DE`), as in [cutting a release](#cutting-a-release); Cronet and Flutter stay as the tag had them unless the fix is theirs.
3. **German:** a new or changed English text reaches German only through Crowdin. When the fix cannot wait for it, set the repository variable `VIKUNJA_APP_ALLOW_INCOMPLETE_GERMAN` to the patch's tag, `v1.2.1` (Settings > Secrets and variables > Actions > Variables), and on the Mac `export VIKUNJA_APP_ALLOW_INCOMPLETE_GERMAN=v1.2.1` before `ios_release.sh` (owner, 2026-11-18). The release scripts then go on and log how many English texts German lacks, also as a warning on the run's summary; English stands in for them. They refuse the override for a tag of another release and for any `x.y.0` or its betas. Delete the variable after the release, and let the German follow on Crowdin.
4. **The dry run** on the branch, `tool/ci/release.sh --dry-run --tag v1.2.1`, then push the branch and the tag: `git push origin release/1.2`, `git tag -a v1.2.1 -m "Vikunja app 1.2.1"`, `git push origin v1.2.1`. The release workflow runs the whole CI for the tag, as for any release, and publishes after the approval; the iOS build follows from the tag on the Mac.
5. **Afterwards:** the fix on `main` (step 1), the hotfix in the release notes of the next minor release, and the warning on the faulty release's notes kept.

Play and the App Store install only higher versions, so a fix of an older line reaches only the devices that have not taken the newer one, and the APK users who stay on it; fix the newest line. A final release of an older line is not marked "Latest" on GitHub.

## The translations

English is the source; every other language comes from Vikunja's Crowdin project through the pull requests of Crowdin's GitHub integration, German included ([D88](decisions.md#d88-translations-through-vikunjas-crowdin-project)). Before the version bump of step 1 above:

```sh
python3 -I tool/l10n_progress.py --shipped-list   # each shipped language's share of the English texts
python3 -I tool/l10n_progress.py                  # every ARB file, shipped or not
```

- **German at 100 %:** `release_build.sh` refuses while German lacks an English text, and the dry run names the reason `German incomplete`. New and changed English texts reach German only through Crowdin: a changed text keeps its German there, but unapproved, and the export leaves it out until it is approved again. Ask Vikunja's German translators there (or translate, or re-approve, as a proofreader), then merge the integration's next pull request once its checks pass. Never add German to `app_de.arb` in a pull request: Crowdin's next pull request takes it out again. `ios_release.sh` runs the same check before a TestFlight build. Both name how many English texts German lacks. Only a patch release may go without them, through `VIKUNJA_APP_ALLOW_INCOMPLETE_GERMAN` set to its tag ([a hotfix](#a-hotfix); owner, 2026-11-18, relaxing [D88](decisions.md#d88-translations-through-vikunjas-crowdin-project)).
- **A shipped language below 50 %:** the build prints a warning and goes on. English grows with every feature, so a language falls behind without anyone touching it; ask its translators on Crowdin. Taking a language off is the reverse of adding one.
- **Adding a language:** once `l10n_progress.py` shows it at 50 % or more, in a pull request of its own, as [CONTRIBUTING.md](../CONTRIBUTING.md#adding-a-language) lists.

The widgets' and iOS's native texts are English and German only, outside Crowdin; any other language shows them in English.

## Crash reports

Since step 41 the app can send opt-in crash reports to Vikunja's Sentry, into the old app's project, as it is ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry); owner, 2026-11-21). Only a build made with the project's DSN has them; a build without it has no question, no switch and no running SDK.

- **The DSN:** the repository variable `VIKUNJA_APP_SENTRY_DSN` of go-vikunja/app (Settings > Secrets and variables > Actions > Variables), which the owner copies from the old app's code before the first tag whose builds should send reports ([beta.md](beta.md#1-the-repository-and-ci)): the DSN alone, with no spaces or line breaks, as `check_sentry_dsn` refuses a newline pasted after it. The new app's reports are told apart from the old app's by their release, `io.vikunja.app@<version>+<build>`. A variable, not a secret: every build carries the DSN, and the job `build` has no environment, so a variable of the environment `release` would not reach it ([D86](decisions.md#d86-ci-and-releases-on-github-actions)). It goes into no file of the repository.
- **Android:** the step of the job `build` that runs `tool/ci/release_build.sh` gets the variable in its environment (`VIKUNJA_APP_SENTRY_DSN: ${{ vars.VIKUNJA_APP_SENTRY_DSN }}`, which `tool/ci/test_github_workflows.py` checks), and the script passes it to the bundle and both APK builds as `--dart-define=VIKUNJA_APP_SENTRY_DSN=…`. A local [dry run](#the-dry-run) takes it from the shell the same way, and a test repository's from its own variable.
- **iOS:** `tool/ci/ios_release.sh` reads the same name from the Mac's shell and passes it to `flutter build ipa` the same way ([each TestFlight build](#each-testflight-build)).
- **Not printed by the scripts:** neither script prints it, but GitHub's log shows the environment of the step that runs `release_build.sh`, and a variable, unlike a secret, is not masked there, so the release job's log shows the DSN. That is harmless, as every build carries it. `check_sentry_dsn` (`tool/ci/release_lib.sh`) runs before the build: without the DSN it prints `notice: VIKUNJA_APP_SENTRY_DSN is not set, so this build has no crash reports (D113)` and the build goes on without them; with an https DSN on sentry.io or a subdomain it prints `OK: VIKUNJA_APP_SENTRY_DSN is an https DSN on sentry.io (D113).`; any other value fails the build without showing it, so a release cannot send to a host the network security config does not cover: `error: VIKUNJA_APP_SENTRY_DSN must be https://<key>@<host>/<project id>, the host sentry.io or a subdomain of it, without a port, a password, spaces, line breaks or anything after the id (D113); its value is not shown`. A dry run with a dummy DSN on another host fails the same way.
- **Checking a candidate:** a build with the DSN has the OK line in its log. On a device or emulator it asks "Send crash reports?" once after the first sign-in, its Account tab's "App lock and privacy" says "Crash reports: Off" (or On) under the title, and that page ends with "Send crash reports"; the [smoke test](#cutting-a-release) prints PASS "a build with crash reports asked once; No thanks declined them". A build without the DSN shows none of it. Neither the OK line nor the app shows the DSN; only the step's environment in GitHub's log does (above).
- **No symbols yet:** there is no Sentry auth token, and nothing uploads the R8 mapping, native symbols or dSYMs, so Java frames of classes that R8 renamed and native frames arrive without names ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry), Limits). An upload would need such a token as a secret of the environment `release` ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry), Open).
- **Licence notices on Android:** `tool/build_android_notices.py` puts the group `io.sentry` under Sentry Java's MIT licence (`tool/android_notices/sentry.txt`), `io.sentry:sentry-native-ndk` under sentry-native's (`sentry_native.txt`) and `com.abovevacant:epitaph`, sentry-android-core's tombstone decoder, under its own (`epitaph.txt`). It adds the code that Sentry Java vendors from `tool/android_notices/sentry_third_party_notices.md`, a copy of the `META-INF/SENTRY_THIRD_PARTY_NOTICES.md` in the `io.sentry:sentry` jar, and refuses it unless its SHA-256 is the one `SENTRY_NOTICES_SHA256` records for the locked version. `--check`, which `checks.sh` and the release build run, fails while `app/assets/legal/android.md` differs from what the script writes. iOS: [licence notices](#licence-notices).
- **Raising Sentry:** `sentry` and `sentry_flutter` are held at one exact version in `app/pubspec.yaml`. After a raise, write the locks and the verification metadata again ([Gradle's dependency verification](#gradle-dependency-verification)); copy the new jar's `SENTRY_THIRD_PARTY_NOTICES.md` over `sentry_third_party_notices.md` and record its SHA-256 in `SENTRY_NOTICES_SHA256`; compare `sentry.txt`, `sentry_native.txt` and `epitaph.txt` with the licences of the new versions at their tags; write `android.md`; on iOS, after a build has resolved the new sentry-cocoa, update `app/assets/legal/ios.md` and commit both `Package.resolved` with equal pins ([licence notices](#licence-notices)). Then go through the new versions' options with D113's lists: Dart's integrations are an allowlist, so a new one stays off, but the Android options are set one by one, so a new one keeps Sentry's default.

## Raising Cronet

The app embeds Cronet, Chromium's network stack, which only an app update brings up to date ([threat model](threat-model.md) R34). Google has published `org.chromium.net:cronet-bundled` three times in nine weeks so far (3 to 6 weeks apart), each 1 to 2.5 weeks after the Chrome stable release it is built from. Look at `https://dl.google.com/android/maven2/org/chromium/net/cronet-bundled/maven-metadata.xml` at each Chrome stable release and before each release of the app; the weekly workflow "Upstream versions" fails while it lists a newer version than `build.gradle.kts` pins. For a newer version:

1. **Check its POM:** the licence is still "Chromium License and licenses of built-in dependencies", and the dependencies are still `cronet` and the transitional artifacts that `app/android/app/build.gradle.kts` excludes (a new one needs its own exclude; the notices refuse any other `org.chromium.net` library).
2. **Raise the version** in `build.gradle.kts`, then write the locks and the verification metadata ([Gradle's dependency verification](#gradle-dependency-verification)), which builds the release APK and so fetches the new AARs, then copy their licences:

   ```sh
   python3 -I tool/build_android_notices.py --refresh-cronet
   ```

   `--refresh-cronet` checks both AARs against the SHA-256 that Google's Maven publishes, refuses a Chromium build that Chromium Dash does not list as a Chrome stable release for Android, copies the licence files into `tool/android_notices/cronet/` and writes `app/assets/legal/android.md`. Then check `CRONET_SUPPLEMENT` in `tool/build_android_notices.py`, what the native library links statically but the licence files do not name: `strings` on the AAR's `jni/arm64-v8a/libcronet.*.so` still shows `__Cr` names (libc++), `libc++abi:`, `libunwind:` and Rust's `panicked at`, and `third_party_licenses.txt` still names none of them; a new library of that kind gets its own entry and text.
3. **Test and commit:** run the tests (`embedded_cronet_test.dart` compares the declared version with `tool/android_notices/cronet/source.json`), check the app on a device or emulator, and commit `build.gradle.kts`, `gradle.lockfile`, `gradle/verification-metadata.xml`, `tool/android_notices/cronet/` and `android.md` together.

## Raising Flutter

The Flutter engine and the Dart runtime, with its BoringSSL and HTTP stack, ship in the app, and no scan sees their advisories ([threat model](threat-model.md) R26 and section 9): read [Flutter's changelog](https://raw.githubusercontent.com/flutter/flutter/stable/CHANGELOG.md) at each stable release and before each release of the app; the weekly workflow "Upstream versions" fails while Flutter's stable release is newer than the pin. On 2026-11-02 that found GHSA-frr6-h895-5pxp in 3.47.8 (BoringSSL in `dart:io` blocks compromised eMudhra intermediates, and on Android 14 and later `dart:io` uses the updatable Conscrypt root store), and the pin moved from 3.47.7 to 3.47.9, which also fixes a native-assets crash of `flutter test` in pub workspaces ([D77](decisions.md#d77-beta-preparation-new-app-id-own-signing-key-public-group-testers)). For a newer version:

1. **The pin:** in `tool/ci/pins.sh`, `FLUTTER_VERSION`, `FLUTTER_LINUX_SHA256`, the `sha256` of that version's stable Linux archive in `https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json`, and `FLUTTER_MACOS_ARM64_SHA256`, the `sha256` of its macOS arm64 zip in `releases_macos.json` beside it, which GitHub's macOS runner downloads (step 38c); the comment above them keeps the earlier pin. The developer guide's [prerequisites](development.md#prerequisites) name the version with its Dart, and the README's [Building from source](../README.md#building-from-source) and CONTRIBUTING.md's [Setup and checks](../CONTRIBUTING.md#setup-and-checks) name it too.
2. **The Mac's SDK:** run `flutter upgrade` from a folder outside the repository, for example `(cd ~ && flutter upgrade)`, until `flutter --version` prints the pinned version. Run inside the repository, it also upgrades the packages in the workspace's `pubspec.lock`. Afterwards `git status` must show no change, and `flutter pub get --enforce-lockfile` must resolve the committed lockfile.
3. **The engine's artifacts:** each Flutter version brings its own `io.flutter` engine artifacts, so write the verification metadata again ([Gradle's dependency verification](#gradle-dependency-verification)) before the Android build can run.
4. **The checks:** `tool/ci/checks.sh`, `tool/ci/test.sh`, `tool/ci/android.sh` and, on the Mac, `tool/ci/ios.sh`, which also boots a simulator for the XCTests, then both [dry runs](#the-dry-run); commit `pins.sh`, `app/android/gradle/verification-metadata.xml`, the README, the developer guide and CONTRIBUTING.md together. GitHub's runners download the pinned archives.

## Gradle dependency verification

`app/android/gradle/verification-metadata.xml` holds the SHA-256 of every file the Android build fetches from Maven repositories: the Gradle plugins, Kotlin, the Android Gradle plugin and its tools, the libraries of the app and its plugins, and Flutter's engine artifacts (step 40h). Gradle fails a build that fetches a file whose checksum differs or that the file does not list, on CI, in the release build and on a developer's machine alike. It was written on the Mac from the builds that run: the release APK, the bundle, the per-ABI APKs, the debug and profile APKs, the widgets' unit tests and `:app:dependencies`. The Linux and Windows builds of `aapt2` are trusted without a checksum, as only the macOS one was fetched there; a maintainer on Linux replaces that trust with their checksums by the command below. Sources and Javadoc that an IDE fetches are trusted too.

After a change of what Gradle fetches (a version in `app/android/app/build.gradle.kts` or `settings.gradle.kts`, a pub upgrade of a plugin with Android libraries, Cronet, a new Flutter version), write it again with the lockfile:

```sh
(cd app && flutter build apk --config-only)   # gradlew and local.properties, if missing
(cd app/android && ./gradlew --write-verification-metadata sha256 --write-locks :app:dependencies \
  :app:assembleRelease :app:bundleRelease :app:assembleDebug :app:assembleProfile :app:testDebugUnitTest)
```

Since step 41 it also lists Sentry's Android SDK, which sentry_flutter 10.4.0 brings ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry)): `io.sentry`'s `sentry`, `sentry-android`, `sentry-android-core`, `sentry-android-ndk`, `sentry-android-replay` and `sentry-bom` 8.64.0, `sentry-native-ndk` 0.17.6 and `sentry-spotlight` 8.64.0 (debug builds only); `com.abovevacant:epitaph` 0.2.0, which sentry-android-core needs; `kotlin-stdlib-jdk7` and `kotlin-stdlib-jdk8` 1.9.24, to which the lock moved from 1.8.0; and the `.module` file of `androidx.compose.ui:ui-util-android` 1.6.5, metadata only. They were written with the command below on 2026-11-21, and the diff added only new components with their SHA-256 and changed no checksum. `settings.gradle.kts` takes the Android Gradle plugin 7.4.2 off sentry_flutter's build script classpath, so neither that plugin nor its tools are fetched ([developer guide](development.md#security-checks-and-android-dependencies)).

Gradle adds what is missing and keeps the rest. Read the diff before committing it: new entries belong to the new versions; a changed checksum of a version already listed means that the file changed upstream, so stop and find out why. Entries of versions no longer used stay harmless; prune them by hand now and then, keeping the `<configuration>` block. A failed build names the file and links a report under `app/android/build/reports/dependency-verification/`.

## When the publish job fails

- **A `ci` job failed or was cancelled,** so `publish` never started. One cause lies outside the repository: `ios` cancelled after 15 minutes with "The job was not acquired by Runner of type hosted", when GitHub had no macOS runner free. "Re-run failed jobs" runs that job again and keeps the build, whose artifact lasts 14 days (fewer if the repository's artifact retention setting is lower). The release waits for `ios` on purpose: a tag that does not build on iOS is not released on Android either.
- **Before Google Play** (the check, the signing, a certificate): nothing is published yet. Fix the cause, for example a secret of the environment, and use "Re-run failed jobs", which keeps the build and asks for the approval again.
- **During or after publishing:** "Re-run failed jobs" too. Each step skips what is already published with the same content and fails on other content: Play by the version code already on its track, dl.vikunja.io by the object's `sha256` metadata, the GitHub release by downloading its files and comparing their SHA-256; a leftover draft release is deleted and created again.
- **Not "Re-run all jobs":** it builds and signs again, and the new APK need not equal the one already published, which dl.vikunja.io and the GitHub release then refuse.
- **To publish other files under a tag** that dl.vikunja.io or GitHub already has, delete the object from the bucket or the release on GitHub first. Play takes a version code only once.
- **`secret-scope` fails:** a release secret is also a repository or organisation secret ([step 2 above](#once-in-go-vikunjaapp)).
- **A fix in the repository,** `release_certificates.txt` included, needs a new commit and a new tag, the next beta or the next patch: the jobs check out the tag.

## The dry run

```sh
tool/ci/release.sh --dry-run                       # the tag defaults to v<the pubspec's version name>
tool/ci/release.sh --dry-run --tag v1.0.0-beta.1   # the pubspec must have that version
```

It runs the whole Android release locally except the publication. `release_build.sh` builds the bundle and the APKs unsigned with the release's checks, with `https://source.example/vikunja-app/tree/<tag>` standing in for the source link. `release_sign.sh` signs them with a throwaway JKS key, valid for one day, whose key password differs from its store password, and runs every check but the comparison with the committed certificates. Each publish step prints what it would publish and where, and why it does not; the Play step also names the languages of the What's new it would send ("Would send Play's What's new in de-DE, en-US …", or "Would send no What's new" for a beta without one). The script ends with `DRY RUN: NOT RELEASABLE (…)`; without `--dry-run` it refuses, as releases come only from go-vikunja/app. It needs Flutter, the Android SDK's build-tools (`apksigner`, `zipalign`, `aapt2`), a JDK and access to GitHub for the desugar_jdk_libs source; the files land in `build/release/unsigned/` and `build/release/signed/`.

The same rehearsal runs in a test repository on GitHub, any repository but go-vikunja/app, and publishes nothing there either. With the repository variable `VIKUNJA_APP_RELEASE_DRY_RUN=true`, a `v*` tag runs the jobs `build` and `dry-run`, the release's steps with `--dry-run`, without an environment or a secret; the source link is that repository's tree at the tag, and a private repository gives the reason `repository not public`; until the vikunja.io pages are published, each page that fails their check is a reason too. `VIKUNJA_APP_IOS_JOB=true` adds the job `ios` to its CI, which costs macOS minutes in a private repository. Without the variable a tag there runs only the CI. Such a repository holds no secret and no key.

A local `flutter build apk --release` is signed with the debug key and prints a warning, unless `app/android/key.properties` (gitignored) names a keystore with `storeFile`, `storePassword`, `keyAlias` and `keyPassword`; with `VIKUNJA_APP_UNSIGNED=true` it stays unsigned. Such builds are for testing only.

## iOS: TestFlight from the Mac

`tool/ci/ios_release.sh` builds the iOS app of a release tag on the owner's Mac, signs it with Xcode's automatic signing for the owner's team, checks it and uploads it to App Store Connect, which hands it to TestFlight and later to App Review. No CI job runs it: the job `ios` builds unsigned only, and the owner runs the release by hand once the tag's CI is green. Running it in CI would need the team's signing and the API key in CI secrets ([D74](decisions.md#d74-ios-phase-app-store-prerequisites-testflight-from-the-mac-photo-locations-capture-cover)).

### Once, before the first upload

1. **The Apple Developer Program:** the account that publishes the app, enrolled as an individual or an organisation; the App Store shows the enrolled name as the seller. The membership is renewed every year: when it lapses, the app leaves the App Store and takes no updates.
2. **The team id:** ten capital letters and digits, under Membership details in the developer account. The script reads it from `DEVELOPMENT_TEAM`. It is not secret (every signed build carries it, and Flutter prints it while signing), but it stays out of the repository so that a fork signs with its own team.
3. **Xcode signed in, with a device:** add the account under Xcode > Settings > Accounts, and register an iPhone with the team once: connect it to the Mac with Xcode open, or add its UDID under Certificates, Identifiers & Profiles > Devices. Automatic signing archives with a development profile, which Xcode cannot create for a team without a device ("Your team has no devices from which to generate a provisioning profile"); the export then signs for distribution. Automatic signing also needs the App IDs `io.vikunja.app` and `io.vikunja.app.widgets` (whether `io.vikunja.app` is still free at Apple is open, [D15](decisions.md#d15-app-id-iovikunjaapp-and-the-name-vikunja)), both with the App Groups capability and only the group `group.io.vikunja.app`, a distribution certificate and the profiles; Xcode creates what is missing on the first signed build (`flutter build ipa` passes `-allowProvisioningUpdates`). If it cannot, create the App IDs and the group under Certificates, Identifiers & Profiles > Identifiers.
4. **The app record:** in App Store Connect, Apps > + > New App: iOS, the name `Vikunja` ([D76](decisions.md#d76-store-listings-and-policies-the-apps-pages-photo-locations-removed-on-android); another only if App Store Connect refuses it, [D89](decisions.md#d89-store-listing-and-web-pages-of-the-official-app)), the bundle id `io.vikunja.app`, a SKU of your choice (for example `vikunja-app`). Creating the record reserves the name, so it can come before the first build. The listing, the screenshots and the App Privacy answers: [store-listing.md](store-listing.md#app-store-connect).
5. **The API key:** the Account Holder requests API access once under Users and Access > Integrations > App Store Connect API. Then generate a team key with the Developer role (it covers delivering builds; App Manager only if Apple refuses the upload with it) and download `AuthKey_<id>.p8`; Apple offers the file only once. Keep it outside the repository (`*.p8` is gitignored) with `chmod 600`: the script refuses a key file that other users can read. It reads three variables, prints none of them and takes them out of the environment before Flutter or Xcode runs, so that only altool gets them; altool gets the file's path, never its content:

   | Variable | Value |
   |---|---|
   | `VIKUNJA_APP_ASC_KEY_ID` | the key's id |
   | `VIKUNJA_APP_ASC_ISSUER_ID` | the issuer id shown above the team keys |
   | `VIKUNJA_APP_ASC_KEY_FILE` | the path of `AuthKey_<id>.p8` |

6. **The source link** (step 38c): `VIKUNJA_APP_SOURCE_CODE_URL`, the repository's https URL without `.git`, by default `https://github.com/go-vikunja/app`. The build links the repository's tree at the tag, `<URL>/tree/<tag>`, as the Android release does, so that each build says where its source code is; the About page shows it ([D87](decisions.md#d87-mit-vikunjas-contribution-rules-and-the-move-into-go-vikunjaapp)), and the script checks that it opens signed out. Until the import is merged (step 38d) go-vikunja/app has no such tag: set the variable to a public repository that has it.

### Each TestFlight build

After the tag's CI is green ([cutting a release](#cutting-a-release), step 3), on the Mac:

```sh
git fetch --tags && git checkout v1.0.0-beta.1
export DEVELOPMENT_TEAM=… VIKUNJA_APP_ASC_KEY_ID=… VIKUNJA_APP_ASC_ISSUER_ID=… VIKUNJA_APP_ASC_KEY_FILE=…/AuthKey_….p8
export VIKUNJA_APP_SOURCE_CODE_URL=https://github.com/go-vikunja/app   # the default; another public repository before the move
export VIKUNJA_APP_SENTRY_DSN=…   # the repository variable's value; without it the build has no crash reports
tool/ci/ios_release.sh --tag v1.0.0-beta.1
```

The script:

- refuses to run unless `xcode-select` points to Xcode (the native-asset build hooks ignore `DEVELOPER_DIR`), Flutter is exactly the version `tool/ci/pins.sh` pins, HEAD is the tag with a clean working tree, the source link opens signed out at the tag, each vikunja.io page of `RELEASE_WEBSITE_PAGES` opens signed out with its anchor, the team id and the three key variables are set, the App Store icon is 1024 × 1024, RGB without an alpha channel and untagged or sRGB, and German has every English text ([the translations](#the-translations));
- computes the version from the tag with `release_version.py` and runs the release-only source-link test;
- builds with `flutter build ipa --release`, the tag's version, `SOURCE_CODE_URL`, the crash reports' DSN when it is set ([crash reports](#crash-reports)) and generated export options: method `app-store-connect`, automatic signing, the team, and `manageAppVersionAndBuildNumber` off so that Xcode never changes the version;
- checks the archived `Runner.app` and `VikunjaWidgets.appex`: both carry the tag's version, the app declares `ITSAppUsesNonExemptEncryption` false, both privacy manifests are the committed ones, every required-reason API that a binary in them uses is declared (`tool/ci/required_reason_apis.py`, [below](#privacy-manifests)), and the licence page has every notice (`tool/ci/ios_notices.py`, [below](#licence-notices));
- requires exactly one IPA, since `flutter build ipa` reports success even when the export fails, prints its SHA-256 and uploads it with `xcrun altool --upload-package` and the key.

**The Swift package** (since step 41, [D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry)): sentry_flutter brings sentry-cocoa through Swift Package Manager, pinned in `app/ios/Runner.xcworkspace/xcshareddata/swiftpm/Package.resolved` (sentry-apple-binaries 9.34.0). The first build after a change fetches that repository and its two binaries, `Sentry.xcframework.zip` and `SentryObjC-Static.xcframework.zip` of sentry-cocoa's release, so it needs network; later builds take them from `app/build/ios/SourcePackages`.

App Store Connect takes only `MAJOR.MINOR.PATCH` as the version (`CFBundleShortVersionString`), so every beta of a release has the release's version and the Android version code as its build number (`CFBundleVersion`), which grows with every tag:

| Tag | Version | Build |
|---|---|---|
| `v1.0.0-beta.1` | 1.0.0 | 1000001 |
| `v1.0.0-beta.2` | 1.0.0 | 1000002 |
| `v1.0.0` | 1.0.0 | 1000099 |
| `v1.0.1-beta.1` | 1.0.1 | 1000101 |

On iOS the app therefore reports 1.0.0 with the build number for every beta of 1.0.0, for example the User-Agent `Vikunja-App/1.0.0+1000002`. A build number goes to App Store Connect only once per version, even when processing fails, and a version released in the App Store takes no more builds: a fix needs the next tag, as on Android.

The build shows up under TestFlight in App Store Connect after processing; Apple emails a problem found while processing, for example a missing API declaration. Internal testers (members of the team in App Store Connect) can install it at once; external testers, by invitation or a public link, only after Beta App Review has passed the first build of a version, which needs the test information of [store-listing.md](store-listing.md#app-store-connect): the public demo's account `demo` / `demo` in the sign-in fields, never in the notes, and the review notes ([Q21](open-questions.md#q21-a-server-for-the-store-reviewers)). The external group, its public link and each build's What to Test: [beta.md](beta.md#testflight).

### Export compliance

`ITSAppUsesNonExemptEncryption` is `false` in `Runner/Info.plist`, so App Store Connect asks no encryption questions for each build. The extension needs no such key; App Store Connect reads the app's. The app uses encryption only through standard protocols: HTTPS through the system's `URLSession`, and for servers with a pinned certificate, a private CA or a client certificate the TLS of Dart's `dart:io` (BoringSSL in the Flutter engine, [D65](decisions.md#d65-connection-settings-per-server-address-applied-in-the-apps-transport)); the Keychain for tokens and secrets; SHA-256 for PKCE, account ids and certificate fingerprints. None of it is proprietary encryption, which is what Apple counts as exempt from the export documentation. Apple's page adds that an app with exempt encryption may still owe the U.S. government a year-end self-classification report: check that once before the App Store release (step 37d). If App Store Connect asks anyway, the answer is that the app uses only exempt encryption. *Note 2026-11-02, step 37d ([D77](decisions.md#d77-beta-preparation-new-app-id-own-signing-key-public-group-testers)): checked for the United States: since BIS's rule of 29 March 2021 ([86 FR 16482](https://www.federalregister.gov/documents/2021/03/29/2021-05481/export-administration-regulations-implementation-of-wassenaar-arrangement-2019-plenary-decisions)) the annual report covers only mass-market components and executable software ([15 CFR 740.17(e)(3)](https://www.law.cornell.edu/cfr/text/15/740.17)), not an end-user app that uses only standard encryption, so none is due. France is open ([Q23](open-questions.md#q23-french-encryption-declaration-for-the-app-store)): Apple's [table](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption/) asks for a French encryption declaration for an industry-standard algorithm that the operating system does not provide, which BoringSSL in the Flutter engine is ([beta.md](beta.md#before-100)). Neither is legal advice.*

### Privacy manifests

`Runner/PrivacyInfo.xcprivacy` and `VikunjaWidgets/PrivacyInfo.xcprivacy` sit at the root of the app and of the extension, each in its target's resources (`tool/add_widget_extension.rb` adds them; rerun it after renaming either). Both say no tracking, no tracking domains and no collected data: Apple counts data as collected when it leaves the device in a way that the developer or the developer's partners can access, and apart from the crash reports below the app sends data only to the Vikunja server the user chooses. That is usually the user's own or their organisation's; the onboarding's "Try the public demo" fills in `https://try.vikunja.io`, which the Vikunja project runs, but the user picks it. The app has no analytics or advertising SDK. Since step 41 it has Sentry's for the opt-in crash reports, which go to Vikunja's Sentry once the user allows them ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry)): `Sentry.framework` declares that data in its own manifest (below), Runner's still declares none, and that, like every sentence that says the app collects no data, now depends on the App Privacy answer, which declares Crash Data and Other Diagnostic Data ([store-listing.md](store-listing.md#app-store-connect)). Until step 38f the developer had no access to the demo and no partnership with its operator, and App Store Connect's App Privacy answer, "Data Not Collected", rested on the same reasoning; if Vikunja's account publishes the app, the demo and Vikunja Cloud are the developer's own servers, so the label is open until the Apple account is decided, and the manifests follow its answer ([store-listing.md](store-listing.md#app-store-connect), [D89](decisions.md#d89-store-listing-and-web-pages-of-the-official-app)).

The required-reason APIs, from the code and from the symbols the release binaries import (`nm -u`), checked against [Apple's list](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) on 2026-10-29:

| Bundle | Category | Reason | Why |
|---|---|---|---|
| `Runner.app` | File timestamp | `C617.1` | Timestamps and sizes of files in the app container and the App Group container: the attachment cache pruned by modification date (`dart:io` `stat`, which the Flutter engine declares as a wrapper, `0A2A.1`), package_info_plus reading the creation date of the app's Documents folder and the modification date of the app bundle (its own manifest declares nothing), picked files copied into the container |
| `Runner.app` | User defaults | `CA92.1` | The app's own preferences through shared_preferences in the standard defaults; no App Group defaults |
| `Runner.app` | System boot time | `35F9.1` | Since step 41: sentry-cocoa, which sentry_flutter links into the app statically, uses `systemUptime`; Sentry's own manifest gives the same reason ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry)) |
| `VikunjaWidgets.appex` | File timestamp | `C617.1` | The extension prunes its list selections by the modification date of files in the App Group container |

Not declared: disk space and active keyboards. Before step 41 system boot time was not declared either (Dart's `Stopwatch` reads `clock_gettime_nsec_np`, which is not on the list; the engine declares its own `systemUptime`). Apple asks the bundle that holds a binary to declare its APIs, so a framework needs a manifest of its own. The extension uses no user defaults. The plugin `vikunja_widgets` uses none of these APIs; its Swift code is linked into the Runner and has no manifest of its own.

The plugins the app links bring their manifests as resource bundles inside the app: file_selector_ios, flutter_secure_storage_darwin, image_picker_ios, local_auth_darwin, package_info_plus, quick_actions_ios, share_plus, url_launcher_ios and webview_flutter_wkwebview declare no tracking, no collected data and no API; flutter_local_notifications and workmanager_apple declare user defaults `CA92.1`; shared_preferences_foundation declares user defaults `1C8F.1`; `Flutter.framework` declares file timestamp `0A2A.1` and `C617.1` and system boot time `35F9.1`. flutter_web_auth_2 has none and needs none (it uses no listed API). sentry_flutter brings no resource bundle; `Sentry.framework`, which the app embeds since step 41, declares user defaults `CA92.1`, system boot time `35F9.1` and file timestamp `C617.1`, and as collected data crash data, performance data and other diagnostic data, not linked to the user and not used for tracking, for app functionality.

**SQLite on iOS is the system's.** The frameworks that Flutter makes from the packages' build hooks have no manifest, and Flutter offers no way to give them one yet ([flutter/flutter#140966](https://github.com/flutter/flutter/issues/140966), [dart-lang/native#878](https://github.com/dart-lang/native/issues/878)). The SQLite that sqlite3's hook bundles (`sqlite3.framework`) imports `stat`, `fstat` and `lstat` and also `statfs` and `fstatfs`, disk space APIs: SQLite reads the file system's type to choose its locking, which none of Apple's disk space reasons describes ([sqlite3.dart#410](https://github.com/simolus3/sqlite3.dart/issues/410)). Since 1 May 2024 App Store Connect does not accept an app that uses such an API without declaring it, and a build refused in processing still uses up the tag's build number. The workspace's `pubspec.yaml` therefore has sqlite3's hook load the system's SQLite on iOS (`hooks.user_defines.sqlite3`, `/usr/lib/libsqlite3.dylib`, by its full path since `dlopen` searches `/usr/lib` only for old binaries); system libraries need no manifest, and Android keeps the bundled build. The app's SQL needs SQLite 3.30 (`NULLS LAST`; upserts 3.24), and iOS 15, the oldest the app supports, ships 3.36; the app's database tests pass on Apple's SQLite of macOS (3.51), but no build has run on iOS 15 itself yet. Apple's build keeps the WAL file (empty) and the shared-memory file after the last connection closes; the sign-out wipe deletes both with the database. `cupertino_http.framework` and `objective_c.framework` use none of the listed APIs. `tool/ci/required_reason_apis.py` checks this for every binary of the archive (`nm -u`, and the two listed Objective-C selectors in the bytes) against the manifests of its framework, or for the app's and the extension's executables against their bundle's and the plugins' resource bundles, and the release refuses an undeclared category.

### Licence notices

On iOS the licence page shows Flutter's `NOTICES` of the pub packages and the app's legal assets ([D67](decisions.md#d67-agpl-30-or-later-with-an-app-store-permission-dco-reserved-brand-embedded-cronet)). Flutter leaves out a package without a `NOTICES` or `LICENSE` file without a word, and the page leaves out an asset it cannot read, so `tool/ci/ios_notices.py` checks the built `Runner.app` ([D74](decisions.md#d74-ios-phase-app-store-prerequisites-testflight-from-the-mac-photo-locations-capture-cover)): every licence in each package's file is in `App.framework/flutter_assets/NOTICES.Z` (a package without one must be the repository's, under its `LICENSE`, or the Flutter SDK's, under the SDK's), the repository's `LICENSE` is listed under the name the app's own notice joins, the only frameworks are Flutter's, `App.framework` and the native assets of `NativeAssetsManifest.json`, and every legal asset of `app/lib/core/legal/app_licenses.dart` is bundled and equal to its source. The Android notice is bundled on iOS too but not shown.

Since step 41 it also checks the Swift packages fetched by URL, which are linked into the app statically and have no notice in `NOTICES.Z` ([D113](decisions.md#d113-opt-in-crash-reports-through-vikunjas-sentry)); today that is sentry_flutter's sentry-apple-binaries 9.34.0 (sentry-cocoa, MIT). It reads their pins from `app/ios/Runner.xcworkspace/xcshareddata/swiftpm/Package.resolved`, the file `flutter build ios` resolves and builds with, and requires each package to be listed in `app/assets/legal/ios.md` with its version and with its checkout's licence file (in `app/build/ios/SourcePackages/checkouts/`); the frameworks a package brings, `Sentry.framework` for this one (`SWIFT_PACKAGE_FRAMEWORKS`), are then allowed. It fails when the project's own copy, `app/ios/Runner.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`, which Xcode may write when the project is opened alone, pins anything else than the workspace's: it compares their pins (identity, location and state, in any order), not the whole files, so their format version and `originHash` may differ. Both files are committed; keep their pins equal: copy the workspace's over the project's, or delete the project's. `ios.md` is written by hand, a line per package with its licence text below; the licence page shows it on iOS only (`LegalAssets.ios`). The third-party code bundled inside sentry-cocoa is not listed, as its release carries no notices for it. The job `ios`, each TestFlight build and the iOS dry run run the script:

```sh
python3 -I tool/ci/ios_notices.py app/build/ios/iphoneos/Runner.app   # after flutter build ios --release --no-codesign
```
