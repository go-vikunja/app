# Decision log

ADR-lite. Each entry has a number, a status and the step that took it. A decision is replaced by a new entry, never edited away. The background for most entries is in [research/synthesis.md](research/synthesis.md) §2–3 and [research/flutter-stack.md](research/flutter-stack.md).

## D1: Flutter 3.47.5 pub workspace with pure-Dart packages

*Accepted, step 1.*

- **Context:** The app needs shared logic that runs in the UI isolate, in background isolates and in plain unit tests.
- **Decision:**
  - Use Flutter 3.47.5 / Dart 3.13.4, the stable release installed when step 1 started. The 3.47.6 hotfix is not adopted yet.
  - The repository is one pub workspace: `app`, `packages/vikunja_domain` and `packages/vikunja_api`, plus `packages/vikunja_logic` later.
  - It has a single `pubspec.lock`.
  - Lints are very_good_analysis 11, with `public_member_api_docs` off.
- **Consequences:**
  - `flutter pub get` runs only at the root.
  - CI pins the exact Flutter version.
  - Code uses the Dart 3.13 constructor syntax (`new(...)`, `factory name(...)`), which the lint `unnecessary_type_name_in_constructor` enforces.
  - `packages/*/lib` must stay Flutter-free, which is checked in CI.

## D2: material_ui and cupertino_ui

*Accepted, step 1.*

- **Context:** The Material and Cupertino libraries inside the Flutter SDK are being decoupled. The in-SDK Material library is scheduled for deprecation (Nov 2026).
- **Decision:**
  - New code imports `package:material_ui/material_ui.dart` (1.6.x) and `package:cupertino_ui/cupertino_ui.dart` (1.1.x), never `package:flutter/material.dart` or `cupertino.dart`.
  - Localisation delegates come from material_ui (`GlobalMaterialLocalizations.delegates`).
- **Consequences:**
  - There is no migration later.
  - Third-party widgets built on the legacy libraries may need wrappers.
  - Since step 25 the WebView plugin (`webview_flutter` and its Android and WebKit packages) imports the legacy Material library internally; the app's own code still never does ([D52](#d52-descriptions-edited-in-a-bundled-tiptap-page-in-a-locked-down-webview-with-a-native-toolbar-checklists-ticked-in-place-no-silent-overwrite-of-a-description-changed-on-the-web)).

## D3: Riverpod 3 with code generation

*Accepted, step 1.*

- **Context:** Every entry point (UI, background tasks, notification actions, widget callbacks) must build the same object graph without a widget tree.
- **Decision:** Use flutter_riverpod 3 with riverpod_annotation and riverpod_generator for dependency injection and state. A headless `ProviderContainer` serves the non-UI isolates.
- **Consequences:**
  - The app needs a build_runner step. The generated `*.g.dart` and l10n files are committed, and they are excluded from analysis and from the format check.
  - CI regenerates them and fails when the result differs from the committed files. After changing ARB files or annotated providers, run `cd app && flutter gen-l10n && dart run build_runner build`.
  - riverpod_lint is not enabled yet, because it would be a new dependency.

## D4: go_router

*Accepted, step 1.*

- **Context:** The app needs deep links (`vikunja-<app>://task/<id>`, pasted web URLs) and later a bottom-navigation shell with per-tab stacks.
- **Decision:** Use go_router 18. It is owned by flutter.dev, works with material_ui, and has `StatefulShellRoute`. Step 1 has two routes: connect (`/`) and server overview (`/server`, nested under `/`). `/server` redirects to `/` while no server is selected.
- **Consequences:**

  - go_router_builder (typed routes) can be added once there are enough routes to justify it.

## D5: dio with native_dio_adapter

*Accepted, step 1.*

- **Context:**
  - Self-hosters often use private CAs. On Android, `dart:io` ignores user-installed CAs (dart-lang/sdk#50435).
  - The client also needs interceptors for auth, retry and redacted logging.
- **Decision:**
  - Use dio 5 everywhere.
  - The app injects `NativeAdapter` from native_dio_adapter: Cronet on Android, NSURLSession on iOS.
  - The packages receive a configured `Dio` and never pick a transport.
- **Consequences:**
  - cronet_http clashes with another namespace under AGP 9 (dart-lang/http#1932). The workaround is `android.uniquePackageNames=false` in `app/android/gradle.properties`.
  - Flutter warns that plugins applying the Kotlin Gradle Plugin (KGP) will stop building in a future version; cronet_http is one of them. Until upstream fixes it, the template flag `android.builtInKotlin=false` stays.
  - Pinned or mTLS servers will need a per-server switch to `IOHttpClientAdapter` (step 35).
  - Without Google Play services (AOSP images, de-Googled or Huawei devices), every Cronet provider is disabled, so `createPlatformHttpAdapter` falls back to `dart:io`. That transport does not trust user-installed CAs. Embedded Cronet (`--dart-define=cronetHttpNoPlay=true`, about +6.5 MB APK) avoids this and is the option for F-Droid and other no-GMS builds ([Q3](open-questions.md#q3-licence-and-distribution), [research/flutter-stack.md](research/flutter-stack.md) §3.21).

## D6: v1/v2 negotiation with capability gating

*Accepted, step 1.*

- **Context:**
  - `/api/v2` exists only from 2.4.0 onwards and can be hidden by proxies.
  - Development builds report `dev`/`unstable` instead of a semver.
  - Admins and licences switch features on and off.
- **Decision:**
  - Probe `/api/v2/info` and `/api/v1/info` in parallel. A probe counts only for a 200 with a JSON body that has a string `version`. Every API version whose probe counts goes into `ServerConnection.apiVersions`. When both count, the v2 `/info` document is the one used.
  - Follow at most one redirect per connection attempt, and only when the resolved `Location` keeps the `/api/v1/info` or `/api/v2/info` path under another origin or sub-path, or is a same-host `http` → `https` redirect. The root derived from it is probed like any other candidate. An `https` → `http` downgrade is never accepted; an `http` → `https` upgrade is. Any other redirect off the host, or to a login-like path, is `BehindLoginProxy`.
  - Derive `ServerCapabilities` from the reachable API versions, version thresholds, the `/info` flags and `enabled_pro_features`.
  - Features check capabilities, never version strings alone.
- **Consequences:**
  - The adapter choice per API group follows `Capability.apiV2`.
  - Re-negotiation at login, every 24 h and after a "route absent" 404 is planned for steps 3 and 5.

## D8: Cleartext policy

*Accepted, step 1.*

- **Context:** Many self-hosted servers on a home LAN only speak plain `http://`. Using it silently would expose passwords and tasks to anyone on the network.
- **Decision:**
  - The OS configuration allows cleartext, so such servers can be reached at all:
    - Android: a network security config with `cleartextTrafficPermitted="true"` that trusts system and user CAs.
    - iOS: `NSAllowsArbitraryLoads`, plus `NSLocalNetworkUsageDescription`.
  - The connector tries `https` first. It tries `http` only when the user typed no scheme and every `https` candidate failed at the connection level (DNS, refused, timeout, or a TLS handshake failure). A rejected certificate does not count: a TLS server answered, so the connector reports `TlsFailure` and does not fall back to `http`.
  - The app uses an `http` server only after the user confirms an "Unencrypted connection" dialog, and marks it as unencrypted afterwards.
  - Only the `http` and `https` schemes are accepted.
- **Consequences:**
  - App Review may ask about `NSAllowsArbitraryLoads`.
  - A server with an untrusted certificate is reported as a TLS failure even when it also serves plain `http`, so the user is pointed at the certificate rather than at cleartext.
  - The OS permissions cannot be narrowed to the hosts users type:
    - iOS ATS exceptions are build-time only, so exception domains cannot name hosts typed at runtime.
    - On iOS 10 and later, adding `NSAllowsLocalNetworking` (or `NSAllowsArbitraryLoadsInWebContent` / `NSAllowsArbitraryLoadsForMedia`) makes iOS ignore `NSAllowsArbitraryLoads`. That would silently block confirmed `http` connections to fully qualified hosts (split-DNS LAN names, Tailscale `*.ts.net`, VPN hosts).
    - `NSAllowsArbitraryLoads` therefore stays as long as users can confirm `http` for arbitrary hosts. The in-app "Unencrypted connection" confirmation is the actual control.
    - Android's per-domain cleartext rules are build-time only as well, so `cleartextTrafficPermitted="true"` stays too.
  - `NSAllowsArbitraryLoads` also removes ATS's TLS 1.2 and forward-secrecy minimums for `https`. System certificate validation still applies.

## D14: Browser sign-in only

*Accepted 2026-10-09, step 1 review. From [Q4](open-questions.md#q4-login-methods). Plugin, `client_id` and redirect scheme: [D23](#d23-browser-sign-in-through-flutter_web_auth_2-client-id-and-redirect-uri).*

- **Context:** Vikunja plans to remove username and password login. On ≥ 2.3.0 the browser flow covers local, LDAP, every OIDC provider and TOTP, because the web frontend's login page handles them.
- **Decision:**
  - The only way to sign in is OAuth 2.0 + PKCE in the system browser: ASWebAuthenticationSession on iOS, Custom Tabs on Android (planned through flutter_web_auth_2). The code is exchanged at `/api/v2/oauth/token`, or at `/api/v1/oauth/token` on 2.3.x.
  - Not planned for now: a native password + TOTP form, API-token login, and OIDC in an embedded WebView.
  - The OAuth `client_id` and the redirect scheme are fixed in step 3. The scheme must start with `vikunja-` and must not be `vikunja-desktop` or `vikunja-flutter`.
- **Consequences:**
  - The app never handles passwords or TOTP codes.
  - OAuth sessions are always short (72 h without a refresh) and there is no 30-day "stay signed in". [D22](#d22-session-keep-alive-through-background-sync) keeps sessions alive.
  - Roadmap step 4 (password + TOTP, API tokens) is replaced by multi-account ([D16](#d16-multi-account-in-the-first-release)).
  - Managing TOTP and API tokens in the account settings (step 31) and guest access through link shares (step 32) are not sign-in methods and stay planned. Step 32's registration and password reset are re-scoped for browser sign-in when that step starts.

## D16: Multi-account in the first release

*Accepted 2026-10-09, step 1 review. From [Q6](open-questions.md#q6-multi-account).*

- **Context:** The architecture keeps tokens and one database per account from step 3 onwards.
- **Decision:**
  - The first release has an account switcher: add, switch and remove accounts (roadmap step 4).
  - An account is a server plus a user. Each account has its own tokens, database, outbox and sync state. The UI shows one active account at a time.
  - Background sync and reminders cover every signed-in account, not only the active one.
- **Consequences:**
  - The session manager (step 3) is multi-account from the start. Per-account providers are keyed by account id.
  - Removing an account signs it out and wipes its secure entries; from step 6 on it also deletes its database and cancels its notifications.
  - Notification payloads and widget data carry the account id, so a tap opens the right account.

## D17: Notification policy

*Accepted 2026-10-09, step 1 review. From [Q7](open-questions.md#q7-notification-policy-defaults).*

- **Decision:**
  - Local notifications only for undone tasks where the user is the creator or an assignee. Tasks that are visible only through shared projects or subscriptions get none.
  - Task reminders fire at their reminder time. A task with a due date also gets a due-date notification at the exact due time.
  - Android schedules both as exact alarms. The onboarding after the first sign-in asks for the notification permission and for exact-alarm access (`SCHEDULE_EXACT_ALARM`, denied by default on Android 14+). iOS asks for the notification permission at the same point.
  - No daily overdue digest for now.
- **Consequences:**
  - Without exact-alarm access Android falls back to inexact alarms (`inexactAllowWhileIdle`). The notification settings show this and link to the system setting.
  - The store release (step 37) needs the Play Console exact-alarm declaration.
  - A digest can be added later as a setting without changing the scheduler.

## D19: Quick-add quirk policy

*Accepted 2026-10-09, step 1 review. From [Q9](open-questions.md#q9-quick-add-quirks).*

- **Decision:** The Quick Add Magic port (step 13) keeps the web grammar but fixes four parser bugs, items 1–4 of the quirk register in [research/client-logic.md](research/client-logic.md) §20:

## D22: Session keep-alive through background sync

*Accepted 2026-10-09, step 1 review. From [Q5](open-questions.md#q5-session-lifetime). The refresh mechanism is refined by [D26](#d26-refresh-concurrency-single-flight-re-read-and-adopt-write-ahead-epoch).*

- **Context:** OAuth sessions end after 72 h without a refresh (`service.jwtttl`, sliding). With browser sign-in only ([D14](#d14-browser-sign-in-only)) there is no 30-day session.
- **Decision:**
  - The background sync (step 16) refreshes the session of every signed-in account at least about every 24 h, even when nothing else needs syncing.
  - Android uses WorkManager periodic work. iOS uses BGAppRefresh, which the OS runs at its own discretion.
  - The session manager (step 3) supports refreshing from background isolates: file lock, re-read, write-ahead.
  - Since step 2+3, opening or resuming the app checks the active session with `GET /user`; a check that has to refresh an expiring access token moves the 72 h window. Step 16 adds the background runs.
- **Consequences:** On iOS a session can still expire when the app is neither opened nor woken for 72 h. The account then goes to `needsReauth`: local data stays, the outbox pauses, and a "Sign in again" notification appears.

## D23: Browser sign-in through flutter_web_auth_2, client id and redirect URI

*Accepted 2026-10-09, step 2+3. Implements [D14](#d14-browser-sign-in-only). Since step 10 ([D44](#d44-task-detail-complete-rich-text-from-an-own-parser-of-the-web-editors-schema-details-and-comments-online-on-demand-deep-links-on-the-app-scheme)) the Android callback filter matches only `oauth/callback`, and iOS declares a URL type for the scheme, which task deep links use.*

- **Context:**
  - D14 makes OAuth 2.0 + PKCE in the system browser the only sign-in, and leaves the plugin, the `client_id` and the redirect scheme to this step.
  - Vikunja has no client registry. The `client_id` is free text that must match between the authorize and the token call (else 400 code 17001). The redirect URI's scheme must start with `vikunja-` (else 17002). There is no consent screen ([research/auth.md](research/auth.md) §7).
- **Decision:**
  - `client_id`: `dev.coderoftime.vikunja`, the app id ([D15](#d15-app-id-devcoderoftimevikunja)).
  - Redirect URI: `vikunja-dev.coderoftime.vikunja://oauth/callback`, so the callback scheme is `vikunja-dev.coderoftime.vikunja`. It is neither `vikunja-desktop` nor `vikunja-flutter`, as D14 requires.
  - The browser leg runs through flutter_web_auth_2 5.1.0: ASWebAuthenticationSession on iOS; on Android a Chrome Auth Tab where the browser supports it, otherwise a Custom Tab, with the plugin's `CallbackActivity`.
  - The browser session is ephemeral (`preferEphemeral: true`), so no web login in Safari or Chrome is reused. Vikunja has no consent screen and its callback carries only `code` and `state`, no `iss` (RFC 9207; `frontend/src/views/user/OAuthAuthorize.vue`). With a reused web login, a malicious server could send the sheet to another server's authorize page and receive a code, and the PKCE verifier with it, without the user noticing (a mix-up). This replaces the step 2+3 plan and [research/auth.md](research/auth.md) §15.1's advice not to set `preferEphemeral`.
  - "Sign in again" accepts only the account's own user. Another user is refused before anything is stored, and its new session is logged out best effort.
  - The app uses the plugin only through a `WebAuthenticator` interface; tests use a fake.
  - The authorize URL is `{frontend_url}oauth/authorize` (the server root + `/` when `/info` has no `frontend_url`) with an S256 challenge over a 32-byte random verifier and a 16-byte random state, both fresh per attempt. An `http://` `frontend_url` is never used for an `https://` server; the server root + `/` is used instead.
  - The token client does not follow redirects, and neither does any request that carries an access token.
  - The code is exchanged at `/api/v2/oauth/token` when `/api/v2` is reachable, otherwise at `/api/v1/oauth/token`, with a JSON body.
  - The callback must match the redirect URI's scheme and path and the state, and must carry a `code`. An `error` parameter is a failure. A cancelled sheet returns silently.
- **Consequences:**
  - Android declares the `CallbackActivity`, exported, with a `VIEW` / `DEFAULT` / `BROWSABLE` intent filter for the scheme. iOS needs no URL type for ASWebAuthenticationSession; step 2+3 verifies this on the simulator.
  - Every sign-in shows the Vikunja login form, and OIDC and SSO users sign in at their identity provider again each time. iOS shows no "… Wants to Use … to Sign In" prompt (checked on the iOS 18.6 simulator).
  - On Android, the plugin opens a Custom Tab instead of an Auth Tab for Chrome and Edge before 141, Samsung Internet before 28 and Firefox before 143, which it treats as lacking ephemeral support. There the sheet can share the browser's cookies and reuse a web login; other browsers may ignore the flag as well.
  - Signing out of the app does not end a web login the user has in the browser. Only the fallback browsers above would reuse it.
  - The mix-up is not fully closed: a malicious server can still show another server's login page, but the user has to type that server's credentials. Closing it needs a server change: RFC 9207 `iss` in the callback, or a consent screen that names the client. Worth raising upstream.
  - PKCE keeps an intercepted code useless to another app that claims the same scheme. Without a consent screen, though, any app with a `vikunja-…` scheme can get a token for a user who is signed in to the web app in the system browser. This is a server-side property.
  - The plugin's stable 5.x line predates both its UIScene migration (6.0.0-alpha.2) and its built-in Kotlin migration (6.0.0-alpha.0). 5.1.0 is used because 6.0 is still alpha. Under the app's UIScene lifecycle it finds the window through its `UIApplication.keyWindow` fallback; the sheet opens and cancels correctly on the iOS 18.6 simulator, and the Custom Tab on the Android emulator (step 2+3, without completing a sign-in). Flutter warns that the plugin's old Kotlin Gradle plugin setup will stop building in a future release, so the move to 6.0 is due once it is stable. If a version stops working, the `WebAuthenticator` interface allows a small platform channel of our own (ASWebAuthenticationSession and Custom Tabs) instead, recorded as a new decision.
  - **The iOS deployment target stays 15.0.** The plugin's README says 4.0 and later "require" iOS 17.4, but its `Package.swift` and podspec declare iOS 11, and the Swift source uses the iOS 17.4 `ASWebAuthenticationSession.Callback` API only behind `#available(iOS 17.4, *)`. Below 17.4 it falls back to `init(url:callbackURLScheme:completionHandler:)` (iOS 12+), which handles our custom scheme. Only `https` callbacks (universal links) need 17.4, and the app does not use them. The fallback is checked by reading the 5.1.0 source; it is not run on a device, because no simulator runtime older than iOS 18.6 is installed. A real iOS 15–17.3 device check belongs to the release checklist (step 37).
  - iOS logs that ASWebAuthenticationSession support for `http://` pages is deprecated. Servers on plain `http://` may lose browser sign-in in a future iOS release.
  - Code-grant sessions are never long-lived: 72 h without a refresh ends them ([D22](#d22-session-keep-alive-through-background-sync)).

## D24: Tokens in secure storage, readable after the first unlock

*Accepted 2026-10-09, step 2+3.*

- **Context:**
  - The refresh token is the most sensitive secret the app holds.
  - Background sync (step 16) and notification actions (step 15) must refresh tokens while the device is locked.
  - Principle 5 of the [architecture](architecture.md#1-principles): secrets live only in the Keychain or the Keystore.
- **Decision:**
  - flutter_secure_storage 11.x, with the entries `account.<id>.refresh_token` and `account.<id>.access_token` per account.
  - iOS: `KeychainAccessibility.first_unlock_this_device` and `synchronizable: false`.
  - Android: the plugin's v11 defaults (AES-GCM with a key wrapped by an Android Keystore RSA key). `android:allowBackup="false"`, set since step 1, keeps the entries out of Auto Backup.
  - The access token is stored as well, so another isolate can adopt a refresh result instead of refreshing again ([D26](#d26-refresh-concurrency-single-flight-re-read-and-adopt-write-ahead-epoch)).
  - No other place holds secrets: not SharedPreferences, not the database, not logs. The log redaction also covers `Bearer`, `access_token`, `refresh_token`, `code=` and `state=`.
- **Consequences:**
  - After a restart, nothing can refresh until the user unlocks the device once. Background runs before that must treat the locked Keychain like a network error: keep everything, retry later.
  - Tokens never leave the device through iCloud Keychain or backups. A backup restored onto another iPhone brings the account registry ([D25](#d25-account-registry-in-sharedpreferences-without-secrets)) but no tokens, so those accounts need a new sign-in.
  - Widgets and extensions get no keychain access group. Step 19 revisits this only if an extension must authenticate.
  - Changing the accessibility class later means rewriting the existing items.
  - iOS keeps Keychain items when the app is deleted, but not its preferences. The first UI start that finds neither the install marker (`auth.install_marker`) nor a registry therefore wipes secure storage once (`app/lib/core/auth/previous_install.dart`); a locked Keychain leaves the marker unset, so the next start tries again. A registry without the marker is an update from an older build and is left alone. On Android, deleting the app removes everything and the wipe finds nothing.
  - Deleting the app never logs its sessions out on the server. They end after 72 h without a refresh.

## D25: Account registry in SharedPreferences, without secrets

*Accepted 2026-10-09, step 2+3. Builds on [D16](#d16-multi-account-in-the-first-release).*

- **Context:**
  - The app starts with several accounts ([D16](#d16-multi-account-in-the-first-release)). The UI and background isolates need the account list, the active account and each account's server before any database exists (step 6).
  - From step 6 on, the per-account databases are found through this list.
- **Decision:**
  - The registry is JSON in `SharedPreferencesAsync`: the accounts (`Account`: id, server root, user id, username, display name, `addedAt`, `needsReauth`), the active account id, and each account's last server connection (root, reachable API versions, `/info` re-serialised by `serverInfoToJson`).
  - Account id: the first 32 hex characters of `sha256("${serverRoot}|${userId}")`. The same user on the same server is always the same account; signing in again replaces its session, and the old session is logged out best effort.
  - The registry holds no tokens or other secrets ([D24](#d24-tokens-in-secure-storage-readable-after-the-first-unlock)).
  - `SharedPreferencesAsync` rather than the cached legacy API: every read goes to the platform store, so a background isolate never works on a stale in-memory copy.
- **Consequences:**
  - The registry and secure storage are written separately and can disagree after a crash or a restore. An account without tokens is handled like `needsReauth`: the accounts provider marks it when the app starts (`app/lib/core/auth/accounts_without_tokens.dart`), and a session manager that finds no tokens ends the session the same way. Secure storage that cannot be read (the Keychain before the first unlock) does not count as missing tokens.
  - The id depends on the normalised server root. The same server reached through two different addresses (a LAN IP and a domain) gives two accounts.
  - An entry that cannot be decoded is left out of the state but written back unchanged, so it is not lost; a readable entry with the same id replaces it. A registry that cannot be decoded at all is copied to `auth.account_registry.unreadable` before it is first overwritten.
  - Step 4 builds the switcher on this registry. Step 6 names the database files by account id.

## D26: Refresh concurrency: single-flight, re-read and adopt, write-ahead, epoch

*Accepted 2026-10-09, step 2+3. Refines the mechanism that [D22](#d22-session-keep-alive-through-background-sync) names ("file lock, re-read, write-ahead").*

- **Context:**
  - Vikunja rotates the refresh token on every refresh and has no grace period. Reusing a rotated token gives 401 code 16002 and the session cannot be recovered; the loser of a concurrent rotation gets 16004 ([research/auth.md](research/auth.md) §4.1).
  - Several isolates can refresh the same account: the UI isolate now, background tasks and notification actions later (steps 15–16).
  - A response that is lost after the server committed a rotation also kills the session.
- **Decision:**
  - Single-flight: one refresh per account and isolate at a time.
  - Before calling the server, re-read the stored refresh token. If it differs from the caller's snapshot, adopt the stored tokens and skip the call.
  - On 16002 or 16004, re-read storage a few times with short delays and adopt a newer token if one appears. Only then is the session ended (`needsReauth`).
  - Write-ahead: persist the rotated tokens before the new access token is used.
  - The refresh request is not tied to UI cancellation and has a generous timeout.
  - A per-account auth epoch, increased by sign-out and account removal. A refresh that finishes under an older epoch is discarded. Sign-out retires the session manager first and wipes storage afterwards; the retired manager hands out no token and writes nothing until a new sign-in replaces it. `retire()` waits only for a storage write that has already started, never for a refresh still on the network.
  - Every session-ended answer re-reads storage first: 16002 and 16004 as above, and also 16003 and 412, which are about the session of the token sent. A session that another isolate stored meanwhile is adopted.
  - If the secure write after a successful refresh fails, the new tokens stay in memory and are written again before the next refresh; newer tokens in storage win.
  - Expiry is judged with the per-account server clock offset stored in preferences, so a cold start or a new isolate need not wait for a response.
  - Failure classes: network errors keep the tokens for a later retry; 5xx is retried once; 429 waits for `Retry-After`, capped at 10 min; a session-ended answer (16002 after re-reading, 16003, 412 code 1020 or 1040) marks the account `needsReauth` and keeps its local data.
  - Cross-isolate lock: `RandomAccessFile.lock` does **not** serialise two isolates of one process. POSIX record locks belong to the whole process, so a second isolate acquires a lock the first still holds (verified on the macOS host by `app/test/core/auth/file_lock_isolates_test.dart`; Android and iOS use the same `fcntl` locks). The re-read and adoption rules above are therefore the only cross-isolate mechanism, as documented in `app/lib/core/auth/session_manager.dart`.
  - A 5xx on refresh can be a lost race too: SQLite servers answer the loser with 500 instead of 16004 ([research/README.md](research/README.md) item 7). Before the one retry, storage is re-read; a newer token found there is adopted instead of retrying with the dead one.
- **Consequences:**
  - The session manager is the only code that refreshes. `vikunja_api` sees it only through `AccessTokenSource`.
  - Without a lock, two isolates can send the same refresh token at once. The loser then adopts the winner's tokens once they are written, so the adoption re-reads must outlast the winner's write-ahead.
  - The remaining risk is a response lost after the server rotated: the process is killed mid-request, or the network drops. That session ends in `needsReauth`. Background runs must not start a refresh with only seconds of runtime left (step 16).
  - Retirement is per isolate. A sibling isolate can still write tokens back after a sign-out in another isolate; step 16 needs a guard for that.

## D31: One Drift SQLite file per account, shared across isolates, deleted on sign-out

*Accepted 2026-10-10, step 6. Implements principle 1 of the [architecture](architecture.md#1-principles) and the per-account database of [D16](#d16-multi-account-in-the-first-release).*

- **Context:**
  - Since step 5 the screens read through repository interfaces ([D29](#d29-ui-reads-through-repository-interfaces-the-online-implementation-is-replaced-by-drift-in-step-6-without-ui-changes)), but nothing survives a restart and the app needs the server.
  - Background sync, notification actions and the widget callback (steps 15–18) will open the same database from other isolates. The iOS widget extension is a separate process and never opens it ([research/flutter-stack.md](research/flutter-stack.md) §3.2–3.3).
  - drift 2.35 runs on sqlite3 3.x, which ships SQLite through a Dart build hook; `sqlite3_flutter_libs` is end-of-life.
- **Decision:**
  - drift 2.35 with drift_flutter 0.3 and sqlite3 3.7 (build hook, prebuilt SQLite with verified hashes; no `sqlite3_flutter_libs`).
  - One database per account at `<application support>/accounts/<accountId>/vikunja.db` (`AccountDatabaseFiles.pathFor`), opened through `driftDatabase(name:, native: DriftNativeOptions(databasePath:, shareAcrossIsolates: true))` in WAL mode. Never in the iOS App Group container. Not encrypted: the file holds no secrets, and an encrypted database would need its key in every background isolate.
  - Schema version 1: `projects`, `project_views`, `labels`, `users`, `tasks`, `task_labels`, `task_assignees`, `task_reminders`, `task_relations` and the key-value `sync_state`; indexes on `tasks(project_id)`, `tasks(done, due_date)` and `project_views(project_id)` (the primary key `(task_id, label_id)` of `task_labels` doubles as its `task_id` index). Ids are the server ids. Every entity row keeps the server's `created` and `updated`, because step 7's delta sync keys on `updated`. Dates are nullable UTC epoch milliseconds. Related tasks are stored as relation rows only; a task's `relatedTasks` is rebuilt from the rows whose other task is local. Tasks carry `sync_run_id`, the run that last returned them, so the purge at the end of a run survives a restart. Reminders have no server id and are keyed by `(task_id, ordinal)`.
  - Foreign keys with `ON DELETE CASCADE` from the task child tables to `tasks`, from `task_labels` to `labels`, `task_assignees` to `users` and `project_views` to `projects`; none on `tasks.project_id` (a task can arrive before its project, and the purge keeps them in step) or `task_relations.other_task_id` (the other task may be one the user cannot read).
  - The schema is dumped to `app/drift_schemas/drift_schema_v1.json` (`dart run drift_dev schema dump`, drift_dev's file name), the test helpers are generated from the dumps (`drift_dev schema generate` into `app/test/core/db/generated/`), and a test checks that the generated schema still matches the code. Every later schema change bumps the version, adds a dump and a migration test on that harness.
  - Pseudo projects (Favorites `-1`, saved filters `≤ -2`) are not stored in step 6. The sync skips them, because no screen shows them yet; step 24 (saved filters) decides their storage.
  - No bucket, position or outbox columns yet, which settles the open point of [D30](#d30-kanban-board-reads-deferred-to-step-20): step 11 adds the outbox and the merge columns (`base_json`, `dirty_fields`, `sync_status`), step 20 the bucket tables, each by a migration.
  - Sign-out and account removal close the database and delete the file with its `-wal`, `-shm` and `-journal` companions (`AccountDatabaseFiles.deleteFor`); the order of the token and registry wipe ([D26](#d26-refresh-concurrency-single-flight-re-read-and-adopt-write-ahead-epoch)) is unchanged. Local data of an account in `needsReauth` stays ([D22](#d22-session-keep-alive-through-background-sync)).
- **Consequences:**
  - The database, like the session manager, is a provider keyed by the account id (`appDatabase(accountId)`), closed on dispose and on sign-out through an `OpenDatabases` registry, so that sign-out can await the close before it deletes the files. With `shareAcrossIsolates`, `close()` only disconnects the client and the database isolate closes sqlite afterwards on its own, so the registry waits until the isolate has removed its `IsolateNameServer` mapping (polled every 20 ms, up to 5 s, logged on timeout) before the wipe deletes the files; a client in another isolate (step 16) keeps the isolate alive past that wait and must be stopped first, or a re-opened account would attach to the old isolate and write into an unlinked file. `shareAcrossIsolates` finds the running database server through `IsolateNameServer`, so every isolate of the process shares one connection and one stream-update bus. It must be closed explicitly.
  - Per-account files make an `account_id` column unnecessary; the research schema ([research/sync.md](research/sync.md) §9.2) had one.
  - Android's `allowBackup="false"` keeps the file out of Auto Backup. On iOS it is part of the device backup; it holds no secrets.
  - `flutter build` needs the sqlite3 build hook to fetch its prebuilt library (honours `HTTPS_PROXY`); an F-Droid flavour would compile from source (`hooks.user_defines.sqlite3`).
  - Switching accounts switches databases, so an account switch never shows another account's rows.

## D32: Initial sync by keyset paging with per-page checkpoints; full re-pull as refresh until step 7

*Accepted 2026-10-10, step 6. The incremental delta and the delete reconciliation are step 7.*

- **Context:**
  - Verified server facts ([research/sync.md](research/sync.md) §9, [research/api-v1.md](research/api-v1.md) §1.4, [research/api-v2.md](research/api-v2.md) §3.2): `GET /tasks` excludes the tasks of archived projects; keyset paging by id (`filter=done = false && id > <lastId>`, `sort_by=id&order_by=asc`) works on both API versions; the server caps `per_page` silently at `max_items_per_page`; the project list repeats the pseudo projects on every page; Vikunja leaves no tombstones.
  - Page-number paging is neither resumable nor stable while the data changes.
  - The app can be killed during the first pull of a large account.
- **Decision:**
  - `DefaultSyncEngine`, one per account, headless (no `BuildContext`, no Riverpod inside; the read client, the database, a clock and a `GET /user` source are injected, because the read client has no user port). Runs are serialized per account; a call during a run joins it. `status` replays the current `SyncStatus` on subscription, once the stored state has been read.
  - Phases, in order: `account` (`GET /user`) → `projects` (all pages, `is_archived=true`, upsert and purge the projects the server did not return) → `labels` (all pages) → `tasks` (two `per_page=1` requests for the total, then keyset `done = false`, then `done = true`, `per_page = info.max_items_per_page`, `page: 1` on every request, following the returned page size) → `archivedTasks` (the same keyset on `GET /projects/{id}/tasks` for every archived project and its descendants) → `finishing` (purge the tasks not seen in this run, write `last_synced_at`).
  - After every page the engine checkpoints run id and start time, phase, done count and total, last id, done filter and archived project id in `sync_state`. `ensureInitialSync()` resumes an interrupted run from that checkpoint and returns at once for an account that has completed a run. `refresh()` starts a new run id, re-pulls everything and purges by "not seen in this run"; purging happens only in `finishing`, so an interrupted run never deletes.
  - Every keyset page must be strictly ascending by id and start above the cursor; otherwise the run fails as `UnexpectedResponse` before the page is stored. A server that applied another order to `/tasks` or `/projects/{id}/tasks` would make the cursor skip ids, and the purge would then delete them silently.
  - Before the purge, `finishing` makes one more keyset pass over `GET /tasks` with `updated >= <newest updated at the start of the task phase − 120 s>` and marks its rows with the run id. The bound is a server time, the newest task `updated` the server reported in one `per_page=1` request sorted by `updated` descending before the open pass began (since step 7; step 6 used the device clock at the run start, which a device clock ahead of the server moved past a flip during a long run). A task reopened after the open pass had passed its id, and completed again after the done pass had, is returned by neither filter and would otherwise vanish until the next refresh; the 120 s overlap is the one step 7's delta uses for the server's commit lag. Tasks of archived projects cannot change, so `/tasks` suffices.
  - A failed request ends the run with `SyncFailed(failure, lastSyncedAt)`; rows from earlier runs stay readable, and `refresh()` rethrows the failure to its caller, as the repository contract of [D29](#d29-ui-reads-through-repository-interfaces-the-online-implementation-is-replaced-by-drift-in-step-6-without-ui-changes) requires. A stored state the engine cannot read when it is built is reported as `SyncFailed(UnexpectedResponse, lastSyncedAt: null)` and read again on the next call, so the first-sync screen's Retry covers a damaged file as well.
  - `SyncRunning.initial` stays true until the first run has completed: the app shows a blocking first-sync screen then (cancel = sign out) and a quiet indicator afterwards. An account that has synced opens the shell at once and refreshes quietly on start; a `NetworkFailure` with cached rows is an "offline" notice, not an error.
  - Until step 7, `refresh()` is this full re-pull. Step 7 replaces it with the `(updated, id)` delta, the project diff and the count checks; the stored `updated` and the run-id purge are built for that.
- **Consequences:**
  - The local repositories serve every list from the database: `showDone` is a WHERE clause, `loadMoreProjectTasks` is a no-op and `PagedList.hasMore` is false. The 5-page cap on the overview ([D29](#d29-ui-reads-through-repository-interfaces-the-online-implementation-is-replaced-by-drift-in-step-6-without-ui-changes)) is gone.
  - A refresh costs about `tasks / max_items_per_page` requests plus the project, label and archived-project pages, on every pull-to-refresh. Large accounts feel this until step 7.
  - Kanban buckets and positions are not synced ([D30](#d30-kanban-board-reads-deferred-to-step-20)); comments and attachments are not either.
  - The engine is contract-tested against the live 2.7.0 server from an app test tagged `contract` (`VIKUNJA_CONTRACT=1 flutter test --tags contract` in `app/`), because it needs the app's database code.
  - Step 16 can run the same engine in a background isolate through the same `ProviderContainer`; the `SyncStatus` of a run in another isolate is not shared yet.

## D33: Incremental sync: watermark on `updated` with a 120 s overlap, keyset over (updated, id), delete detection by per-project count check and id reconcile, daily full resync

*Accepted 2026-10-10, step 7. Replaces the "full re-pull as refresh" part of [D32](#d32-initial-sync-by-keyset-paging-with-per-page-checkpoints-full-re-pull-as-refresh-until-step-7); the initial sync of D32 is unchanged and stays available as the full resync.*

- **Context:**
  - Since step 6 every `refresh()` re-pulls the account: about `tasks / max_items_per_page` requests plus the project, label and archived-project pages, on every pull-to-refresh ([D32](#d32-initial-sync-by-keyset-paging-with-per-page-checkpoints-full-re-pull-as-refresh-until-step-7)). A sync on a timer is out of the question at that price, and web changes should appear on the phone after one sync.
  - Verified server facts ([research/sync.md](research/sync.md) §2–§3 and §7, [research/api-v1.md](research/api-v1.md) §4.1–4.2): `updated` is filterable and sortable; filter values are RFC 3339 and converted to UTC; timestamps have second granularity; the server appends `id asc` as the final tie-breaker unless the last sort is already `id`; parentheses and `||` are allowed in filters (16 KiB, 100 levels). `tasks.updated` is bumped by task edits (done, dates, favourite, reminders, assignees in the body) and by label add and remove, **asynchronously** by comment, attachment, relation and assignee changes through an event listener, and not at all by pure position or bucket moves. `projects.updated` is bumped by task create, update and delete, label changes and share or team changes, not by a favourite or subscription toggle. `GET /tasks` leaves out the tasks of archived projects. Deletes leave no tombstone: a deleted task is absent (404, code 4002 on a single read); project deletes are hard and cascade; losing access makes a project and its tasks vanish from the list. `GET /projects` with `is_archived=true` returns everything the user can see, flat. v2 returns `total`; v1 has no total, but with `per_page=1` the page count from the headers is the item count. A label rename does not bump `tasks.updated`.
  - The general API rate limit is off by default and 100 requests per minute per user when on; `Cache-Control: no-store` on every API response rules out HTTP caching; the login limiter does not apply to authenticated routes.
- **Decision:**
  - `SyncEngine.refresh()` is the incremental run. `fullResync()` is the full pull of [D32](#d32-initial-sync-by-keyset-paging-with-per-page-checkpoints-full-re-pull-as-refresh-until-step-7) with its purge by run id, and `ensureInitialSync()` is unchanged. Every completed run writes `last_synced_at` (`SyncIdle.lastSyncedAt` keeps meaning the last completed run of any kind) and the task watermark (`sync_state` key `watermark`): the newest task `updated` the database holds when the run completes, `MAX(tasks.updated)`, a server time, never the device clock, and never lower than before; an account without tasks stores 1970, so its delta asks for everything, which is nothing. The full pull writes `last_full_sync_at` as well. The new state lives in `sync_state`; the schema stays at version 1.
  - An incremental run is serialized with the other runs (a `fullResync()` asked for during an incremental run follows it rather than joining it, because joining would resolve without the full pull), reported as `SyncRunning(initial: false)` from before its first request, with phases of its own, and does, in order:
    1. **Projects:** all pages with `is_archived=true`, diffed against the local table. A project the server no longer lists is purged with its tasks (the foreign keys cascade through the task child tables); a project that was not local before is *added*, one that was archived and no longer is *un-archived*, an archived one whose `updated` differs, or that is newly archived (itself or through a parent, which takes its tasks out of `GET /tasks`), *changed*: the archive may have followed a task edit inside the second a sync last saw, which leaves `updated` as it was; a live project needs no such flag, its tasks come through `GET /tasks`. Only rows that differ from the local ones by value (the favourite flag bumps no `updated`) are written, so a run that finds nothing new leaves the database's watchers alone; the archived set is noted. The ids of the projects to pull whole are written with the rows (`sync_state` key `pending_whole_pull`): a run that fails afterwards would otherwise find them local and unchanged, and an archived project shared while archived would stay empty until the daily full pull; a completed run clears the key. The list is walked by page number, so when the server's count (`total` on v2, the page count on v1) changes between two pages, an item deleted meanwhile has shifted the next page's first item into the page already fetched, and the walk starts over (three times at most, then the run fails as `UnexpectedResponse`); on v1 a delete that leaves the page count unchanged goes unnoticed for that run, and a project it dropped comes back as *added* on the next one.
    2. **Labels:** all pages with the same guard against a change while paging, upsert the ones that differ, purge the ones not returned. Labels are few, and task rows take their labels from the `labels` table by id, so a rename shows without any task change.
    3. **Task delta** on `GET /tasks`: keyset over `(updated, id)` from the watermark minus 120 s. The first page has `filter=updated >= '<W − 120 s>'`, every later page `filter=(updated > '<U>') || (updated > '<U − 1 s>' && id > <I>)` with `(U, I)` the last item of the previous page, always `sort_by=updated&sort_by=id&order_by=asc&order_by=asc` and `per_page` = the server's maximum. The tie clause is not `updated = '<U>'`: Vikunja 2.7.0 compares a date filter value as if it sat just above its second (`>=` behaves like `>`, `<` like `<=`, `=` never matches; verified on both API versions with sort direction and fractional-second values), and timestamps are whole seconds, so `updated > '<U − 1 s>'` means `updated >= '<U>'` under the server's and the exact semantics alike. Of every page, the rows that differ from the local ones are upserted in one transaction: every change bumps `updated`, asynchronously for the listener's changes, which the overlap re-reads. The overlap covers the listener's lag and the second granularity; the rows it returns again unchanged are not written.
    4. **Archived projects:** an archived project whose `updated` changed gets the same delta over `GET /projects/{id}/tasks`, because `/tasks` leaves it out. An added or un-archived project gets the full keyset-by-id pull of its tasks instead, because they may carry `updated` values older than the watermark; the ids it returns are complete, so the project's local tasks not among them are purged right there (no separate count).
    5. **Delete detection:** a deleted task leaves no trace, and `projects.updated` has second precision, so a delete inside the second the previous sync saw leaves the project looking unchanged (the contract test showed it deterministically). Delete detection therefore does not key on `projects.updated`: one probe, `GET /tasks?per_page=1`, gives the server's count of live tasks (`total` on v2, the page count on v1), compared with the local count outside the archived projects. Only on a mismatch are the live projects counted one by one with `GET /projects/{id}/tasks?per_page=1`, and the ones whose count differs reconciled: keyset by id over `GET /projects/{id}/tasks` without a done filter (the endpoint returns done tasks without one; no view is involved), upserting the rows and purging the project's local tasks whose ids were not returned, after its last page. A `NotFound` with Vikunja's code 3001 means the project was deleted, a `Forbidden` with code 7003 that the user lost access to it (verified on 2.7.0 on both API versions: only a deleted project answers 404/3001, an unshared one 403/7003); either way it is purged with its tasks. When the probe matches, no project is counted. Tasks of archived projects cannot change (the server refuses edits and deletes there with 412), so they stay outside the probe. A move is caught by the delta already, because it bumps the task's `updated`; the counts of both projects then match.
    6. **Finishing:** watermark := max(`MAX(tasks.updated)` over the rows not more than 1 h ahead of the device clock, old watermark): a row from a server whose clock once ran fast would otherwise put every delta in the future for good, so such a row is logged and left out; `last_synced_at` := now; `pending_whole_pull` cleared; `SyncIdle`. A failure anywhere keeps the old watermark and the old rows and emits `SyncFailed`; because a project's tasks are purged only after its last page, an interrupted run never purges by a partial result. The incremental run has no checkpoint: it is short and restarts from the watermark.
  - **24 h rule:** `refresh()` runs `fullResync()` instead when `last_full_sync_at` is missing or older than 24 h, or when no watermark is stored (a database written by step 6). The daily full pull catches what the delta cannot see: positions and bucket moves, any server-side change that bumped no `updated`, and a count that matched by coincidence. It sets the watermark afresh (no max with the old one), so a value a fast clock once stored goes with it.
  - **Keyset filter:** the parenthesised `||` filter is proven by the contract test on 2.7.0 on both API versions with `per_page=5`, so that several delta pages occur: the test asserts the first page's `updated >=` filter, the parenthesised form of every continuation and the `updated, id` sort. Neither version rejects it, so there is no page-number fallback.
  - **Triggers** (`features/sync/application/`): `StartupSync` on the shell's first frame and on an account switch, unchanged except that it is incremental now. A `ForegroundSyncScheduler`, one per active account, runs `refresh()` on resume (after a pause or hide; a focus change alone, such as a dialog or the notification shade, is not one) when the last run finished more than 60 s ago and every 60 s while the app is in front; after a `SyncFailed` with a `NetworkFailure` the interval doubles up to 5 min and resets on success; it never overlaps (it joins the engine's run) and stops when the app is paused or hidden, on sign-out and while nothing listens to its provider (the first-sync screen), because a provider without listeners is not rebuilt either; its clock and timer are injectable. Pull-to-refresh and "Sync now" stay incremental; the Account tab gets a secondary "Full resync" (`fullResync()`), disabled during a run and in `needsReauth`. Nothing runs in the background (step 16), no WebSocket (step 17).
  - **Budget:** a run that finds nothing new costs the project pages, one labels page, one empty delta page and the count probe: 4 requests for a small account (5 since step 13, which reads the user and its settings on every run, [D38](#d38-quick-add-the-web-grammar-in-vikunja_logic-with-d19s-fixes-weekday-and-ordinal-dates-at-the-default-time-and-an-unknown-project-kept-in-the-title-a-live-composer-labels-created-online-and-assignees-looked-up-on-submit-the-task-through-the-outbox)), which the contract test asserts (`GET /projects`, `/labels`, `/tasks` with the delta filter, `/tasks?per_page=1`); the engine logs the request count of every run at FINE. With the 60 s timer that is at most 240 requests per hour, well below the server's optional limit of 100 per minute. Changes add the delta pages, the delta of each changed archived project, one count request per live project when the probe differs, the reconcile pages of a project with a mismatch and the full pull of a new or un-archived project.
  - **Rejected alternatives:**
    - **CalDAV `sync-collection`** (RFC 6578, Vikunja 2.4.0) reports deleted tasks per project since a sync token, but needs CalDAV credentials (Basic auth with a CalDAV token the user would have to create in the web app, which browser sign-in does not give the app, [D14](#d14-browser-sign-in-only)), XML handling and one token per project, and a token older than 30 days forces a full resync anyway.
    - **Webhooks** fire on a server-side event to a public HTTPS URL per project; a phone has no such URL, a relay would be a push service of its own ([D20](#d20-scope-cuts-and-desktop-adaptations)), and webhooks are per project and per project admin, not per user.
    - **Full id reconciliation of every project on every run**, the research's safety net ([research/sync.md](research/sync.md) §3.2), costs as much as the full pull. It is what the daily full resync does, once a day.
    - **`filter=id in …` over chunks of local ids** (research §3.2, item 4) pages at 50 as well, needs the chunks to stay under 16 KiB and gains over the keyset only for projects with many deletes. It may come back for big projects.
    - **ETag / `If-None-Match`** exists on v2 single reads only, not on lists.
    - **A separate cheap probe** ("about 2 requests decide whether a delta is needed", the step 6 plan) is unnecessary: the first delta page is the probe.
- **Consequences:**
  - Web changes, deletions included, are on the phone after one `refresh()`: on start, on resume, every minute while the app is open, on pull-to-refresh and on "Sync now". Large accounts stop paying the full pull on every refresh.
  - Until the next full resync, the delta does not see pure position and bucket moves (not stored yet, [D30](#d30-kanban-board-reads-deferred-to-step-20)), a change the listener has not committed when the run passes (the next run's 120 s overlap catches that), and a task deleted right before its project was archived (the archived project is outside the count probe).
  - `SyncPhase` grows by `delta` and `reconcile`, with their labels in the ARB files; `SyncStatus` keeps its shape. A full resync no longer happens unnoticed: once a day a refresh takes as long as the step 6 refresh did.
  - A database written by step 6 has no watermark, so its first step 7 refresh is a full resync.
  - Step 16 runs the same `refresh()` in the background and moves the daily full resync and the session keep-alive there; step 17 uses the WebSocket as a trigger of `refresh()`, never as a source of truth.
  - The engine is contract-tested against the live 2.7.0 server on both API versions (`app/test/contract/incremental_sync_contract_test.dart`, tagged `contract`): seed, initial sync, then creates, edits, a done, deletes, a move, a new project, an archived project with an edited task, a deleted and a renamed label; one `refresh()` must mirror the server, and a second one with nothing changed must issue at most 4 requests.

## D34: Outbox: local-first writes, serial sender, coalescing, retry classes, sync interplay (pending fields win until sent, pending deletes hidden), v1 full-replace emulation

*Accepted 2026-10-10, step 11. Implements principle 3 of the [architecture](architecture.md#1-principles). Replaces the outbox part of [D31](#d31-one-drift-sqlite-file-per-account-shared-across-isolates-deleted-on-sign-out): the reserved `base_json`, `dirty_fields` and `sync_status` columns become `pending_changes` and `pending_delete`.*

- **Context:**
  - Since step 7 the database mirrors the server and stays current ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync)), but every screen is read-only. The most frequent actions of a daily driver are done, undo, favourite and delete, and they must work offline, because the lists do.
  - Verified server facts ([research/sync.md](research/sync.md) §4.4, §6 and §8, [research/api-v1.md](research/api-v1.md) §5.1 and §6, [research/api-v2.md](research/api-v2.md) §3.4): v2 `PATCH /tasks/{id}` with `Content-Type: application/merge-patch+json` merges the sent fields onto the server's current state, field by field, and answers with the full task; a patch that changes nothing answers 304 with an empty body; an unknown key is a 422. v1 `POST /tasks/{id}` is a full replace: an omitted field clears description, dates, priority, colour, percent done, repeat and favourite, omitted `assignees` and `reminders` delete them, `labels` in the body are ignored and so is `bucket_id`. A date is cleared with `0001-01-01T00:00:00Z` on both versions and `hex_color` travels without `#`. Marking a repeating task done makes the server reopen it with shifted dates (mode 0 by `repeat_after`, mode 1 by a month, mode 2 from now) and return that. `DELETE /tasks/{id}` answers 204 on v2 and 200 on v1; a 404 with code 4002 means the task is already gone. There are no idempotency keys and no preconditions: `If-Match` is ignored on writes, a conflicting edit never gets a 412, and concurrent writes are serialized by a row lock, so the last write wins. A 401 with code 11 is refreshed once and retried by the auth interceptor ([D26](#d26-refresh-concurrency-single-flight-re-read-and-adopt-write-ahead-epoch)); the transport retries GET and HEAD only.
  - Answers that will not change on a retry: 403 code 7003 (no access), 404 code 3001 (project gone), 412 code 3008 (project archived), 400 code 4001 (empty title), 422 (validation). Transient: network errors, 5xx and 429 with `Retry-After`.
  - The step 7 sync upserts every row the server returns by value and the reconcile purges rows the server does not list. Without a rule for unsent local edits a pull would overwrite a change still on its way, and a task deleted offline would come back.
  - The research design ([research/synthesis.md](research/synthesis.md) §2.7): one transaction per local write, coalescing, serial FIFO sending, backoff, a "Sync problems" list and an incremental pull after the drain.
- **Decision:**
  - **Local-first.** `TaskRepository.setDone`, `setFavorite` and `deleteTask` change the local row and queue the server call in one transaction and return when it has committed; they never throw for network reasons. The UI is optimistic: the row shows the change with the next stream event, offline too. Done shows an Undo snackbar for 3 s (persisting under a screen reader); undo is a second write, `undoDone(previous)`: `done: false` plus, for a repeating task, the dates the task had before, because the server may already have moved them on; the server does not shift an open task again, so the undo works whether the done is still queued, in flight or answered. A delete hides the row at once.
  - **Schema version 2** (migrated from 1; dump `drift_schemas/drift_schema_v2.json`, migration test with data): the table `outbox` (`id` uuid, an account-local `sequence` for FIFO, `kind` update or delete, `task_id`, `payload` as JSON of the `TaskChanges`, `created_at`, `attempts`, `next_attempt_at`, `last_attempt_at` (the "failed … ago" of a sync problem), `state` pending, sending or failed, `last_error` as JSON of the normalized failure: kind, code, message) with an index on `(state, sequence)`; `tasks` gains `pending_changes` (the coalesced `TaskChanges` the server has not accepted yet, nullable) and `pending_delete`. Not the `base_json`, `dirty_fields` and `sync_status` of D31: there is no 3-way merge, because the server offers no precondition that would detect a conflict and v2 merges per field on its own, so the dirty set is enough, and a delete is a flag.
  - **`TaskChanges`** (`vikunja_domain`): one nullable field per writable property (`title`, `description`, `done`, `isFavorite`, `priority`, `percentDone`, `hexColor`, `dueDate`, `startDate`, `endDate`); null means unchanged, a date is a `DateChange` (`set` or `clear`); `merge(later)` lets the later value win per field; `isEmpty`. It is the outbox payload and the argument of the write port. Step 11 sets `done` and `isFavorite` only; step 12 adds the remaining properties (`repeat_after`, `repeat_mode`, `project_id`, reminders, cover image).
  - **Write ports** (`vikunja_api`, `lib/src/write/`): `TasksWritePort.update(id, TaskChanges)` returns the task as the server stored it; `delete(id)` treats 404 code 4002 as success on both versions. `VikunjaWriteClient` from `createWriteClient(dio:, connection:)` picks v2 or v1 from the connection like the read client. The v2 adapter sends a merge-patch with only the set fields under their wire names (`due_date`, `is_favorite`, `percent_done`, …), `DateChange.clear` as the zero date, never a key the server does not know, and re-reads the task after a 304. The v1 adapter emulates the patch: `GET /tasks/{id}`, overlay the changes, `POST` the whole object back with `assignees` (`{id, username, name}`) and `reminders` exactly as read and never `labels`, so the full replace clears nothing. Both go through `normalizeError`; a cancelled request rethrows its `DioException`.
  - **Coalescing** in the write transaction: an update for a task whose update is still pending is merged into it (`TaskChanges.merge`; into the newest such op, so an older one left behind failed never takes an edit a newer op would revert) and into the row's `pending_changes`; an update followed by a delete becomes the delete; a delete is final. An op that fails for good while a newer op of the task is queued folds into that op (an update gives it the fields it does not set, a delete makes it moot), so a task never has two ops the sender could send in either order and a Retry can never overwrite a newer edit. Rows with `pending_delete` are left out of every DAO query; the counts the sync's probe compares ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync)) include them, because the server holds those tasks until the delete is sent.
  - **`OutboxSender`** (`core/outbox/`), one per account, headless (the write client, the database, a clock and the `SyncEngine` are injected, so steps 15 and 16 can run it without a widget tree): drains the queue oldest first, one op at a time, each claimed `sending` in a transaction that re-reads it (an edit merged in since the queue was read goes with it), never two sends at once per account. A drain starts when the sender is built (app start), after every local write, when the app comes back to the front, on "Send now" in the Account tab (which drops every backoff first), when a retry is due, when a paused sender resumes, and when a sync reaches the server while the oldest op waits out a network failure (the backoff is dropped: the network is back); nothing runs in the background yet (step 16). Only the request is guarded: once the server has stored the change, an error while applying the answer locally propagates and leaves the op `sending`, so nothing is re-sent on the spot; the next start resets and re-sends it. The oldest op blocks the queue while it waits for its backoff, so later ops never overtake it; a `failed` op does not block. On success the server's task replaces the row, every field except the ones a newer op of the same task still holds pending; those fields leave `pending_changes`; the op is deleted. A repeating task therefore comes back open with its shifted dates. After a drain that sent at least one op the sender calls `SyncEngine.refresh()`, so server-computed fields arrive.
  - **Retry classes:**

    | Answer | Op | Sender |
    |---|---|---|
    | success, 304, or 404 code 4002 on a delete | the response is applied (a delete removes the row), the op is removed | next op |
    | `NetworkFailure`, `ServerFailure`, `RateLimited`, `TokenRejected` after the interceptor's own refresh and retry (the session was replaced by a new sign-in, or the server will take the next token; a session that ended for good arrives as `SessionEnded`), and an answer that is not Vikunja's: `UnexpectedResponse` with no status or one below 400 (a captive portal's page, a proxy's redirect, an empty body) and `NotFound` without a Vikunja code (a web server's 404 during a deploy) | back to `pending`; `attempts + 1`; `next_attempt_at` = now + 2 s · 2ⁿ, shortened by up to half at random, at most 15 min; a `Retry-After` above zero wins when the server sends one, capped the same way | waits for it; later ops wait behind it |
    | `SessionEnded` | stays `pending`, untouched | `paused` until the account is signed in again ([D22](#d22-session-keep-alive-through-background-sync)); nothing is ever dropped |
    | `NotFound` with a Vikunja code (3001; on an update also 4002, the task itself gone), `Forbidden`, `DomainError` code 3008, `ValidationFailed`, `UnexpectedResponse` 4xx or 5xx | `failed`, the failure as `last_error`: a `SyncProblem`, or folded into a newer queued op of the task | goes on with the next pending op |

    The spec's table had `TokenRejected` pause the sender and every `UnexpectedResponse` and `NotFound` fail for good; the review of step 11 moved them: a `TokenRejected` pause had no resume trigger (the session manager sets `needsReauth` only for `SessionEnded`), and the read side already treats a portal's or proxy's answer as a failed run to retry, so the two halves of the app now agree on what is transient.

  - **Sync problems:** `watchSyncProblems` streams the failed ops joined with the task title; the Account tab lists them with what failed and when, Retry (the op goes back to `pending`) and Discard (the task is read from the server first, `GET /tasks/{id}` through the read client, then the op is deleted and the row replaced, or removed on a 404 or a 403, which means the task left the user's projects and its row would otherwise stay purge-protected forever; a read that fails for another reason throws and changes nothing, so the local edit is never lost offline; the op is checked again inside the transaction, so a retry or delete that got through meanwhile is not undone). "Send now" says in a snackbar what still blocks the queue afterwards and is not offered while every queued change is a sync problem. `watchPendingChanges` counts every queued op, `sending` included; the Account tab shows "Pending changes: N" with "Send now" while N > 0, and a row whose task has unsent changes shows a cloud-off icon.
  - **Sync interplay:** the sync engine's upserts (initial, full, incremental, reconcile) overlay the row's `pending_changes` on the incoming task, so the incoming values win for every other field and the unsent fields keep the local value; a `pending_delete` row is written but stays hidden; every purge (the full pull's, the reconcile's, a removed project's) skips rows with a pending op; no run touches the outbox. Once the op is sent, the drain's refresh sorts the row out.
  - **UI:** the circle of a task row and the done control of the sheet call `setDone` (haptic, strikethrough at once, "Marked done · Undo" in the lists, where a done row stays in place until its own 3 s are up and its snackbar has gone, so a second tap never pulls the earlier row away under the finger; the sheet's checkbox is its own undo); the star toggles the favourite in the row and the sheet; Delete sits in the sheet's overflow menu behind an adaptive confirmation, after which the sheet closes and a snackbar confirms. The screens see the repository interface plus `SyncProblem`, `OutboxOperationKind` and `PendingTaskIdsSource` from `core/outbox/`, nothing of the DAO or the sender. The sign-out dialog says how many queued changes the wipe would lose and points to Send now. Semantics on every new control, en and de, dark mode and 200 % text scale as in every step.
  - **Rejected alternatives:**
    - **Sending each write straight to the server, without a queue.** Offline, a write would fail or be lost, and two quick taps could overtake each other. The transport retries GET and HEAD only, for good reason, so every write path would need retries of its own, and the notification actions (step 15) and the widgets (steps 18–19) need the same queue anyway (principle 3).
    - **Blocking the UI until the server answers.** A spinner on every tick, no editing offline, and a repeating task would still need the response applied afterwards. The optimistic row costs one stream event, and the Undo snackbar covers the mistaken tap.
    - **CalDAV** (Vikunja 2.4.0) as the write channel: it needs a CalDAV token created in the web app, which browser sign-in does not give the app ([D14](#d14-browser-sign-in-only)), it is a second protocol (XML, iCalendar) next to the JSON API, a VTODO has no favourite flag, and the result would have to be pulled back through the API anyway.
    - **`If-Match` preconditions and a 3-way merge over `base_json`** (the D31 reservation; [research/sync.md](research/sync.md) §6): the server ignores `If-Match` on writes and never answers 412 for a conflict, and v2's merge-patch already merges per field on the server. A field changed on the web while the same field waited in the outbox is overwritten by the phone's value; the description editor of step 25 revisits that for the one field where it hurts.
    - **Idempotency keys:** the server has none. An uncertain create needs the lookup of [research/sync.md](research/sync.md) §9.4, which arrives with creates in step 12.
- **Consequences:**
  - Done, undo, favourite and delete work offline and show at once; what is queued is visible in the Account tab and on the rows. Nothing is dropped silently: a permanent rejection keeps the local edit visible until the user retries or discards it, and a sign-out with queued changes says so in its dialog before the wipe (the only way an edit is lost, and only on the user's word).
  - Writes are at least once: an op whose answer could not be applied locally (the database closing, a full disk), or a kill between the server's apply and the local one, is re-sent at the next start. For a repeating task a re-sent `done: true` shifts the dates a second time; the GET-before-resend that would avoid it is left for a later step.
  - Undo of a repeating task restores the dates the task had; `done_at` stays stamped on the server, absolute reminders stay shifted (`TaskChanges` has no reminders field until step 12; relative ones follow the restored date) and the server's checklist reset in the description is not reverted.
  - Last write wins per field: a field the web changed while the phone's queued value for the same field waited loses to the phone; every other field survives (v2 by the server's merge, v1 by the overlay on a fresh read). Until step 12 only `done` and `is_favorite` can collide.
  - A repeating task shows done until the server answers, then reopens with the shifted dates. Marked done offline, a mode 2 task computes "from now" at send time, not at tap time.
  - The probe's local counts include the rows queued for deletion, because the server holds them until the delete is sent; a pending or failed delete therefore costs no extra requests on every refresh. A task deleted on the web while its local delete is queued is a mismatch until that delete is sent, which the 404 code 4002 answers as success.
  - The transport keeps retrying GET and HEAD only; writes are retried by the sender with its backoff, and a paused sender resumes with the next sign-in, so the 72 h session end ([D22](#d22-session-keep-alive-through-background-sync)) never loses an edit.
  - `TaskRepository` gains the write methods; the step 5 widget tests keep running against the fake repository. The migration to schema version 2 runs on the first open after the update.
  - Step 12 extends `TaskChanges` and adds creates (a local id until the server answers, the id mapping and the uncertain-create lookup); steps 15 and 18–19 send their "Mark done" through the same outbox; step 16 drains it in the background.
  - The write ports are contract-tested against the live 2.7.0 server on both API versions (`packages/vikunja_api/test/contract/write_contract_test.dart`: a task seeded with an assignee, two reminders and a label keeps all three through a done toggle, the v1 full-replace regression; undo, favourite, title, a repeating task reopened a day later, a delete twice), and so is the whole pipeline (`app/test/contract/outbox_contract_test.dart`: seed, initial sync, `setDone`, `setFavorite` and `deleteTask` drained and checked on the server and in the row, a write whose first attempt fails with a `NetworkFailure` and is retried, a repeating task reopened with the server's date).

## D35: Creates through the outbox: temporary negative ids with remap, create/update/delete coalescing, lost-response recovery by title within a 1 h window

*Accepted 2026-10-11, step 12a. Extends [D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation) by the create path it left for step 12 and by the remaining core properties of `TaskChanges`; the outbox, the sender and the retry classes of D34 are unchanged.*

- **Context:**
  - Since step 11 done, undo, favourite and delete go through the outbox ([D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation)), but a task can neither be created nor edited on the phone. Step 12 is split: 12a is the daily-driver half, creating a task and editing its core properties (title, project, dates, priority, percent done, colour, repeat); labels, assignees and reminders are 12b ([roadmap](roadmap.md#steps)).
  - Verified server facts ([research/client-logic.md](research/client-logic.md) §2.3–§2.5, §3 and §6, [research/api-v1.md](research/api-v1.md) §5.1, [research/sync.md](research/sync.md) §8, [research/synthesis.md](research/synthesis.md) §2.7): a create is v2 `POST /projects/{id}/tasks` and v1 `PUT /projects/{id}/tasks`, 201 with the task as the body. Writable on create: `title` (required; empty is 400 code 4001), `description`, `done`, `due_date`, `start_date`, `end_date`, `priority`, `hex_color` (no `#`), `percent_done` (0..1), `repeat_after` (seconds, 0..315360000, else 4029), `repeat_mode` (0, 1, 2), `is_favorite`, `reminders`, `assignees` and `bucket_id`; `labels` are ignored on create. The server assigns `id`, `index`, `identifier`, `created`, `updated` and `created_by`. The client cannot choose an id and there is no idempotency key, so a create whose answer was lost leaves a task on the server that a blind resend would duplicate. `project_id` in an update moves the task, and the server reassigns `index` and `identifier`; a move into an archived project fails with 412 code 3008. "Remove repeat" is `repeat_after 0, repeat_mode 0`.
  - The web's editing rules the app ports: the date shortcuts of `buildDateShortcuts(now)` with the day-interval table (two shortcuts on the same day keep the first, `today` is hidden from 21:00 while another shortcut landing on today still shows, `thisWeekend` on Sunday, `inAMonth` is clamped to the month's last day; test vectors for Fri 2026-09-11, Mon 2026-09-14, Tue 2026-09-15, 2026-09-30 and Fri 2026-09-11 21:30); the default time of a date-only pick (`frontend_settings.default_due_time` when valid, which arrives with the user settings of step 30, otherwise the next breakpoint among 9, 12, 15, 18 and 21, where "at HH:00 exactly" counts as that breakpoint and after 21:00 it is 9 the same day; a date change keeps a time already set); the repeat editor with the presets every day, every week and every 30 days, the modes default, monthly and from completion date, the units hours, days and weeks, an amount of 0 ignored and a negative one refused; the six colour picker defaults `#1973ff #7F23FF #ff4136 #ff851b #ffeb10 #00db60` plus "no colour"; priority 0..5; percent done in 10 % steps.
  - The sync of step 7 upserts by value and purges what the server does not list ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync)); a row the server does not know yet must survive both, and its count must not make the probe reconcile on every refresh.
- **Decision:**
  - **Temporary ids.** `TaskRepository.createTask(NewTask)` inserts the task row under a negative id, the next value of a counter in `sync_state` (`local_task_ids`) negated, never reused and never colliding with a server id (those are positive), without an `updated` (a server time, which the watermark must not take from the device clock) and with `pending_changes` null, and queues a `createTask` op whose payload is the `NewTask` as JSON, in one transaction; it returns the local id. The row is an ordinary task for every DAO query and every screen, sorted before every server task in the lists; the detail sheet shows no identifier for it. The sync never overwrites or purges it, because it has a queued op, and the local count the probe compares ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync)) leaves it out, because the server does not hold it yet.
  - **Coalescing on a temporary id.** While the create has not left the device (pending and never sent, or rejected by the server), an edit folds into it (the `TaskChanges` applied onto the stored `NewTask`), favourite included, so the create carries the edits and a rejected create is re-queued with them; `done`, which a create cannot carry (a new task is open), becomes an update queued behind it; a delete cancels the create with the row, and nothing is sent. Once the create may be on the server (in flight, or sent without an answer), later edits and a delete queue behind it as ordinary ops under the temporary id: the sender takes no op under a temporary id until its create is through, and the remap rewrites them to the server id. When the server rejects a create with such an edit behind it, the edit folds into the rejected create too (only a `done` stays queued), so that a later edit folded into the create is never reverted by the older one on Retry. An edit or delete addressed to a temporary id whose create was answered meanwhile is followed through `task_id_remaps` to the server row. Every other coalescing rule of D34 is unchanged.
  - **Sending a create and the remap.** The sender claims the op and calls `TasksWritePort.create(NewTask)`: v2 `POST`, v1 `PUT` on `/projects/{id}/tasks`; the body carries title, description, priority, percent done, colour, repeat and favourite under the wire names of an update, a date only when set, because the server stores the zero date for an omitted one, and the project in the path only, because a `project_id` in a v1 body would override the path; never `done`, reminders, assignees, `bucket_id` or `labels`; the answer is parsed with the shared codec. On success, in one transaction: the create op goes, the ops queued behind it move to the server id, the temporary row is deleted and the server's task is upserted under its id (a row the sync pulled meanwhile under that id is replaced), the fields those ops still hold are re-applied on top, and `(local_id, server_id, at)` is recorded in the new table `task_id_remaps` (schema version 3, migrated from 2 with a dump and a migration test). `watchTask(id)` is one stream over the task tables and the remap table that resolves `id` through the remap on every emission, so a sheet or page open on the new task follows it; it emits null once the row is gone.
  - **Lost response.** A `NetworkFailure` or a `ServerFailure` on a create (the connection broke or timed out, or a proxy answered for an upstream still at work: the request may have been processed without this device seeing the answer) records `sent_at` on the op, the time of the first such attempt, so that the window covers every attempt, next to the D34 backoff. A create the app was killed over while it was `sending` is treated the same at the next start: the reset marks it uncertain as of its attempt time (an earlier `sent_at` stays) instead of resending it blindly as D34 does for an update. The next attempt first asks `listInProject(projectId, TaskQuery(filter: "created >= '<sent_at − 1 h>'", sorted by created descending))` and adopts the newest task of the project with the sent title that no other create of this device has adopted yet (of two in the same second, whose order the server leaves undefined, the one with the higher id), completing the create as if the answer had arrived; only when none is found is the create sent again. The window is an hour, the skew between the device clock and the server's `created` that the sync engine tolerates too ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync)); the exact title and project keep the match narrow.
  - **A rejected create** (a `DomainError` such as 4001, an empty title on v1, or 4029, a repeat beyond ten years; a `ValidationFailed` such as the 422 of an empty title on v2; no access, project gone or archived) is a sync problem that names the title. The ops queued behind it wait; a delete among them cancels the create and the row, because the server never had the task; an edit folds into the failed create and re-queues it, as does Retry in the Account tab; Discard cancels the create with the row, without the server read an update's discard makes.
  - **Edits.** `TaskChanges` gains `repeatAfter` (a `Duration`, sent as seconds), `repeatMode` and `projectId`; `updateTask(id, changes)` on a positive id is the `queueUpdate` path of D34 with these fields, and the server's answer is applied as before. After a move both adapters read the task back, because the server's answer still carries the old project's identifier (verified on 2.7.0: it builds the identifier before moving), so the applied task has the new `identifier` and `index`; the v1 adapter overlays `project_id` into the full `POST` like any other field. On a server with only `/api/v1` nothing changes for the create: `PUT` takes the same body.
  - **UI.** A full-screen edit page (`/home/tasks/:id/edit`, from the detail sheet's Edit action and from tapping its title) edits title, project (the tree without archived projects), due, start and end date with time (adaptive date and time pickers, Clear, the ported shortcut chips, the breakpoint default time), priority, percent done in 10 % steps, colour (the six defaults, no colour, and the current custom colour if any) and repeat (never; every amount of hours, days or weeks with the three presets; monthly; from completion). Save is disabled while nothing changed or the title is empty, sends the diff only and pops with a "Saved" snackbar; back with unsaved changes asks first. A FAB on the Overview and on a project's task list opens the new-task sheet: a title field, a project chip (the current project, else the project titled Inbox, because the server's `default_project_id` is not synced before step 30, else the first project of the tree), due shortcut chips, Add, and "More options", which creates the task and opens the edit page on it.
  - **Rejected alternatives:**
    - **Client-chosen ids.** The server assigns `id` and `index` and the client cannot set a `UID` ([research/sync.md](research/sync.md) §8), so no id is known until the server answers and a create cannot be made idempotent from the client's side.
    - **Blocking creates until the server answers.** Offline capture is the point of principle 3 and of lists that work offline; a spinner on every Add and no "More options" without the network would put the most frequent capture behind the server, and the sync would still have to take the server's answer in. The one price of the local id, the remap, is paid once per create.
    - **A separate drafts table for unsent creates.** Every list query, the detail sheet and the edit page would need a union of two tables; a negative id in `tasks` makes a new task an ordinary row that every existing query, stream and screen handles unchanged.
    - **The remap as `sync_state` entries** instead of a table: `watchTask` needs to follow one local id, the guard needs to look a local id up, and 12b's label and assignee ops will resolve a temporary task id at send time; a keyed table serves all three without parsing a map on every read.
    - **Resending a lost create blindly**, at least once as D34 does for updates: a repeated update is harmless, a repeated create is a duplicate the user has to find and delete. Never resending would lose the task whenever the request did not arrive. The lookup pays one read for the rare case.
    - **Matching by `created_by` and description as well**, as the research proposed ([research/sync.md](research/sync.md) §9.4, [research/synthesis.md](research/synthesis.md) §2.7): the description is not editable in 12a, and the title within a one-minute window on one project identifies the app's own create well enough; the match can grow when step 25 makes descriptions editable.
- **Consequences:**
  - A task created offline is on screen at once under its temporary id and keeps every edit made before the send; the create goes out as one request with those edits (a done, or an edit made while the create is in flight, is a second request after it), a delete before the send costs no request, and the identifier appears once the create was sent and the drain's refresh ran.
  - Negative ids never reach the server: a create op is sent through `create()`, never through `/tasks/{id}`. After the remap the next delta sees the server task under the same id and upserts it normally. Rows with negative ids stay out of the probe's local count, so an unsent create costs no reconcile on every refresh.
  - The migration to schema version 3 runs on the first open after the update. `task_id_remaps` keeps one row per create and is never pruned: a screen may still hold the old id, and temporary ids are never reused.
  - Lost-response recovery makes creates effectively once: the duplicate of a blind resend is replaced by one extra read. Its blind spot is accepted: a task another member created in the same project with the same title within that hour would be adopted and the phone's own never sent. The adopt branch is contract-tested on both API versions (a task created on the server, the same create queued and marked uncertain, drained without a second request).
  - Last write wins per field, as in D34, now for every core property: a field the web changed while the phone's queued value for the same field waited loses to the phone. The description is still read-only (step 25).
  - `default_due_time` set on the web is not honoured until step 30 brings the user settings; until then the breakpoint rule applies.
  - Step 12b adds labels, assignees and reminders: label and assignee changes need op kinds of their own on the label and assignee endpoints and, on a temporary id, wait for the create's remap, which `task_id_remaps` serves; reminders go into `TaskChanges`, which also completes step 11's undo on a repeating task. Step 13's quick add and step 15's notification actions create and edit through the same `createTask` and `updateTask`. Kanban buckets on create, attachments and the description editor are later steps.
  - Contract-tested against the live 2.7.0 server on both API versions: the write client (a create with every core field echoed back and an identifier `<PREFIX>-n`, a move to another project with the new identifier, repeat changed, switched to monthly and removed, an empty title rejected as a 422 `ValidationFailed` on v2 and a 400 `DomainError` 4001 on v1, a repeat beyond ten years refused with 4029) and the whole pipeline (a task created offline, drained, is on the server with its fields and the local row carries the server id; create + edit before the send is one request; create + delete is none; a move between projects; repeat removal).

## D36: Labels and assignees as id-set deltas in the task update, sent through their endpoints after a read-before-write diff; reminders as the whole list; label creation online-only

*Accepted 2026-10-11, step 12b. Extends [D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation) and [D35](#d35-creates-through-the-outbox-temporary-negative-ids-with-remap-createupdatedelete-coalescing-lost-response-recovery-by-title-within-a-1-h-window) by the last task properties of step 12. Replaces the plan in D35's consequences that label and assignee changes need op kinds of their own; the op kinds, the sender and the retry classes of D34 and D35 are unchanged, and the remap of D35 now restores the task's child rows too.*

- **Context:**
  - Since step 12a the edit page changes every core property and creates go through the outbox ([D35](#d35-creates-through-the-outbox-temporary-negative-ids-with-remap-createupdatedelete-coalescing-lost-response-recovery-by-title-within-a-1-h-window)); labels, assignees and reminders are still read-only, and step 11's undo on a repeating task leaves absolute reminders shifted because `TaskChanges` has no reminders field ([D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation)).
  - Verified server facts (Vikunja 2.7.0, probed live on both API versions on 2026-10-11; [research/client-logic.md](research/client-logic.md) §4 for the web's reminder editor):
    - **Labels on a task:** an add is v2 `POST`, v1 `PUT /tasks/{id}/labels` with `{"label_id": N}`, 201. A label that is already attached answers 400 code 8001, a label that does not exist 404 code 8002, a label the user cannot see (another user's label on no task the user can read) 403 without a code, a missing task 404 code 4002. A remove is `DELETE /tasks/{id}/labels/{labelId}`, 204 on v2 and 200 on v1; a label that is not attached answers 403, not 404, and so does a label id that does not exist. `labels` in a create body are ignored on both versions: the response echoes them, but nothing is stored. On the SQLite test server a label add can answer a transient 500 when it races the server's own asynchronous `updated` write after an assignee change; a retry succeeds.
    - **Assignees:** an add is v2 `POST`, v1 `PUT /tasks/{id}/assignees` with `{"user_id": N}`, 201. A user who is already assigned answers 400 code 4021, a user without access to the project 403 code 7003, a user who does not exist 404 code 1005. A remove, `DELETE /tasks/{id}/assignees/{userId}` (204 on v2, 200 on v1), succeeds also when the user is not assigned or does not exist: it is idempotent. `assignees: [{id}]` in a create body is applied on both versions.
    - **User search:** v2 `GET /projects/{id}/users/search?q=` answers an envelope with all results in one page; v1 `GET /projects/{id}/projectusers?s=` a bare array. The parameter may be omitted, which lists everyone with access to the project (owner, shares, teams). The user JSON carries `id`, `name`, `username`, `created` and `updated`, no email.
    - **Reminders:** `reminders` is a full replacement, in a v2 merge-patch (`[]` and `null` both clear) and in the v1 full `POST` (an omitted list clears them, which the D34 overlay already guards against). Create bodies accept them on both versions. An absolute reminder is `{"reminder": "<RFC 3339>", "relative_period": 0, "relative_to": ""}`, a relative one `{"relative_period": <signed seconds>, "relative_to": "due_date" | "start_date" | "end_date"}`, whose instant the server computes; a period without `relative_to` is 400 code 4022, and a reminder relative to an unset date is stored with the zero date as its instant. The server stores one reminder per computed instant: reminders that land on the same instant (two absolute ones, an absolute and a relative one, or every relative one of an unset date) are stored once, while the update's answer still echoes the list as sent; clearing or moving a date can therefore drop a reminder the client never touched (verified on both versions). The server returns the list sorted by instant, and it shifts the reminders of a repeating task marked done (absolute ones by the interval, relative ones from the new dates).
    - **Label create:** v2 `POST`, v1 `PUT /labels` with `{title, hex_color, description}` (title 1 to 250 characters), 201 with the label. The web picks a random colour from `ffbe0b fd8a09 fb5607 ff006e efbdeb 8338ec 5f5ff6 3a86ff 4c91ff 0ead69 25be8b 073b4c 373f47`.
  - The outbox rules that must keep holding: one op per task in FIFO order, an update merged field by field into the queued one, a failed op folded into a newer one ([D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation)), and the update queued behind an unsent create that the remap rewrites to the server id ([D35](#d35-creates-through-the-outbox-temporary-negative-ids-with-remap-createupdatedelete-coalescing-lost-response-recovery-by-title-within-a-1-h-window)). Writes are at least once, so a resent label or assignee request must not fail on its own earlier success.
- **Decision:**
  - **Id-set deltas in `TaskChanges`.** `TaskChanges` gains `labels` and `assignees`, each an `IdSetChange` (`vikunja_domain`: the ids `added` and `removed`; `merge(later)` lets the later change win for an id both touch, so add then remove is a remove and remove then add an add; `applyTo(current)`; `isEmpty`), and `reminders`. No new op kind: a label or assignee change is a field of the ordinary update op, so it is queued, merged, ordered and folded by the D34 rules, and on a task whose create is still queued it is part of the update that waits behind the create (as a `done` does, D35) and is rewritten to the server id by the remap, so it is sent after it. `TaskDraft.diff` on the edit page emits the deltas by id (added = draft minus original, removed = original minus draft).
  - **Sending through the endpoints with a read-before-write diff.** `TasksWritePort.update(id, changes)` first sends the body fields as before (reminders included; v2 merge-patch, v1 `GET` → overlay → `POST`). When `labels` or `assignees` carry a change, it takes the task as the server has it (the answer of that request, or `GET /tasks/{id}` when there were no body fields) and sends only what differs: label removes for ids attached now, label adds for ids not attached, assignee removes for ids assigned now, assignee adds for ids not assigned, in this order, then reads the task back once, which is the result. The races a retry or a concurrent web edit can meet are tolerated: a label add answered 400 code 8001 and an assignee add answered 400 code 4021 count as done; a label remove answered 403 is checked with one `GET /tasks/{id}` and counts as done when the label is no longer attached, otherwise the `Forbidden` propagates. Every other failure fails the op as a whole; a retry reads again and sends only what is still missing. The whole update is therefore idempotent, and D34's at-least-once resend is harmless for these fields.
  - **Failures.** `NotFound` 8002 (label gone) and 1005 (user gone) and `Forbidden` 7003 (user without access to the project) or without a code (a label the user cannot see) are permanent failures of D34's table: a sync problem that names the task, with Retry and Discard; a `NotFound` with a code other than 4002 never removes the task. The transient 500 is a `ServerFailure` and retried. Discard reads the task from the server, which restores its labels, assignees and reminders as well.
  - **Reminders as the whole list.** `TaskChanges.reminders` is the task's complete reminder list (empty removes every reminder; the later list wins on merge), sent as `reminders` in the patch and overlaid in the v1 `POST`. `NewTask.reminders` carries them on a create; an edit before the create was sent folds them into the `NewTask`, so they travel with the create. A relative reminder's instant is computed locally from the date it refers to (null while that date is unset), when the reminders are set and when that date changes; the server's value replaces it with the next answer or pull. The editor does not add a reminder equal to one already listed, because the server would keep both.
  - **Local apply and sync.** The task's child rows change in the transaction that queues the op: `task_labels` and `task_assignees` by `IdSetChange.applyTo`, `task_reminders` replaced. An id without a local label or user row is queued but skipped for the child rows, because of their foreign keys. `completeCreate` applies the pending changes of the ops behind the create to the child rows too, so labels and assignees chosen before the remap stay visible. The sync's upserts keep a row's pending labels and assignees (applied as a delta to the incoming sets) and its pending reminders (replacing the incoming list, relative instants recomputed), as D34 does for the scalar fields.
  - **Read-back after reminder and date changes.** Because the update's answer echoes reminders the server merged, `update` reads the task back after a reminder change and after any change of the due, start or end date, as it does after a move and after label or assignee requests (one final read for all of them). The incremental sync also rewrites a task whose reminders differ from the local ones (an order-insensitive comparison, `sameReminders` in `vikunja_domain`), although `Task ==` ignores them, so a local list that drifted heals on the next pull. The edit page warns before saving when two reminders would share an instant, counting every relative reminder of an unset date as one.
  - **A label deleted on the server leaves the queue.** When the label sync removes labels, `OutboxDao.forgetLabels` takes their ids out of every unsent update in the same transaction: an update left empty is deleted (and its sync problem with it), a failed one that changed is queued again with a clean slate, one in flight is left alone. Otherwise a label add failing for good with 8002 would hold every later label and assignee edit of the task, which fold into it, until a Discard.
  - **Undo on a repeating task** sends `reminders: previous.reminders` with the restored dates when the task had reminders, so the server's shift of the absolute ones is taken back; nothing changes for a task without reminders.
  - **Label creation online-only.** The label picker offers "Create label "X"" when no label has the typed title (case-insensitive); `LabelRepository.create(NewLabel)` goes straight to `LabelsWritePort.create` with a random colour of the web's palette and stores the answer locally, and attaching the new label then goes through the outbox like any other. Offline the picker says that creating a label needs a connection; titles over 250 characters are refused before a request. A create whose answer was lost (timeout, broken connection, server error) is not repeated blindly, because the server stores two labels with the same title: the repository looks for a label with exactly that title created within the last hour (the clock tolerance of D35) that the device does not know yet and adopts the newest; it remembers titles whose create went unanswered and looks again before the next create of that title, and when that lookup fails too, the create stops with the error. The picker then says that it could not confirm the label was created.
  - **People search online, known users offline.** `UserRepository.searchAssignees(projectId, query)` calls `UsersPort.searchProjectUsers` on the two endpoints above and stores the users it returns; the people picker searches on open and 300 ms after the last keystroke, and only the latest query's answer counts. When the search fails, the picker shows `knownUsers()` (the people of the synced tasks and of earlier searches) filtered locally, with a notice. Moving the task to another project after picking keeps the assignees; a user without access there fails with 7003 as a sync problem.
  - **UI.** The edit page gets the sections Labels and Assignees after Project and Reminders after the dates: label chips in the label's colour and assignee chips with initials and the display name, each with a remove button; the label picker and the people picker as adaptive sheets with multi-select; reminder rows in the existing wording (a relative one with the instant computed from the draft's dates, or a warning that its date is not set) with edit and remove, and a reminder sheet with the web's presets relative to the due date (else the start, else the end date), a custom relative form (amount, minutes to weeks, before or after, due, start or end date) and an absolute date and time. Editing a relative reminder keeps its sign: the web always shows "before" ([research/client-logic.md](research/client-logic.md) §20), which the app does not copy.
  - **Rejected alternatives:**
    - **Separate op kinds for label and assignee changes**, as D35 anticipated. A second kind of op per task would need its own ordering against the task's update and create, its own coalescing (add then remove), its own fold into a failed op and its own rewrite at the remap; inside `TaskChanges` the delta merges field-wise like every other field, one op per task keeps D34's ordering, coalescing and folding rules and D35's remap handling as they are, and the read-before-write diff makes the whole op idempotent.
    - **The bulk endpoints that set a task's whole label or assignee list.** Last write wins on the whole set: a label someone added on the web while the phone's change waited would be dropped. The delta touches only the ids the user changed.
    - **Assignees in the v1 full `POST` body** that the adapter sends anyway (and in the create body, where the server applies them). One code path for both versions, and a failure that names the request it belongs to (a 7003 for one user), are worth the extra requests; a whole list in the body would also be last write wins on the whole set, like the bulk endpoints.
    - **Offline label creation with temporary label ids.** It would need a second remap, of label ids in `task_labels` and in the queued deltas, for a rare action. Deferred to the label management of step 28, or to quick add in step 13 if that needs it.
    - **Label and assignee requests without the read.** 8001 and 4021 could be tolerated blindly, but removing a label that is not attached answers 403, which looks like a permission failure and would need the read anyway; the read also keeps the requests to the ids that differ.
- **Consequences:**
  - Labels, assignees and reminders are editable offline and on a task whose create is still queued; the reminders go out with the create in one request, the labels and assignees as the update right after the remap.
  - An update with label or assignee changes costs a read when it has no body fields, one request per id that differs and a final read (on v1 plus the overlay's read); an edit of the scalar fields alone costs what it did.
  - The requests of one update are not atomic on the server: when one fails for good (a 7003 for the second of two people), the earlier ones stay applied, the op becomes a sync problem, Retry sends only what is still missing, and Discard restores the server's state locally.
  - Per id the last write wins: a label the web removed while the phone's add waited is attached again, but a label the web added meanwhile stays, which the bulk endpoints would have lost.
  - A label or person not known locally yet is sent but not shown on the task until the next sync brings its row. A relative reminder's instant is the device's computation until the server answers.
  - Reminders that would share an instant are merged by the server; the edit page warns before such a save, and the read-back plus the sync's reminder comparison keep the local list equal to the stored one.
  - Undo of a repeating task restores dates and reminders; `done_at` stays stamped and the checklist reset in the description is not reverted ([D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation)).
  - Creating a label needs a connection until offline creation comes with the label management of step 28 (or with quick add in step 13, if that needs it); label editing and deletion are step 28. Quick add attaches labels and assignees through the same deltas.
  - Contract-tested against the live 2.7.0 server on both API versions: the write client (label create; labels added and removed, each twice without a failure; the user and a second user shared into the project assigned and unassigned, repeated calls idempotent; a user without access refused with 7003, a missing label with 8002, another user's label with a `Forbidden`; absolute and relative reminders set, the relative instant computed by the server, cleared with `[]`; a create with reminders; on v1 a label or reminder change keeps the assignees; the user search returning owner and shared user, filtered by the query) and the whole pipeline (a task created offline with a reminder, then a label and the user as assignee before the send, is on the server with all three and the local row carries the server id; a label removed and added again; a repeating task with an absolute reminder marked done, then undone, has its reminder back at the original instant).

## D37: Account switcher: a sheet from an avatar button and an Accounts section, a switch resets the navigation, the most recently active account follows a removal, inactive outboxes drain in the foreground

*Accepted 2026-10-11, step 4. Fulfils the switcher of [D16](#d16-multi-account-in-the-first-release) on the registry of [D25](#d25-account-registry-in-sharedpreferences-without-secrets), which gains an additive recency field; the browser sign-in of [D23](#d23-browser-sign-in-through-flutter_web_auth_2-client-id-and-redirect-uri), the sign-out of step 2+3 (now offered for any account), the database per account of [D31](#d31-one-drift-sqlite-file-per-account-shared-across-isolates-deleted-on-sign-out) and the outbox of [D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation) are unchanged.*

- **Context:**
  - D16 promises adding, switching and removing accounts in the first release. Until now the app can hold several accounts but offers no way to a second one: onboarding is reachable only without an active account, and the UI signs out only the active one.
  - The plumbing exists: the registry holds several accounts and the active id ([D25](#d25-account-registry-in-sharedpreferences-without-secrets)); every per-account object is keyed by the account id (the session manager, the authenticated `Dio`, the database, the sync engine, the outbox sender); the active-account providers (`activeAccountIdProvider`, `taskRepositoryProvider`, `syncStatusProvider`, `foregroundSyncSchedulerProvider`, …) follow the registry; the shell re-runs the session check and a quiet sync when the active id changes; `SignOut` works for any account id.
  - What a second account exposes:
    - A screen opened for account A holds ids of A's database: the edit page and the detail sheet a task id, a project screen a project id, a picker the task's project. After a switch the repositories follow B, so the same id would be read from B's database: another task, or none.
    - The tab stacks of the shell (`StatefulShellRoute.indexedStack`) keep their pushed routes across a switch.
    - The router treats a sync status that has not been reported yet like "needs the first sync" ([architecture](architecture.md) §7.4), so a switch to an account whose engine is not built yet would pass through the first-sync screen although the account has synced before.
    - `remove` activates the first remaining account in stored order: after cancelling the first sync of an account just added, the user could land in a third account instead of the one they came from.
    - The outbox sender of an account is built only when something reads it, which in the UI is the active account's repository. Changes queued in an account the user switched away from wait until it is active again, or until the background sync of step 16.
  - The browser session is ephemeral ([D23](#d23-browser-sign-in-through-flutter_web_auth_2-client-id-and-redirect-uri)): the server's login page always asks for credentials, so a second user on the same server can be added without signing out on the web first. Signing in to an account that is already on the device gives the same account id and replaces its session ([D25](#d25-account-registry-in-sharedpreferences-without-secrets)); it never adds a duplicate.
- **Decision:**
  - **Entry points.** An avatar button with the active account's initials (semantics "Accounts, signed in as *name* on *host*") at the trailing end of the Overview and Projects app bars opens the **account switcher sheet**, an adaptive modal sheet: the accounts in recency order, the active one first and marked, each with initials, display name (else username) and `@username · <host>` (the port only when it is not the default), a "Sign in again" badge for `needsReauth` and an "N unsent" badge while its outbox holds ops; a tap on another account switches, closes the sheet and confirms with a snackbar; "Add account"; "Manage accounts" opens the Account tab. The Account tab gets an **Accounts** section under its header: the other accounts (a tap switches; a menu with "Remove…") and "Add account". The banner, the sync status, the pending changes and the sync problems on the Account tab stay about the active account.
  - **The switch.** `AccountSwitcher.switchTo(id)` only sets the active id in the registry (a no-op for the active and for an unknown id); every provider keyed by the active account follows. When the active id changes, the shell closes every route above it on the root navigator (edit page, sheets, dialogs, pickers), resets every tab to its root and shows the Overview, so no screen of the previous account reads the new account's database. A switch to an account that has synced before never passes through the first-sync screen, also while its engine has not reported yet; an account whose first sync has not completed goes to `/sync`.
  - **Recency in the registry.** The registry stores the activation order, most recent first, as an additional JSON field next to the accounts and the active id. `setActive` and `upsert(activate: true)` move the id to the front, `remove` drops it. A registry without the field (written before step 4, or by an older build) reads as the stored account order with the active account first; an entry this version cannot read keeps its place untouched ([D25](#d25-account-registry-in-sharedpreferences-without-secrets)). The UI lists the accounts in this order; the stored order of the accounts does not change.
  - **A removal activates the most recently active remaining account**, not the first in the list. The shell stays while an account remains; the router goes to Connect only after the last one.
  - **Add account through the Connect screen in an adding mode.** "Add account" pushes the onboarding Connect screen over the shell, with a close button (Android back and the iOS swipe do the same) that returns without signing in, and the servers of the existing accounts as one-tap chips ("Your servers") under the address field. The server overview and the browser sign-in are the onboarding ones. On `SignInSucceeded` the app goes to `/home`, where the router sends a new account to its first sync. `SignInSucceeded` carries `isNewAccount`, computed by `SignInController` from the registry before the sign-in (`signInAgain` is never new); when it is false, the account was already on the device, its session has been replaced and it is now active, and a snackbar says "You're already signed in to this account — switched to it".
  - **Remove through the existing sign-out, for any account.** The Accounts section's menu removes any account and the Sign out button the active one, both through `SignOut` (server logout, retire the session, wipe the tokens, remove the registry entry, dispose the sender and the engine, close and delete the database). The confirmation names the account and its server, says that its local data is deleted and, when its outbox holds ops, that its unsent changes are lost; while other accounts exist, the active account's button reads "Sign out of this account" and the dialog says that the app switches to the next account. Removing an inactive account leaves the active one, its engine, its scheduler and its screens untouched. Removing the active one runs the switch above and confirms with "Signed out of *name*". Cancel on the first-sync screen of an added account is the same sign-out, so the account the user came from is active again.
  - **Inactive outboxes drain in the foreground.** A keep-alive service runs while the shell is up and, on start, on resume and when the account list changes, asks the outbox sender of every signed-in account other than the active one that is not in `needsReauth` and has queued ops (counted on its database) to drain. It never builds a sender for an account without queued ops (opening the database to count is fine), never runs during a sign-out, and leaves the active account to the existing triggers. A sender once built keeps its own backoff timers, like the active one: it is kept alive per account until the account is removed. Inactive accounts are not synced.
  - **No frame of the wrong account.** Riverpod delivers derived providers one frame after the registry changes, so the transition does not rely on them alone. Each account has its own kept-alive status provider (`accountSyncStatusProvider(id)`), and `syncStatusProvider` returns the active account's, never the previous one's; the router's redirect reads the registry and that status itself. A switch, a removal of the active account and re-adding an existing account first wait (at most 5 s) for the target account's engine to report its stored state, so a synced account never shows the first-sync screen and a new one never shows its empty Overview. Screens that read the outbox (sync problems, the pending-changes line and chips, the remove dialog's count) ignore a value carried over from the previous account. The edit page sits in an account-bound wrapper that shows a blank page after a switch instead of looking the old id up in the new database. `/sync` has no entrance transition: with one, a shell → `/sync` → shell round trip within the animation would build two shells with the same navigator keys.
  - **No switch during a sign-in or a sign-out.** `switchTo` returns whether it switched and refuses while a sign-in, a sign-out or another switch runs; the sheet disables its rows meanwhile. A sign-in that completes activates its own account, which a switch made during it would otherwise silently undo.
  - **Rejected alternatives:**
    - **A navigation drawer** with the accounts. It is not native on iOS, and it competes with the tab bar for the top-level navigation and covers it; the sheet works the same on both platforms and leaves the tabs alone.
    - **Switching only by long-pressing the Account tab.** Not discoverable, and a long press on a tab has no affordance that a screen reader announces; the avatar button is visible and labelled.
    - **Tab stacks kept per account.** The kept screens are bound to ids of another account's database, which is the leak the reset prevents, and every account's stacks would stay in memory with their providers.
    - **Activating the first remaining account on a removal**, as the registry did. Arbitrary: the user expects to return to the account they came from, for example after cancelling the first sync of an account just added.
    - **Syncing inactive accounts in the foreground too.** Every account would cost what the active one costs ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync): up to 240 requests per hour while idle) for data that is not on screen; queued changes are what cannot wait. Step 16 brings background sync for every account.
    - **A separate "add account" route tree.** It would duplicate the onboarding screens (Connect, server overview, sign-in), their redirects and their tests; the adding mode is a flag on the same screen.
- **Consequences:**
  - Every account is one tap away from the Overview and Projects tabs, and the Account tab manages them. The same user on the same server cannot be added twice (same id), and the server chips reuse the stored root of an existing account, so adding a second user there does not create a second address for the same server ([D25](#d25-account-registry-in-sharedpreferences-without-secrets)).
  - A switch drops the previous account's navigation: each tab starts at its root, so a project opened in the Projects tab is closed. The switcher is reachable from the tab roots only, so no open edit page is lost today; a notification tap of step 15 that opens a task of another account has to switch first, through the same transition.
  - The recency field is additive: a build before step 4 ignores it and writes the registry without it, which costs only the order.
  - Changes queued in an account that is not shown reach the server while the app is in front, whichever account is active; its web changes arrive when it is active again, or with step 16. A drain that finds the session ended marks the account `needsReauth`, which the sheet shows; signing in again happens after switching to it.
  - Start and resume open the database of every inactive account to count its queue, and a sender built for an inactive account stays until the account is removed. Requests are made only while ops are queued.
  - Removing an inactive account pauses the active account's scheduler and session check only while the global "signing out" flag is set.
  - Notifications per account (step 15) and background sync and drains for every account (step 16, [D22](#d22-session-keep-alive-through-background-sync)) build on the same registry; the foreground drain stays for the time the app is in front.

*Accepted 2026-10-12, step 15. Carries out [D17](#d17-notification-policy) (the policy, the exact alarms and the permissions asked after the first sign-in) and the "every signed-in account" of [D16](#d16-multi-account-in-the-first-release), whose "cancels its notifications" on removal is now built. The outbox of [D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation), the creates of [D35](#d35-creates-through-the-outbox-temporary-negative-ids-with-remap-createupdatedelete-coalescing-lost-response-recovery-by-title-within-a-1-h-window), the reminders of [D36](#d36-labels-and-assignees-as-id-set-deltas-in-the-task-update-sent-through-their-endpoints-after-a-read-before-write-diff-reminders-as-the-whole-list-label-creation-online-only) and the refresh rules of [D26](#d26-refresh-concurrency-single-flight-re-read-and-adopt-write-ahead-epoch) are unchanged; the session manager gains a "no refresh" option for the background isolate.*

- **Context:**
  - The server never pushes reminders. Its cron looks at the reminders of the coming minute, stores an in-app notification for the assignees, the creator and the subscribers and sends an e-mail when that is enabled; a due date has no notification of its own, only the daily overdue e-mail ([research/sync.md](research/sync.md) §4.3). Nothing of that reaches a phone without polling, so the app has to schedule OS notifications itself from the local database ([research/sync.md](research/sync.md) §9.7), which since step 7 mirrors the server and holds every reminder with its instant ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync)).
  - D17 fixes the policy: undone tasks where the user is the creator or an assignee, reminders at their time and the due date at the exact due time, exact alarms on Android, the notification and exact-alarm permissions asked after the first sign-in, no overdue digest. D16 says that reminders cover every signed-in account and that a payload carries the account id, so a tap opens the right account.
  - Platform facts ([research/flutter-stack.md](research/flutter-stack.md) §3.10): iOS keeps at most 64 pending local notifications per app and drops the rest; Android allows about 500 alarms per app. `SCHEDULE_EXACT_ALARM` is denied by default on Android 14+ for a new install that is not an alarm or calendar app; the user grants it on the system page `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`, and without it an alarm can only be inexact (`inexactAllowWhileIdle`, minutes late in Doze). `USE_EXACT_ALARM` is granted automatically but Play policy reserves it for alarm, timer and calendar apps. `POST_NOTIFICATIONS` is a runtime permission on Android 13+; `RECEIVE_BOOT_COMPLETED` lets the plugin re-register the pending notifications after a reboot. A notification action without `DarwinNotificationActionOption.foreground` (iOS) or with `showsUserInterface: false` (Android) runs in a separate Flutter engine, through a top-level `@pragma('vm:entry-point')` function (`onDidReceiveBackgroundNotificationResponse`); a tap arrives in `onDidReceiveNotificationResponse`, or in `getNotificationAppLaunchDetails()` when it started the app. Android needs core library desugaring for the plugin.
  - Packages (pub.dev, 2026-10-12): flutter_local_notifications 22.3.2 (22.3.0 added `openAppNotificationSettings()`) and timezone 0.11.2. Due dates and reminder instants are absolute UTC instants: the server computes a relative reminder's instant and the app computes it locally for an unsent edit ([D36](#d36-labels-and-assignees-as-id-set-deltas-in-the-task-update-sent-through-their-endpoints-after-a-read-before-write-diff-reminders-as-the-whole-list-label-creation-online-only)). A notification is scheduled at an instant (`tz.TZDateTime.from(instant, tz.UTC)`), so no time zone is ever involved and the research's flutter_timezone is not needed.
  - A repeating task marked done comes back open from the server with shifted dates and reminders ([research/sync.md](research/sync.md) §4.4); the sender applies that answer to the row ([D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation)), so the database changes and the next occurrence can be scheduled from it.
  - The headless constraints: tokens are readable while the device is locked, once unlocked after a restart ([D24](#d24-tokens-in-secure-storage-readable-after-the-first-unlock)); a refresh that loses a race, or whose answer is lost, ends the session ([D26](#d26-refresh-concurrency-single-flight-re-read-and-adopt-write-ahead-epoch)), and a notification action has seconds, not a session's worth of care; two isolates may run an outbox sender for the same account; the sender claims an op `sending` in one SQLite transaction before it sends (D34), which alone was not enough: a new sender reset every `sending` op, also one still in flight elsewhere, and the next op could overtake it, so since step 16 an op `sending` elsewhere stops the queue until it is 5 min old and only then goes back to pending ([D40](#d40-background-sync-one-periodic-job-for-every-signed-in-account-with-a-deadline-skipped-while-the-app-is-in-front-the-incremental-run-as-the-session-keep-alive-a-one-off-drain-after-a-background-done-server-notifications-synced-into-a-local-inbox-on-their-own-cadence-new-unread-ones-as-activity-notifications-the-first-run-silent)); the database is shared across isolates (`shareAcrossIsolates`, [D31](#d31-one-drift-sqlite-file-per-account-shared-across-isolates-deleted-on-sign-out)); the session manager re-reads and adopts tokens another isolate stored (D26).
  - The contracts were laid down in `app/lib/core/notifications/` before the step: `NotificationGateway` (initialize, capabilities, requestPermission, openExactAlarmSettings, openNotificationSettings, schedule, cancel, pendingIds, showNow), `NotificationPayload` (`{account, task, key}`), `NotificationPreferences` (reminders and due dates, both on by default) with its store interface, and the pure functions `planNotifications` and `diffSchedule`.
- **Decision:**
  - **The plan** (`planNotifications`, pure): the candidates are the tasks with `done = false`, not queued for deletion, whose `createdById` is the user or whose assignees contain the user. Each reminder with an instant after `now` gives one entry with the key `<taskId>:reminder:<ordinal>` (the reminder's position in the task's list; a relative reminder of an unset date has no instant and gives none), when the account's `reminders` preference is on; the due date gives `<taskId>:due` at its instant, when `dueDates` is on and the instant is after `now`. A snooze whose `originalFireAt` equals the entry's planned instant and whose `until` has not passed moves the entry to `until`; any other snooze is dropped. The list is sorted by instant, then key. The title is the task title; the body is "Reminder · *project*" or "Due now · *project*", with the identifier when the task has one, localised through the app's l10n for the device locale (`lookupAppLocalizations`, which needs no widget tree, so the background isolate gives the same texts).
  - **The diff against a rolling window** (`diffSchedule`, pure, deterministic): of the plan only the first *window* entries are handed to the OS, 100 on Android and 60 on iOS (slack under the cap of 64 for snoozes and the test notification). A scheduled entry whose key is not in the window, or whose instant, title or body differs from the plan, is cancelled; a window entry that is not scheduled identically is scheduled; everything else is left alone. The window is refilled on every reconcile, so the OS always holds the soonest entries. Exactness is part of the diff: each row records whether the OS was given an exact alarm, so a granted or revoked exact-alarm permission re-registers the whole window on the next reconcile; the plugin's pending list is a cache that does not notice a revocation.
  - **OS ids:** a 31-bit positive hash of `<accountId>:<key>` (the first four bytes of its SHA-256, the sign bit cleared), stored with the entry. A collision inside the account (another key of the account already holds the id) probes upwards until a free id is found. Collisions across accounts are accepted: the plugin's id space is one per app, the probability is 2⁻³¹ per pair, and the other account's next reconcile finds its entry gone from `pendingIds()` and schedules it again. Id 1 is reserved for the test notification.
  - **The table `scheduled_notifications`** in the account's database (schema version 4, migrated from 3 with a dump `drift_schema_v4.json` and a migration test with data): `key` (primary key), `os_id` (unique), `task_id`, `kind`, `fire_at`, `title`, `body`, `snoozed_until` and `snooze_original_fire_at` (both nullable). The DAO loads it whole, replaces it in one transaction, sets and clears a snooze, deletes by task ids and deletes everything. It lives in the account database, not in preferences, because the background isolate reads and writes it too (`shareAcrossIsolates`) and because it goes with the account's data.
  - **The scheduler** (`NotificationScheduler`, one per account; the gateway, the database, the clock, the preferences store, the user id, the `describe` callback and the window are injected): `reconcile()` loads the tasks and the snoozes, plans, diffs, cancels and schedules through the gateway and writes the table; the write is guarded, so a table another isolate changed meanwhile stands and the run goes once more from it. Runs are serialized; a call during a run queues exactly one more. When the notification permission is not granted, or neither preference is on, it cancels every pending id of the account and clears the table instead. `exact` is the gateway's `capabilities().exactAlarms`: `AndroidScheduleMode.exactAllowWhileIdle` when Android allows exact alarms, `inexactAllowWhileIdle` otherwise, always exact on iOS. Triggers: a debounced (≈ 700 ms) watch on the tables `tasks`, `task_reminders` and `task_assignees` (drift's `tableUpdates`), the preferences stream, app start and resume, and the end of a background action. **One scheduler per signed-in account while the app runs**, not only for the active one: a keep-alive provider the shell listens to builds and keeps them, like `inactiveOutboxesProvider` of [D37](#d37-account-switcher-a-sheet-from-an-avatar-button-and-an-accounts-section-a-switch-resets-the-navigation-the-most-recently-active-account-follows-a-removal-inactive-outboxes-drain-in-the-foreground). Sign-out and account removal dispose the account's scheduler and cancel its pending ids before the database is deleted (`AccountDataWiper`), which fulfils D16.
  - **Preferences per account:** `NotificationPreferencesStore` over the `PreferencesStore` (key `notifications.<accountId>`, JSON), with a `changes` stream; the defaults are on (D17). Not in the database: the scheduler needs them before the database is open, and they are not sync state.
  - **Snooze is local only.** `snooze_10m` and `snooze_1h` write `until = now + 10 min` or `+ 1 h` and `originalFireAt`, the entry's planned instant, onto the table row, hand the OS the moved entry at once and reconcile; the plan then keeps the entry at `until`. A reconcile after the notification fired has dropped its row, so the row is taken from the task itself when needed (the key names the reminder's ordinal or the due date); an instant that is unset or has moved ahead makes the snooze a no-op. When the task's own time changes, the plan's instant no longer matches `originalFireAt` and the snooze is dropped; so is an expired one. Nothing reaches the server.
  - **Done from the background isolate, through the outbox, without a token refresh.** The plugin calls the top-level entry point (`core/notifications/notification_entry_points.dart`, `@pragma('vm:entry-point')`, passed to `initialize()`), which runs `handleNotificationAction(NotificationResponse)`: it builds a `ProviderContainer` the way `bootstrap.dart` does (the `ClientIdentity.load()` override included), decodes the payload and, for `mark_done`, calls `LocalTaskRepository.setDone(taskId, done: true)` on that account (a temporary id is resolved through the remap, D35), which writes the row and the op and starts a drain with a sender of that isolate; it cancels the task's other notifications, awaits the drain for at most ≈ 20 s (≈ 5 s on iOS, which completes the notification response before the Dart side runs and may suspend the process within seconds; that is also why the OS is told before any wait) and reconciles. The sender in that isolate asks the session manager for a token with a new "no refresh" option: it sends only when the stored access token is valid without a refresh, otherwise the op stays queued, untouched, and the next foreground run (or a background run of step 16) sends it. The claim-before-send transaction of D34 guarantees that the UI isolate's sender and the action isolate's never send one op twice. Errors are logged and never crash the isolate; the container is disposed at the end, which only disconnects its database client; the sign-out's wiper alone waits for the database isolate to close sqlite. The texts are resolved for the device locale once per isolate; the headless engine on iOS reports no locales, so the UI isolate notes the tag it resolved and the action isolate falls back to it, then to English. A running UI sees the change through its streams; the row's cloud-off mark covers the unsent case.
  - **A tap opens the task.** `onDidReceiveNotificationResponse` and, for a cold start, `getNotificationAppLaunchDetails()` hand the payload to a tap listener built like the "New task" shortcut listener of [D38](#d38-quick-add-the-web-grammar-in-vikunja_logic-with-d19s-fixes-weekday-and-ordinal-dates-at-the-default-time-and-an-unknown-project-kept-in-the-title-a-live-composer-labels-created-online-and-assignees-looked-up-on-submit-the-task-through-the-outbox): it waits for the shell, switches the account when the payload's account is not the active one (`AccountSwitcher.switchTo`, which refuses during a sign-in or sign-out, and then the tap is dropped), loads the task from that account's repository (a task that is gone gives a snackbar), brings a tab back to the Overview (a page over the shell, the edit page among them, stays and the sheet opens over it) and opens the detail sheet; after a switch it waits until the registry change has reached the providers, since that is when the shell closes the previous account's modals. A notification that fires while the app is in front is still shown (iOS with the alert, banner and sound presentation options).
  - **Onboarding once per device.** After the first completed sync of the first account the router sends the app to `/notifications-setup` while the preferences flag `notifications.onboarded` is unset; "Not now" sets it as well. The screen shows the logo, "Stay on top of your tasks", what gets notified (reminders at their time, due dates at the exact time, only your tasks) and "Turn on notifications" (`requestPermission()`); on Android 14+ without exact alarms a second step explains that reminders can be minutes late without them and offers "Allow exact alarms" (`openExactAlarmSettings()`) and "Skip", re-checking on resume. Then the shell.
  - **The Account tab** gets a Notifications section between the sync status and the pending changes: the switches "Reminders" and "Due dates" (per account), a status line ("Notifications are off" with "Open settings" when the OS has them off; "Reminders may be late" with "Allow exact alarms" on Android without exact alarms), the count of scheduled notifications and "Send a test notification" (`showNow` with the reserved id 1 and a payload for task 0, whose tap opens the Account tab).
  - **The gateway and the platforms.** `LocalNotificationGateway` wraps flutter_local_notifications 22.3.2: the Android channel `reminders` (importance high, name and description localised at initialisation), the three actions on both platforms (Android with `showsUserInterface: false` and `cancelNotification: true`; iOS as the category `task` with `DarwinNotificationAction.plain` and no `foreground` option), `zonedSchedule` with the UTC instant, `capabilities()` from `areNotificationsEnabled()`, `canScheduleExactNotifications()` and iOS's `checkPermissions()`, `requestNotificationsPermission()`, `requestExactAlarmsPermission()`, `openAppNotificationSettings()` and `pendingNotificationRequests()`. Android: core library desugaring, `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM` (never `USE_EXACT_ALARM`), `RECEIVE_BOOT_COMPLETED`, the plugin's receivers and a monochrome notification icon derived from the logo's checkbox mark (since 2026-10-13 the llama head of the new logo's glyph, [D42](#d42-app-icon-the-illustrated-llama-with-a-check-badge-adaptive-themed-and-ios-18-variants-derived-by-script)). iOS: the registrant callback for the background engine in `AppDelegate.swift` and the `UNUserNotificationCenter` delegate; no background modes.
  - **Rejected alternatives:**
    - **Scheduling only the active account.** D16 promises reminders for every signed-in account, and a reminder of an account the user switched away from is the one that would otherwise be missed. The cost is one scheduler and one table watch per account while the app runs, requests none.
    - **Re-scheduling everything on every change** instead of a diff. Every edit would cancel and re-create up to a hundred OS entries (visible as flicker in the system's pending list, and the iOS cap of 64 makes the order of the re-creation matter), and a snooze would be lost with the cancel. The diff touches only what changed and keeps the window full.
    - **The server's in-app notifications as the source.** They are created by the server's cron for the server's recipients, subscribers included, exist only for reminders (not for due dates) and arrive on the phone only when it polls; a notification about a reminder that fired a minute ago, delivered a sync later, is not a reminder. Step 16 shows them in an inbox; step 17 de-duplicates the WebSocket's `task.reminder` event against the local notification.
    - **`USE_EXACT_ALARM`** would spare the exact-alarm prompt, but Play reserves it for alarm, timer and calendar apps and a to-do app does not qualify; a rejected store listing is worse than one more screen. It could be reconsidered for an F-Droid flavour.
    - **Persisting a snooze as a new server reminder.** It would change the task for everyone who sees it, the web has no snooze to show it as one, and a snooze of ten minutes is not worth an outbox op; the snooze stays on the phone and is dropped when the task's own time changes.
    - **A foreground-only Done** (an action that opens the app). The point of the action is the one tap on the notification; an action that opens the app is a tap with extra steps. The outbox makes the background Done as safe as any write (D34).
    - **Refreshing tokens in the action isolate.** A refresh rotates the refresh token without a grace period (D26); a lost race against the UI isolate, or an isolate killed mid-request, ends the session for good, in exchange for sending a `done` a few minutes earlier. The op is queued either way and leaves with the next run.
    - **Hashing `(taskId, reminderInstant)` into the id**, as the research proposed. A reminder moved by a minute would then be a new id with a stale one to clean up; a key by ordinal stays stable across time changes, and the diff sees the changed instant as a reschedule of the same entry.
- **Consequences:**
  - Reminders and due dates fire on the phone from the local data, for every signed-in account, without the server; the one-tap Done is queued like every other write and sent when the stored token allows, and a snooze never reaches the server.
  - The store release (step 37) needs the Play Console exact-alarm declaration for `SCHEDULE_EXACT_ALARM`, as D17 said; the store listing has to explain the use.
  - Without exact alarms on Android 14+ a reminder can be minutes late; the setup screen and the Account tab say so and link to the system page.
  - Until step 16 nothing refills the window while the app is closed: what fires after the app was last in front is what the window held (100 on Android, 60 on iOS); an account with more reminders than that in the near future runs dry until the app is opened. `RECEIVE_BOOT_COMPLETED` re-registers the pending ones after a reboot, nothing more. Step 16's background runs reconcile for every account.
  - A background Done whose access token has expired stays queued until the next foreground run (or a background run of step 16); the notification is gone, the task shows done locally, and the Account tab counts the change as pending. A repeating task marked done from a notification stays done locally until the server's answer reopens it with the shifted dates, which the sender applies and the scheduler then turns into the next occurrence.
  - A cross-account id collision reschedules the colliding entry of the other account at its next reconcile; two notifications are never lost for good.
  - Texts are fixed at scheduling time: a language change on the device re-labels the pending notifications at the next reconcile (the diff sees the changed title or body and reschedules them).
  - The migration to schema version 4 runs on the first open after the update; `scheduled_notifications` of an account goes with its database on sign-out, after its ids were cancelled and its preferences forgotten.
  - New dependencies: flutter_local_notifications 22.3.2 and timezone 0.11.2 (whose database is initialised once at `initialize()` only when `tz.UTC` needs it).
  - App lock (step 35) may add `authenticationRequired` to the actions; grouping, custom sounds and an overdue digest (D17: no) are not planned.
  - Tests: `planNotifications` (creator, assignee and neither; done, pending delete, past instants, a relative reminder without an instant, a snooze applied, dropped and expired, the preference toggles, the order), `diffSchedule` (the window, unchanged kept, changed rescheduled, removed cancelled), the id hash and the collision probe, the scheduler against a fake gateway and an in-memory database (the table written, the watch triggering after a change, permission denied cancelling everything, dispose), the action handler with the fake gateway and the fake write client (Done queued, sent and the task's other notifications cancelled; Snooze rescheduled at +10 min; an unknown payload ignored), the preferences store, the migration from 3 to 4 with data, the wiper cancelling the ids, and widget tests for the setup screen (both buttons, the exact-alarm step on Android, the flag, the redirect only once), the Account tab section (the switches, the status lines per capability, the test button) and the tap listener (waiting, switching the account, opening the detail, a missing task), at 200 % text scale.

Polling from the background is what is left ([research/sync.md](research/sync.md) §9.5).
  - **Sessions.** Access tokens live 600 s (`service.jwtttlshort`); an OAuth session ends after 72 h without a refresh (`service.jwtttl`, sliding with every refresh). D22 asks the background sync to refresh every signed-in account at least about every 24 h, and D16 that background sync covers every signed-in account, not only the active one. D26 makes refreshes from several isolates safe (re-read and adopt, write-ahead) and asks that no background run start a refresh with only seconds of runtime left. D39's action isolate never refreshes, which is right for the seconds a notification action has, but a background sync that never refreshed would keep no session alive.
  - **OS limits** ([research/sync.md](research/sync.md) §9.5, [research/flutter-stack.md](research/flutter-stack.md) §3.9): Android's WorkManager runs periodic work at intervals of at least 15 min, only in Doze maintenance windows, and the App Standby Buckets thin it further (working set about every 2 h, frequent about 8 h, rare about 24 h, restricted about once a day); a worker is stopped after 10 min; one-off work can be expedited within a quota (below Android 12 only as a foreground service). iOS's BGTaskScheduler runs are opportunistic: the system decides from the app's usage, possibly never for a rarely opened app, never after the user force-quit it, not in Low Power Mode or with Background App Refresh off, and each run has about 30 s. workmanager 0.10.10 (2026-09-07; federated: workmanager_android 0.10.9, workmanager_apple 0.9.11) wraps both: periodic and one-off tasks with constraints, `ExistingPeriodicWorkPolicy`, expedited work with an `OutOfQuotaPolicy`, a top-level `@pragma('vm:entry-point')` callback dispatcher calling `Workmanager().executeTask`, and on iOS the `UIBackgroundModes`, `BGTaskSchedulerPermittedIdentifiers` that must equal the Dart task names, `setPluginRegistrantCallback`, `registerPeriodicTask(withIdentifier:frequency:)` and, under UIScene, `registerLaunchHandlers()`.
  - **Server notifications** ([research/api-v1.md](research/api-v1.md) §3.17, [research/sync.md](research/sync.md) §4.1–§4.2): the server stores an in-app notification per recipient for comments, assignments, mentions, created and deleted tasks, created projects, team memberships and fired reminders, never for the doer. The list is v2 `GET /notifications` (an envelope, newest first) or v1 `GET /notifications` (a bare array with `x-pagination-*` headers), each item `{id, name, notification, read_at, created}` with `read_at` the zero date while unread; notifications of projects the user can no longer read are left out. Mark one: v2 `PUT /notifications/{id}`, v1 `POST /notifications/{id}`, body `{"read": true|false}`; mark all: `POST /notifications` on both. The payloads: `task.comment` `{doer, task, comment, mentioned, project}`, `task.assigned` `{doer, task, assignee, project}`, `task.mentioned` `{doer, task, is_new, project}`, `task.created` `{doer, task, project}`, `task.deleted` `{doer, task}`, `project.created` `{doer, project}`, `team.member.added` `{member, doer, team}`, `task.reminder` `{task, project}`; `doer`, `assignee` and `member` are users (`username`, `name`), `task` carries `id`, `title`, `identifier`, `index` and `project_id`.
  - **The web's texts** ([research/client-logic.md](research/client-logic.md) §7), hard-coded English: "commented on #12", "assigned {name or you} to #12", "deleted #12", "created #12", "created {project}", "added {name or you} to the {team} team", "{doer} mentioned you on #12"; task notifications open the task, `project.created` the project, `team.member.added` the team.
  - The contracts were laid down before the step: `ServerNotification` in `vikunja_domain`; `NotificationsPort.list` and `NotificationsWritePort.markRead` / `markAllRead` in `vikunja_api`; `NotificationGateway.showActivity`, `ActivityRepository` and `BackgroundScheduler` (`registerPeriodicSync`, `enqueueDrain`, `cancelAll`) in the app.
- **Decision:**
  - **One periodic job for every signed-in account.** `WorkmanagerBackgroundScheduler` implements `BackgroundScheduler` and registers one periodic sync: on Android every 30 min with `NetworkType.connected` and `ExistingPeriodicWorkPolicy.update`, so registering again on every start neither duplicates the work nor restarts its period; on iOS the BGTaskScheduler task `dev.coderoftime.vikunja.sync` with a frequency of 30 min, which the system takes as the earliest begin date, not a promise (`UIBackgroundModes: fetch` is declared because BGAppRefresh needs it, but no separate background fetch is registered: the system ignores it once `BGTaskSchedulerPermittedIdentifiers` is set). `bootstrap.dart` passes the top-level `callbackDispatcher` (`core/background/background_entry_point.dart`) to `Workmanager().initialize` and registers the job after the first frame while at least one account exists; the last sign-out cancels everything (`cancelAll()`).
  - **The runner and its deadline.** `BackgroundSyncRunner` (`core/background/background_sync_runner.dart`, headless) builds a `ProviderContainer` the way D39's action handler does (the `ClientIdentity.load()` override included), but with session managers that refresh: D26 makes a refresh there as safe as one in the UI isolate, and without it the run would keep no session alive. A deadline is injected: 9 min on Android (under WorkManager's 10 min) and 25 s on iOS (under the ≈ 30 s), so that a refresh still in flight at the deadline has a margin to land its write-ahead (D26). The accounts take turns by the start of their last one (round-robin, the oldest synced first among equals), so an account that never gets through in time (an unreachable server, a slow one) does not keep the others from ever running, and the next account starts only while time remains. The scheduler's reconcile comes first for each account, from the local data alone, so the notification window is refilled even when the network steps use up the time, and once the server proved unreachable the account's other network steps are skipped. At the deadline, and when WorkManager stops the worker (`onTaskStopped`), a token refresh still on its way gets a few seconds to land, then the container is disposed, which aborts the running engine (`dispose()`: the incremental run restarts from its watermark, D33). A failure in one account is logged and does not stop the next. The run writes `background.lastRunAt.<account>` and `background.lastRunResult` to the preferences for the Account tab. Nothing is thrown out of the callback, and it reports success to the plugin even when nothing could run: a failure would add WorkManager's own retry backoff on top of the period, and the next periodic run comes anyway.
  - **Skipped while the app is in front.** The UI isolate writes a heartbeat to the preferences every 30 s while the app is visible, on a timer of its own (the foreground scheduler's ticks wait for a long run and back off up to 5 min); a run that finds it younger than 2 min does nothing, and a run checks again before every account, because the foreground already syncs the active account (D33), drains the inactive outboxes ([D37](#d37-account-switcher-a-sheet-from-an-avatar-button-and-an-accounts-section-a-switch-resets-the-navigation-the-most-recently-active-account-follows-a-removal-inactive-outboxes-drain-in-the-foreground)) and reconciles every scheduler (D39).
  - **One run per account across isolates.** The heartbeat does not keep the isolates apart in every case (a run that began before the app came to the front, a notification action, a cached process), and overlapping runs are not harmless: a full run purges every task it did not mark itself (D33), so tasks another run marked meanwhile would be gone until the next full run, and two outbox senders could send one create twice or let an edit overtake one in flight. So every sync run takes the account's lease in `sync_state` (`sync_lease`, `{owner, until}`, 3 min) in a transaction, renews it on every checkpoint and before every request, checks it in the purge's and the completion's transaction and releases it at the end; a run whose lease another run took stops and purges nothing. The app's engine waits for a lease held elsewhere and adopts the state that run stored; the engines of the background and action containers (`runsHeadlessProvider`) skip the sync instead and never run the daily full resync, which the app runs when it is in front. The outbox needs no lease: an op `sending` elsewhere stops every sender's queue until it is 5 min old, longer than any live sender takes over one op (D34, D39).
  - **Per account**, while time remains: `NotificationScheduler.reconcile()` → `SyncEngine.refresh()` (the incremental run of D33; headless, so never the daily full resync) → `OutboxSender.drain()` (D34; a Done of D39 whose token had expired among the ops) → `ActivitySync.run()` with the notifier (below) → `NotificationScheduler.reconcile()` (D39), which refills the notification window while the app is closed. **The keep-alive costs nothing extra:** every incremental run starts with `GET /user` (since step 13, [D38](#d38-quick-add-the-web-grammar-in-vikunja_logic-with-d19s-fixes-weekday-and-ordinal-dates-at-the-default-time-and-an-unknown-project-kept-in-the-title-a-live-composer-labels-created-online-and-assignees-looked-up-on-submit-the-task-through-the-outbox)), runs are at least 15 min apart and access tokens live 600 s, so that request finds the token expired, refreshes it and slides the 72 h window.
  - **Session ended.** A `SessionEnded` marks the account `needsReauth`, as in the UI isolate (its local data stays, its outbox pauses), and posts one activity notification "Sign in again to *host*" (payload key `session:<account>`). A preferences entry remembers that it was shown for this ended session, so later runs do not repeat it until the account is signed in again.
  - **Expedited drain after a background Done.** When the drain of D39's action isolate ends with `TokenRejected` (the stored access token had expired, and that isolate never refreshes), the handler calls `BackgroundScheduler.enqueueDrain()`: on Android an ordinary one-off task with a network constraint, chained after a drain that is already running (`ExistingWorkPolicy.append`), handled by the same callback dispatcher in a refreshing container, so the op goes out within minutes instead of at the next app open; not expedited, because below Android 12 WorkManager runs expedited work as a foreground service, which the plugin's worker does not provide, and fails it before it starts; on iOS a no-op, because iOS has no on-demand background runs.
  - **The activity sync** (`ActivitySync`, per account, headless; the read and write clients, the database and a clock injected). `run()` pulls pages newest first until a page contains an id already stored, at most 3 pages (once an hour, and on the inbox's pull-to-refresh, it keeps reading while an older stored notification is still unread here, up to the 200 kept, so read states made elsewhere arrive), upserts them (keeping the local `read_pending` and `notified`), then sends the pending reads: one `markAllRead()` when every unread notification is pending read, else one `markRead(id)` per id; `read_pending` is cleared on success and kept on failure (a 403 or a coded 404 for a notification that is gone counts as done, as 2.7.0 answers 403). It prunes the table to the newest 200 and returns the ids that are new and unread. The first run of an account (no `activity_synced_at` in its `sync_state` yet) stores everything as already handled, so a sign-in never floods the shade with old activity; the inbox still lists it. Its cadence is its own, outside the task sync: for the active account on start, on resume, every 5 min while the app is in front (every 5th tick of `ForegroundSyncScheduler`) and on the inbox's pull-to-refresh; for every account in every background run. The quiet task sync stays at its 5 requests (D33, D38).
  - **The notifier** (`ActivityNotifier`). For every new unread notification of the kinds `task.comment`, `task.assigned`, `task.mentioned`, `task.created`, `task.deleted`, `project.created` and `team.member.added`, when the account's `activity` preference is on and the notification permission is granted, it calls `NotificationGateway.showActivity` and marks the row notified, so nothing is shown twice. Never `task.reminder`: the local reminders of D39 fired at the right time, and the server's copy, a sync later, would be a duplicate. `activity` is a new field of `NotificationPreferences`, on by default; a stored entry without it reads as on, so the store needs no migration. The os id is D39's 31-bit hash over `<account>:activity:<id>`; the payload is `{account, task: <taskId, or 0>, key: activity:<id>}`; the title is the task title (else the project or the team); the body follows the web's wording with the doer's name, in en and de: "Anna commented: …" (the first 80 characters of the comment as plain text), "Anna assigned you", "Anna mentioned you", "Anna created this task in *project*", "Anna deleted this task", "Anna created the project *title*", "Anna added you to the team *team*". In the foreground the active account's notifications are not shown (the bell's badge shows them); the other accounts' are. `LocalNotificationGateway.showActivity` uses a second Android channel `activity` (default importance, name and description localised) without actions, and no category on iOS.
  - **The table `server_notifications`** in the account's database (schema version 5, migrated from 4 with a dump `drift_schema_v5.json` and a migration test with data): `id` (primary key), `name`, `payload` (JSON text), `created`, `read_at` (nullable), `read_pending` (nullable: the read state still to send) and `notified` (shown as an OS notification, or suppressed by the first run). The DAO upserts a page, watches everything newest first and the unread count (after applying the pending reads), marks read locally, lists the pending reads, gives the highest id and prunes to the newest 200. It lives in the account database because the background isolate writes it, and it goes with the account's data on sign-out.
  - **Reads are local-first.** `LocalActivityRepository` implements `ActivityRepository` over the DAO and `ActivitySync` (`activityRepositoryProvider` for the active account, `accountActivityRepositoryProvider(accountId)`): marking read changes the table at once (`read_pending`), the badge and the inbox follow, and the next activity sync sends it; offline the inbox works from the table.
  - **The inbox and the taps.** A bell in the Overview app bar with the unread count as a badge ("Notifications, N unread") pushes the inbox (`/home/inbox`) over the shell: newest first, grouped by Today, Yesterday and Earlier, each row with an icon per kind, the doer's initials, the web's text localised, the task's identifier and title and the relative time, bold while unread. A tap marks read and opens the task's detail sheet when the task is on the device (else a snackbar says it is not); `project.created` opens the project. An overflow "Mark all as read", pull-to-refresh and "You're all caught up" when empty. The tap listener of D39 learns two payload keys: `activity:<id>` switches the account when needed, marks read and opens the task, or the inbox when the task is 0 (`team.member.added` among them, until team screens exist); `session:<account>` switches to the account and opens the Account tab with its reauth banner. The Account tab gets an "Activity" switch in its Notifications section and, in the sync status, "Background sync: *time* ago" or "Background sync has not run yet", on iOS with a line that the system decides when it runs.
  - **Rejected alternatives:**
    - **One periodic job per account.** More wake-ups for the same work, while WorkManager's quota, the standby bucket and iOS's scheduling are per app anyway. One job orders the accounts itself (by their last turn) and shares one wake-up, one container and one deadline.
    - **Syncing in a foreground service.** It would run when told to, but it costs battery, shows a permanent notification and needs a Play foreground-service declaration that a periodic sync does not justify; WorkManager is the path Play expects for deferrable work.
    - **The WebSocket in the background.** Neither OS keeps a socket open for an app in the background, and the upgrade shares the login rate limiter; step 17 uses it in the foreground only.
    - **UnifiedPush or ntfy through webhooks** (D20). It needs a webhook per project pointing at a distributor the user runs, server setup the app cannot do for the user; it may come later as an option on top of this polling.
    - **Notification reads through the task outbox.** The outbox is task-centric (ops keyed by task id and coalesced per task, D34); a read is idempotent and cheap to send again, so a `read_pending` column and a resend in the next run cover it without a new op kind.
    - **Showing every server notification on the first sync**, old ones included. A sign-in, a reinstall or an added account would flood the shade with weeks of old activity; the first run stores them as notified and the inbox lists them.
    - **Refreshing tokens only in the UI isolate**, as D39 does for the action isolate. Every session would end after 72 h without opening the app, which is what D22 is about. A background run has minutes (Android) or tens of seconds (iOS) and a deadline below the OS limit, not the seconds of a notification action.
- **Consequences:**
  - On Android, web changes, server notifications and the notification window follow within about 30 min while the app is closed, stretched by Doze and the standby bucket; each run refreshes every account's session, so a session stays alive as long as the OS runs the job at least once in 72 h.
  - On iOS, background runs may come rarely or never, and never after a force-quit; D22's 72 h limit still applies there, and the "Sign in again" notification appears only when a run finds the session ended. The Account tab says that the system decides.
  - Cost: a quiet run costs about 5 requests per account for the task sync, 1 for the activity page and, nearly always, 1 token refresh (the access token lives 600 s), with an empty outbox; a small account's responses add up to a few tens of kilobytes, most of it the project list. At 30 min that is at most 48 runs a day on Android, far fewer in Doze, each waking the radio for seconds in a maintenance window the OS shares with other apps. The foreground budget is unchanged: the quiet task sync stays at 5 requests, and the activity page comes every 5th minute, not every minute.
  - Play policy: the background work is WorkManager's only. The app runs no foreground service of its own and does not opt into workmanager's `FOREGROUND_SERVICE_DATA_SYNC` (opt-in since 0.10.7), asks for no `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` and uses no exact alarm for the sync; D17's exact-alarm declaration stays the only special one.
  - The heartbeat keeps a background run and the UI isolate apart in the usual case and the sync lease and the outbox's in-flight stop in every case, and a sign-out happens only in the front, but a run that began before the app came to the front can still be inside an account the user then removes. D26's open point (a sibling isolate writing tokens back after a sign-out elsewhere) and the background database connection that a sign-out must not outlive ([D31](#d31-one-drift-sqlite-file-per-account-shared-across-isolates-deleted-on-sign-out)) are narrowed by this decision, not closed.
  - The migration to schema version 5 runs on the first open after the update, in whichever isolate opens the database first; `server_notifications` goes with the account's database on sign-out.
  - New dependency: workmanager 0.10.10 (iOS 14.0+, under the app's minimum of 15.0). iOS needs the background mode `fetch`, the permitted identifier `dev.coderoftime.vikunja.sync` and the plugin's registrant and launch handlers in `AppDelegate.swift`, next to the notification plugin's.
  - Not built: deleting server notifications, team and project screens (`team.member.added` opens the inbox), the comments themselves (step 27; the inbox shows the comment text of the notification), the WebSocket (step 17).
  - Tests: the notifications ports with the fake HTTP adapter (both versions, paging, zero dates, payload parsing, the write verbs and bodies, a 404 on a gone notification as success) and the `ServerNotification` getters; a contract test on both versions with two users (B assigns A, and comments when the server has comments enabled; A's list has `task.assigned` with the doer, the task and the project; read, unread, all read); the DAO and the migration from 4 to 5; `ActivitySync` (the first run marks everything notified, later runs return only the new unread ones, the stop at a known id, the 3-page cap, the hourly and pull-to-refresh read-back of the stored window, pending reads sent and kept on failure, the mark-all case); the notifier (the kinds, the preference off, the permission denied, the texts per kind in en and de with their fallbacks, the os id's stability, never twice, five per run and one for the rest, the tray trimmed to ten, the account label); the runner with fakes (the heartbeat skip, the deadline between accounts and the dispose, a session ended → `needsReauth` and one notification, the turn order by the last attempt, the app coming to the front between accounts, an OS stop, an unreachable server skipping the other network steps, every step called); the scheduler adapter against a fake `Workmanager` wrapper (the registration arguments per platform); the action handler enqueueing a drain on `TokenRejected`; an app contract test of the activity sync against 2.7.0; and widget tests for the inbox (the rows per kind, the grouping, the taps on a local task, a missing task and a project, mark all, a failing pull-to-refresh, the empty state), the badge with its semantics, the Activity switch, the background line, the tap routing of activity and session payloads, at 200 % text scale.

## D41: Relations as deltas in the task update, sent through the relation endpoints after a read-before-write diff, temporary ids on both ends resolved at send time, the inverse rows kept locally; duplicate and subscriptions online-only; subtasks from indented quick-add lines

*Accepted 2026-10-13, step 14. Extends [D36](#d36-labels-and-assignees-as-id-set-deltas-in-the-task-update-sent-through-their-endpoints-after-a-read-before-write-diff-reminders-as-the-whole-list-label-creation-online-only) by relations, the last delta of the task update, and [D35](#d35-creates-through-the-outbox-temporary-negative-ids-with-remap-createupdatedelete-coalescing-lost-response-recovery-by-title-within-a-1-h-window) by temporary ids at the other end of an edge; the op kinds, the sender and the retry classes of [D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation) are unchanged, and the remap of D35 now also rewrites relation refs. Carries out the subtasks by indentation that [D38](#d38-quick-add-the-web-grammar-in-vikunja_logic-with-d19s-fixes-weekday-and-ordinal-dates-at-the-default-time-and-an-unknown-project-kept-in-the-title-a-live-composer-labels-created-online-and-assignees-looked-up-on-submit-the-task-through-the-outbox) left for step 14.*

- **Context:**
  - Since step 12b label and assignee changes are id-set deltas in the task's ordinary update op, sent through their endpoints after a read of the task ([D36](#d36-labels-and-assignees-as-id-set-deltas-in-the-task-update-sent-through-their-endpoints-after-a-read-before-write-diff-reminders-as-the-whole-list-label-creation-online-only)), and a create waits under a temporary negative id until the sender remaps it to the server's ([D35](#d35-creates-through-the-outbox-temporary-negative-ids-with-remap-createupdatedelete-coalescing-lost-response-recovery-by-title-within-a-1-h-window)). Relations are read-only: the sync stores every task's `related_tasks` as `task_relations` rows (`task_id` with a cascading foreign key, `other_task_id` without one, `kind`), and the mappers rebuild `Task.relatedTasks` from the rows whose other task is local, but nothing on the phone changes them. Quick add strips the indentation of pasted lines and creates flat tasks ([D38](#d38-quick-add-the-web-grammar-in-vikunja_logic-with-d19s-fixes-weekday-and-ordinal-dates-at-the-default-time-and-an-unknown-project-kept-in-the-title-a-live-composer-labels-created-online-and-assignees-looked-up-on-submit-the-task-through-the-outbox)). Duplicating a task and following one do not exist.
  - Verified server facts (Vikunja 2.7.0, probed live on both API versions on 2026-10-13; [research/api-v1.md](research/api-v1.md) §3.7, §3.10 and §3.16):
    - **Relations:** a create is v2 `POST`, v1 `PUT /tasks/{id}/relations` with `{other_task_id, relation_kind}`, 201 with `{task_id, other_task_id, relation_kind, created_by, created}`. The server stores the **inverse edge on the other task**: a child's `parenttask` edge to its parent gives the parent a `subtask` edge to the child, and the pairs are subtask and parenttask, related and related, duplicateof and duplicates, blocking and blocked, precedes and follows, copiedfrom and copiedto. An edge that is already there, also when only its inverse was created from the other side, answers 409 code 4008; a cycle 409 code 4023; the task itself as the other task 400 code 4010; an unknown kind 422 on v2 and 400 code 4007 on v1; an other task that does not exist **404 code 4002**, the code of a task that is gone, which here must not be read as the base task being gone. A delete is `DELETE /tasks/{id}/relations/{kind}/{otherId}`, 204 on v2 and 200 on v1, and removes **both directions**; an edge that is not there answers 404 code 4009. Reads carry `related_tasks` as `{kind: [Task]}`, `{}` when there are none; the answer of a v1 `POST /tasks/{id}` carries `{}` or null whatever the task has. A relation change bumps `updated` asynchronously and only on the task the request was made on, not on the other task whose inverse edge changed; the incremental sync's 120 s overlap covers the delay ([D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync)).
    - **Duplicate:** v2 `POST`, v1 `PUT /tasks/{id}/duplicate`, 201 with `{duplicated_task: Task}`: a copy with the source's title, labels, assignees, attachments and reminders and `related_tasks.copiedfrom: [source]`, while the source gets `copiedto`. Not idempotent: every request makes another copy.
    - **Subscriptions:** v2 `POST`, v1 `PUT /subscriptions/{task|project}/{id}`, 201; already subscribed 412 code 12002. `DELETE` on the same path, 204 on v2 and 200 on v1; not subscribed 403; deleting a subscription that a task inherits from its project stores an opt-out, and the task then reads `subscription: null`. The creator of a task is subscribed automatically. The state is only on single reads: `GET /tasks/{id}` and `GET /projects/{id}` carry `subscription: {id, entity: "task" | "project", entity_id, created}` or null, an inherited one naming the project; the list reads of the sync carry none.
  - The web's multi-line add ([research/client-logic.md](research/client-logic.md) §1.9 item 12): `parseSubtasksViaIndention` drops blank lines, removes the first line's indent, strips the list markers and makes a line indented deeper than the one before it a subtask of the nearest earlier line with less indent; the web creates the tasks, then each child's `parenttask` relation to its parent, and a child line without a `+project` of its own inherits the parent line's.
  - The outbox rules that must keep holding: one op per task in FIFO order, the field-wise merge and the fold of a failed op into a newer one ([D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation)), the update behind an unsent create that the remap rewrites (D35), and the read-before-write diff that makes the whole update idempotent (D36). What is new: an edge names a second task, whose create may still be queued too.
- **Decision:**
  - **`RelationChange` in `TaskChanges`, like labels.** `TaskChanges` gains `relations`, a `RelationChange` (`vikunja_domain`: the edges `added` and `removed`, each a `TaskRelationRef(kind, otherTaskId)`; `merge(later)` lets the later change win for an edge both touch; `applyTo(current)`; `mapTaskIds(resolve)`; `isEmpty`), stored in the payload JSON as `{"added": [{"kind", "other"}], "removed": […]}`, with older payloads read unchanged. No new op kind: an edge is a field of the task's ordinary update op, queued, merged, ordered and folded by the D34 rules, and on a task whose create is still queued it is part of the update that waits behind the create, as labels are (D36). An edge is queued on the task the user edits, from that task's side, as the web does: a subtask added to a parent is the child's `parenttask` edge to the parent.
  - **Sending with a read-before-write diff.** `TasksWritePort.update(id, changes)` sends the body fields as before; when `relations` carries a change, it takes the task as the server has it (the answer, or `GET /tasks/{id}`), sends a remove for every edge in `removed` that `related_tasks[kind]` lists and an add for every edge in `added` that it does not, removes first (v2 `POST`, v1 `PUT /tasks/{id}/relations`; `DELETE /tasks/{id}/relations/{kind}/{otherId}`), and reads the task back once when anything was sent (the same final read as after label and assignee requests). A 409 code 4008 on an add and a 404 code 4009 on a remove count as done: a retry, the inverse created from the other side or a web edit got there first. Every other-task id must be positive at this point, and the port throws an `ArgumentError` otherwise, because the caller resolves temporary ids. A 404 code 4002 on a relation add, the other task missing, is wrapped into a failure of its own, so that neither the sender nor anything else reads it as the base task being gone.
  - **Temporary ids at both ends.** An edge may be queued on a task whose create is queued, and may name one (a negative `otherTaskId`). The first is D35's case: the update waits behind its create and is rewritten by the remap. For the other end, the sender resolves every relation ref through `TasksDao.resolveId` (`task_id_remaps`) at send time; an op whose relations still name a temporary id waits like an op under a temporary task id, and the next op in line goes first. FIFO puts the other task's create ahead in practice, because it was queued before an edge could name it; the wait covers the case where it is not (that create was rejected or waits out its backoff). `completeCreate` rewrites, in its transaction, `task_relations.other_task_id` and the relation refs of every queued payload from the temporary id to the server id, and the pending overlay restores the remapped task's own rows.
  - **The inverse rows locally.** The transaction that queues the op changes the task's `task_relations` rows by `RelationChange.applyTo` and, when the other task is local, the inverse rows on the other task (the pairs above), so a parent shows a subtask added offline at once, as the server will show it once both sides are synced. Hydration already shows only edges whose other task is local. The sync overlay keeps the pending relation deltas over incoming rows, as it does for labels. Since the server bumps only the task a relation was changed on, a pull may bring one side alone: the upsert also makes the rows other local tasks hold to the pulled task the inverse of its edges, with those tasks' own queued relation changes on top. The v1 update, which cannot change relations, takes them from the read it makes first rather than from its answer.
  - **Failures.** A cycle (409 code 4023), the task itself (400 code 4010), an unknown kind (v2 422, v1 400 code 4007) and the wrapped other-task-missing (`RelatedTaskMissing`, a `NotFound` with the other task's id, stored as a failure kind of its own) are permanent failures of D34's table: a sync problem that names the task and says why (a related task gone, a loop, the task itself), with Retry and Discard. 4008 and 4009 never reach the sender. A missing other task does not hold back the rest of the update: the port tries every other request of the op before it throws, and the outbox forgets the task as it does a gone label: its edges leave that op, every other queued op (a failed one that changed goes back to the queue) and the stored rows. The op stays failed only to say why the edge is gone; an edit merged into it later goes out without that edge. A task the sync purges is forgotten the same way.
  - **Duplicate online-only.** `TaskRepository.duplicateTask(taskId)` drains the task's queued ops first and refuses while any remain (offline that is a failure the UI words as "needs a connection"), then calls `TasksWritePort.duplicate` with the server id, upserts the copy locally and returns its id; the source's `copiedto` edge follows with the next sync at the latest. No outbox op and no temporary id: the server copies its own state of the task (an unsent edit is not part of it, the attachments exist only there), every request makes another copy, and a lost answer could not be recovered the way D35 recovers a create, because the copy has the source's title.
  - **Subscriptions online-only.** `SubscriptionRepository` (`LocalSubscriptionRepository` over the read and write clients; `subscriptionRepositoryProvider` for the active account, `accountSubscriptionRepositoryProvider(accountId)` for any) reads the state with `SubscriptionsPort.forTask` / `forProject` when a screen needs it and toggles it with `SubscriptionsWritePort.subscribe` / `unsubscribe`, returning the state read back; a 412 code 12002 on a subscribe counts as done. A temporary task id is resolved through the remap; a task whose create is still queued cannot be followed yet, and the UI says it is available once synced. Nothing is stored locally and nothing is queued: the state is only on single reads, and a toggle is one cheap request whose result the user sees at once. Already subscribed (412 code 12002) counts as done; an unsubscribe answered 403 without a code is checked with one read of the task or project and counts as done when it shows no subscription, else the 403 is passed on. Unsubscribing a task's own subscription while its project is followed also stores an opt-out, which survives unfollowing and re-following the project (verified on 2.7.0); creators follow the tasks they create, not the projects.
  - **Indented quick-add lines become subtasks.** `parseSubtasksViaIndention(text, mode:)` in `vikunja_logic` returns an `IndentedLine` per task (its text, the index of its parent line, the `+project` it inherits in the mode's prefix), following the web's rules with a tab counted as four spaces, a bare `[ ] ` taken as a list marker as in D38, a line that is only a marker dropped (its subtasks move up to its parent) and the project inherited by grandchildren too, pinned by the web's test vectors (`parseSubtasksViaIndention.test.ts` at `e7d7f17`, ported as Dart cases without copying code, as D38 says). `QuickAddService.submit` uses it for multi-line input: every line is created as D38 says, a child line without a project of its own takes its parent line's, and each child gets `updateTask(childLocalId, TaskChanges(relations: RelationChange(added: {TaskRelationRef(parentTask, parentLocalId)})))`, queued after both creates, so it goes out once both are remapped. Single-line input is unchanged, and the count stays the number of tasks.
  - **UI.** The detail sheet owns the graph:
    - a **Subtasks** section: each subtask with a done checkbox (`setDone`), its title and identifier, a tap opening its detail; an inline "Add subtask" field that creates a task in the parent's project (`createTask`, then the child's `parenttask` edge through `updateTask`), offline too;
    - a **Parent** line when the task has a parent task, which a tap opens;
    - a **Related** section that groups the other kinds under localised names (Related to, Blocks, Blocked by, Precedes, Follows, Duplicate of, Duplicated by, Copied from, Copied to), each edge removable behind an adaptive confirmation, and "Add relation": a sheet with a kind picker (default `related`, because the user's `default_task_relation_type` is not in the synced settings yet) and a search over the account's local tasks by title and identifier, without the task itself and, unless toggled, done tasks;
    - **Duplicate** in the overflow menu, confirmed by a "Duplicated" snackbar whose "Open" opens the copy, or the usual failure message ("needs a connection" while offline or with queued changes);
    - a **follow** bell in the header, its state read online when the sheet opens, hidden while unknown (offline, with a quiet hint that following needs a connection), shown on with "Following the project *title*" when the subscription is inherited, and asking, when an inherited one is turned off, whether to stop following just this task. A project screen's overflow has "Follow project" / "Unfollow project";
    - outside the sheet: no relation editing on the edit page, and the composer's multi-line preview names the tree in its count ("3 tasks, 2 as subtasks").
  - **Rejected alternatives:**
    - **Separate op kinds for relation changes.** D36's reasoning holds: a second op kind per task would need its own ordering against the task's update and create, its own coalescing, its own fold into a failed op and its own rewrite at the remap; inside `TaskChanges` the delta merges field-wise, one op per task keeps the rules of D34 and D35, and the read-before-write diff makes the op idempotent.
    - **Writing the inverse row only after the server answers.** The parent would not show a subtask added offline, the common case of "Add subtask" and of quick add's tree, until the send and a sync that pulls the parent. The server creates the inverse in the same request and deletes both directions, so the local row anticipates exactly what the next pull brings, and the overlay keeps it meanwhile.
    - **Duplicate through the outbox under a temporary id.** A lost answer could not be recovered by D35's lookup by title, because the copy has the source's title: a blind resend could make a second copy, and never resending could lose the copy when the request did not arrive. The server also copies its own state, attachments included, not what the device shows. Online, the user sees the result at once.
    - **Syncing the subscription state of every task.** It is only on single reads, so the sync would need one extra request per task, while it matters only where the bell is shown.
    - **Relations on the edit page.** The detail sheet is where the graph is shown (subtasks with their checkboxes, the parent, the related tasks), and an edge is a single change that needs no save step; a second editor on the edit page would duplicate it.
- **Consequences:**
  - Subtasks and the other relations are editable offline, also between tasks whose creates are still queued; an edge goes out once both creates are through, in the update of its own task, and both tasks show it locally from the moment it is queued.
  - An update with relation changes costs what one with label changes costs: a read when it has no body fields, one request per edge that differs and a final read (on v1 plus the overlay's read).

  - Not built: subtasks nested in the project lists (step 9), Gantt arrows (step 29), the kanban board (step 20), project sharing (step 28), the user's default relation kind (`default_task_relation_type`, until the settings carry it).

## D46: Realtime in the foreground: one WebSocket for the active account while the app is in front, pushed notifications stored at once and a sync nudged for the task they name, re-auth on every token change, quiet fallback to polling

*Accepted 2026-10-19, step 17. Carries out the foreground WebSocket that [D33](#d33-incremental-sync-watermark-on-updated-with-a-120-s-overlap-keyset-over-updated-id-delete-detection-by-per-project-count-check-and-id-reconcile-daily-full-resync) and [D40](#d40-background-sync-one-periodic-job-for-every-signed-in-account-with-a-deadline-skipped-while-the-app-is-in-front-the-incremental-run-as-the-session-keep-alive-a-one-off-drain-after-a-background-done-server-notifications-synced-into-a-local-inbox-on-their-own-cadence-new-unread-ones-as-activity-notifications-the-first-run-silent) leave to step 17, with two corrections to their plan: the socket does not replace the 60 s sync timer, and the server's reminder notifications need no de-duplication.*

- **Context:**
  - Since step 16 the active account's server notifications reach the inbox through a poll about every five minutes while the app is open; a comment written on the web a minute ago shows up minutes later.
  - Verified server facts (Vikunja 2.7.0, both API versions, probed on 2026-10-19; the web read at `e7d7f17`):
    - **The socket** (`/api/v2/ws`, `/api/v1/ws` since 2.3.0) pushes only `notification.created` and, with the time-tracking licence, `timer.*`; **there are no task or project change events**. A pushed notification equals the item of `GET /notifications` field by field, for every kind that is stored: comments (mentions in comments included), assignments, mentions, tasks created or deleted in followed projects, projects created, team memberships and reminders. Events while disconnected are lost, and reads are never pushed.
    - **Auth:** a user JWT within 30 s; a bad token gets `invalid_token` and a normal close; the server closes at the token's expiry ("token expired") unless a refreshed token of the same session re-authenticates the open socket (2.7.0); a logout or revoked session closes that session's sockets ("session revoked"). The server pings every 30 s and drops a socket that does not answer.
    - **The upgrade shares the per-IP limit of login and registration** (10 a minute, refused upgrades included; 429 with `Retry-After`). No setting disables websockets and `/info` does not tell; only the upgrade's status does (404, 426 or 502 behind a proxy that cannot upgrade).
    - **The web** re-authenticates after every token refresh, reconnects with a backoff of 1 to 30 s, and on a notification only reloads its list.
    - The app's REST requests go through Cronet and NSURLSession; dart:io, the only WebSocket client without a new dependency, ignores system proxies and user-installed CAs on Android.
- **Decision:**
  - **One socket, for the active account, while the app is in front** (`realtimeConnectionProvider`, gated like the foreground sync scheduler): after the account's first sync, never while it needs a new sign-in or is being signed out, never in a background isolate, only on servers with the WebSocket capability. It opens on start and resume, closes normally on hide and pause, and moves with an account switch; the socket closes before our own logout request, so the server's "session revoked" that follows is ignored. Inactive accounts keep their poll and the background job is unchanged (D40). `HomeShell` keeps this provider and the other per-account services alive from `initState`; listening in `build` had restarted the 60 s timer and pulled every account's activity on each tab switch since step 16.
  - **Transport** in `vikunja_api` on dart:io without a new dependency: `IoRealtimeConnector` does the upgrade by hand so that a refused one reports its status and `Retry-After`, checks `Sec-WebSocket-Accept`, sends the app's User-Agent and no Origin, gives up after 15 s, and pings every 25 s to notice a dead connection; a drop without a close frame reports no close code. `realtimeUri` uses the API version the account negotiated, keeping the sub-path and port. Nothing logs frames or tokens; the app logs states, statuses and close codes at FINE.
  - **Sequence:** upgrade, then the account's current token, `auth`, `auth.success` within 10 s, `subscribe notification.created`, live; a catch-up of the inbox runs alongside, because events while disconnected are lost.
  - **Events:** a pushed notification is stored at once like a polled one, as handled (the active account in front never gets OS notifications, D40), so the inbox and the bell badge update by themselves; a reminder is stored as the poll stores it, never shown and never counted, so it needs no de-duplication against the local reminder. Comments, assignments, mentions, created and deleted tasks and created projects request one incremental sync of the active account, debounced by 2 s and coalesced with a run in progress; team memberships and reminders request nothing. The 60 s sync timer and the inbox poll stay: the socket carries no task changes and no reads.
  - **Re-auth:** every 20 s the connection reads the account's token (which the session manager refreshes within its 60 s margin) and re-authenticates when it changed; a token of another session (a new sign-in) reconnects instead, and a re-auth without `auth.success` within 10 s closes and reconnects, which also covers servers older than 2.7.0. The session manager is unchanged.
  - **Failures fall back to polling, quietly and within the shared limit:**
    - `invalid_token` and "session revoked" go through the session manager's `refreshAfterRejection`; a newer token reconnects once, anything else stops the socket until the next resume, and a revoked session ends inside the manager's refresh as for HTTP.
    - Drops, "token expired", "auth timeout", 1013, 5xx, a TLS handshake cut off and connection errors reconnect after 2 s doubling to 60 s with ±25 % jitter, reset after a minute live and on resume; six attempts in a row that never reach `auth.success` stop until the next resume.
    - A 429 waits its `Retry-After`, at least 2 s (doubling with every 429 in a row) and at most 5 minutes.
    - Any other refused upgrade (404, 426, 3xx and the like) or a TLS error before any socket of the account was live means the server or a proxy cannot do it: no more attempts until the app starts again or the account changes. After a socket was live the same answers count as temporary.
    - While the shell's offline state says offline, nothing is tried; when it turns online, at once.
  - **Nothing new on screen:** the badge, the inbox and the lists simply update sooner, and the offline banner stays bound to sync runs.
- **Rejected alternatives:**
  - **The socket as the sync trigger in place of the 60 s timer** (the plan of D33): the socket carries no task changes, so web edits would wait for the next notification.
  - **Re-reading the notifications on every event**, as the web does: a request per event for data the event already holds.
  - **Sockets for every signed-in account:** each costs an upgrade from the shared limit and a connection; the inactive accounts' poll is enough for an account not on screen.
  - **web_socket_channel or cupertino_http's socket:** a new dependency, and no status code for a refused upgrade; the hand-made upgrade on dart:io shows 429 and `Retry-After`.
- **Consequences:**
  - While the app is open, a comment, an assignment or a mention made on the web is in the inbox within a second and the task it names is synced within a few seconds; checked on the emulator against the test server (about 1.5 s for a comment, the assignee's avatar on the row within 4 s, the catch-up after a resume).
  - Each opening of the app costs one upgrade and one inbox pull; re-auth costs nothing beyond the token refresh REST needs anyway; a server or proxy that cannot upgrade costs at most a few attempts per app session. On Android a server behind a private CA or reachable only through a system proxy or VPN route that dart:io ignores keeps working through polling.
  - Not built: time tracking events (licensed), sockets for inactive accounts or in the background, showing the server's reminders, a switch to turn realtime off.
  - Tests: the codec on the frames recorded from 2.7.0, `realtimeUri`, the connector against a loopback server (101, 429 with `Retry-After`, 426, 404, a wrong accept key, timeouts, close codes, drops and resets), the connection's state machine with fake sockets and timers (gating, lifecycle, the sequence and catch-up, storage, the debounced sync per kind, re-auth and its timeout, every failure class, the limits, the offline pause, a late close after sign-out), the provider and the shell (no reconnect on a tab switch). Contract tests on both API paths: auth, `auth_required`, an API token refused, a comment pushed equal to `GET /notifications`, logout closing with "session revoked"; in the app a comment reaching the inbox repository through the real socket.

The screen downloads when the board opens and the snapshot is missing or older than five minutes, on pull, when the device comes back online, and quietly 2 s after its own placements have left the outbox. The sync never downloads boards; it purges the snapshots and buckets of views that no longer exist, which also ends the leak of list-view snapshots.
  - **The board model** (`buildBoard`, `vikunja_logic`) joins the snapshot with the local tasks: a queued placement wins; a done task shows in the done bucket and an open one leaves it for the default bucket (the leftmost when none is set), as the server will do; tasks created here, changed after the download or moved into the project show on top of the default bucket; tasks deleted or moved away are hidden; the filters the device can evaluate apply as in D43; a filter-mode board shows its download as it is. A sent placement updates the stored board at once, counts included.
  - **Moves through the outbox:** `TaskChanges.kanban` maps a view to a bucket and a position, merged per view, folded behind an unsent create, kept as pending changes until sent. A later project move or a change that flips `done` drops the placements queued before it, so the server never gets a move for the wrong project or the opposite done state. A drop into the done bucket queues `done: true` with the placement, one out of it `done: false` with the placement; a repeating task dropped into Done is only marked done and placed in the default bucket without a position. The sender writes the body (with done) first, then per view the move and, when the answer's bucket is the target, the position. 10004, a missing bucket, 3008 and 403 become sync problems with their own wording; discarding one puts the card back.
  - **Add a task per column:** the new-task sheet with quick add creates the tasks and places them on top of that column, as many as its limit leaves room for (the rest stay in the default column, which the server fills regardless, and the snackbar says so); in the done column they are created done.
- **Rejected alternatives:**
  - **Downloading boards in the sync:** a request per kanban view and run for data that only matters while the board is open, as for list views (D43).
  - **Every task of every bucket on each download:** a done column with hundreds of tasks would cost several requests every five minutes; the web shows the first page too and loads more on scroll.
  - **A separate outbox operation for moves:** queueing, deletes, failures and sync problems all assume one update per task; a field of `TaskChanges` rides those paths, as labels and relations do.
  - **Placing new tasks with `bucket_id` on the create:** it applies to one view only and would change the create's recovery match (D35); a placement queued behind the create works offline and in every view.
  - **The web's 0 for an empty column:** it triggers a recalculation of every position in the view.
- **Consequences:**
  - A project's Kanban boards work like the web's, offline from their last download, and moves made offline are sent in order.
  - An open board costs one request every five minutes plus one per further page loaded, and each move up to three requests (a read of the task when nothing else changes, the move and the position) plus a quiet download afterwards.
  - Not built: creating, renaming, deleting and limiting buckets and choosing the done and default bucket (step 21), collapsing columns, ordering list views and projects (step 22), Table and Gantt (step 29), kanban views of saved filters, cover images, comment and attachment icons, a read-only mode from `max_permission` (a refused move becomes a sync problem). In filter mode a task the server lists in two buckets shows once.
  - Tests: the web's position vectors; `buildBoard` in every rule; the domain merge rules; the bucket codecs on fixtures recorded from 2.7.0 for both versions; the sub-writes and their order; the v6 to v7 migration; downloads, appends and the purge; the outbox (fold behind a create, project moves, done flips, failures); widget tests for the switcher, the board, cards, drag between and within columns, refused drops, the semantics actions, load more, add a task per column, read-only boards and the landscape layout; the accessibility smoke test at 200 % text in dark mode, en and de, with the rail. ## D48: Bucket management online, applied to the local board at once, from a column menu, with a guard against the server's orphaned tasks

*Accepted 2026-10-19, step 21. Completes the board of [D47](#d47-kanban-board-from-per-view-board-snapshots-moves-and-positions-through-the-outbox-with-the-done-buckets-rules-accessible-drag-and-drop); handles writes the way creating a label ([D36](#d36-labels-and-assignees-as-id-set-deltas-in-the-task-update-sent-through-their-endpoints-after-a-read-before-write-diff-reminders-as-the-whole-list-label-creation-online-only)) and duplicating ([D41](#d41-relations-as-deltas-in-the-task-update-sent-through-the-relation-endpoints-after-a-read-before-write-diff-temporary-ids-on-both-ends-resolved-at-send-time-the-inverse-rows-kept-locally-duplicate-and-subscriptions-online-only-subtasks-from-indented-quick-add-lines)) do, online and without the outbox.*

- **Context:**
  - The board of step 20 showed the server's columns but could not change them.
  - Verified server facts (Vikunja 2.7.0, both API versions, probed on 2026-10-19; the web read at `e7d7f17`):
    - **Buckets:** create v1 `PUT` / v2 `POST`; update v1 `POST` / v2 `PUT` **replaces title, limit and position together** (whatever is left out becomes 0) and answers with an incomplete bucket; delete moves the bucket's tasks to the default bucket, or the leftmost when none is set, keeping their positions and ignoring the limit, and clears the view's default or done id when it was that bucket; the last bucket cannot be deleted (10003). v1 lets ids in the body override the URL. Positions are stored as sent.
    - **Done and default bucket** are fields of the project view: v1 `POST` and v2 `PUT` replace the whole view (leaving out `view_kind` turns the board into a list), v2 `PATCH` merges only what is sent. Choosing a done bucket changes no task. Only project admins may change them (403 for write shares, which may manage buckets); archived projects refuse bucket changes (3008); a view change shows up in `GET /projects`, bucket changes do not.
    - **Upstream bug:** deleting the bucket the tasks fall back to (the leftmost while no other default is set) leaves its tasks in no bucket at all.
    - **The web:** the title is edited in place; the column menu has Limit, Done bucket, Default bucket, Collapse and Delete (disabled for the last bucket, with a confirmation); "Create a bucket" sits at the end; columns are dragged to reorder.
- **Decision:**
  - **Online, applied at once.** `BucketRepository` calls the server and nothing is queued: the actions need server ids, change where queued moves land and are rare. On success it writes the answer into the local board in one transaction (a new column with count 0; renamed, limited and moved columns keep their stored count; a deleted column's cards move to where the server puts them; the view's done and default ids are written to `project_views` alone), then downloads the board quietly. Offline, or on a refusal, nothing changes and a message says why: no connection, the change could not be confirmed, only project admins can choose the done or default column, a board needs at least one column, the column no longer exists, the project is archived, no permission. Every success is announced to screen readers.
  - **Requests:** the bucket update always sends title, limit and position, and no body carries an `id` or `project_view_id`. The view change is a merge-patch on v2 and, on v1, a read of the view followed by writing it back whole with only the bucket ids changed, so kind, filter, title and position survive. A bucket already gone counts as deleted.
  - **The column menu** sits behind an options button in each header ("Options for <column>"): Rename, Limit ("Not set" when none), Done column and Default column (checked when they are, with the web's hints; choosing a checked one clears it), Move left and Move right (where possible), Delete (disabled for the last column). Rename, the limit and a new column use an input sheet; titles are trimmed and must not be empty, which is stricter than the server; a limit below the current count is allowed and shows red. Delete asks first, naming the column, where its tasks go and, when needed, the column that becomes the default. "Create a column" is a tile one column wide at the end of the board, so the phone's column snapping stays even; a new column goes to the right. Filter-mode boards and archived projects show none of this.
  - **Reordering** by Move left and Move right in the menu and as screen-reader actions, with the position from the new neighbours (also when they share a position or the first is at 0, where the web's formula would land on the wrong side; a move that cannot land is not offered). Columns are not dragged: on a phone that would compete with dragging cards and with the snapping board.
  - **Guard against orphaned tasks:** before deleting, the app reads the view from the server; when the column to delete is the one tasks fall back to and holds tasks (when it looks empty, the board is downloaded first to be sure), the app first makes the leftmost remaining column the default, then deletes; when the delete fails, the old default is put back. When the first call is refused (a write share is not an admin), nothing is deleted.
  - **The board model follows the server's done rule more closely:** a done task moves into the done column only when it was marked done after the board's download (its `doneAt`, else `updated`, is newer, or a done change is still queued), and an open task leaves the done column only when it changed after the download; tasks that were done before a done column was chosen stay where the server keeps them. The download now takes its time before the request.
- **Rejected alternatives:**
  - **Bucket changes through the outbox:** temporary bucket ids would have to be remapped in queued moves and snapshots, and a move queued into a column deleted offline would have nowhere to go.
  - **The v1/v2 full view replace for done and default:** one missing field breaks the view; v2's merge-patch and v1's read-then-write cannot.
  - **Collapsing columns:** a phone shows one column at a time; it would also break the even snapping.
  - **Editing the title in the header:** the keyboard would cover the board and fight the snapping and the drop targets; a sheet does not.
- **Consequences:**
  - A board can be set up completely in the app, while online.
  - Each change costs its request plus a board download; a guarded delete one view read and up to two more requests.
  - Not built: collapsing and dragging columns, managing columns offline, a permission model from `max_permission` (a refusal shows as a message). Moves still queued into a deleted column fail as the existing sync problem.
  - Tests: the write ports on fixtures recorded from 2.7.0 for both versions (verbs, bodies, 304, the v1 view kept whole, the error codes); the repository against a fake server with each action compared to a fresh download, the guard in every branch, the plans for deletion and moves; the DAO additions; the refined done rule; widget tests for the menu, the sheets, the confirmation, the tile, the moves and announcements and read-only boards; the accessibility smoke test at 200 % text in dark mode, en and de. Contract tests on both API versions: create, rename keeping limit and position, limit, reorder (also in front of a column at 0), delete moving tasks, the last column, done and default set and cleared without changing the view or any task; in the app each action against the server leaves the local board equal to a fresh download and the guard keeps the tasks. Checked on the Android emulator: the menu, a limit set and cleared, a column created and deleted, with the server following.

## D49: Manual ordering: list views by drag through the outbox, projects reordered and nested online, never a project position below 0.1

- **Context:**

## D51: One filter engine on the device with the server's semantics, saved filter definitions synced on change and managed online, a filter builder, offline search

*Accepted 2026-10-20, step 24. Carries out what [D43](#d43-task-lists-from-the-local-database-like-the-webs-a-view-snapshot-for-positions-and-server-only-filters-the-overviews-saved-filter-downloaded-by-the-sync-upcoming-with-the-web-presets-and-a-pinned-overdue-part) and [D45](#d45-app-shell-on-wide-android-screens-the-colour-scheme-and-dynamic-colour-the-webs-display-settings-applied-only-when-set-translated-default-names-the-project-tree-with-favourites-saved-filters-and-archived-projects-smart-lists-a-sticky-offline-banner) left to step 24: lists, boards ([D47](#d47-kanban-board-from-per-view-board-snapshots-moves-and-positions-through-the-outbox-with-the-done-buckets-rules-accessible-drag-and-drop)), saved filters and the Overview no longer depend on the server for their filters. The views form of [D50](#d50-project-management-and-views-online-applied-to-the-local-database-at-once-from-the-project-screens-menu) gets the builder; saved filter changes go online like [D48](#d48-bucket-management-online-applied-to-the-local-board-at-once-from-a-column-menu-with-a-guard-against-the-servers-orphaned-tasks).*

- **Context:**
  - Lists evaluated only the default filters (`done = false`, `done = true`, none) on the device; any other view filter, every saved filter and the Overview's filter came from a download, showed changes made here only after the next one, and were empty offline until downloaded once. Saved filters could not be created or changed in the app, and there was no search.
  - Verified facts (the server's filter code and the web read at `e7d7f17`, probed on Vikunja 2.7.0 with both API versions on 2026-10-20; 267 vectors from the source and 445 observed results):
    - **Grammar:** a value runs to the next `&`, `|`, `(` or `)`; `&&` and `||` fold strictly from the left, only parentheses group; consecutive AND-joined range conditions on labels or reminders must hold for the same label or reminder; field names are exact snake_case; errors 4016, 4017, 4019, 4024, 4033.
    - **Semantics:** a missing date fails every comparison, `!=` included; `filter_include_nulls` adds missing values and, for whole numbers with `=`, `<` and `>`, also 0; labels by id and assignees by exact username match by existence, so `!=` and `not in` include tasks without any; `percent_done` runs from 0 to 1; `project` never includes subprojects; `like` uses `%` and `_` and folds ASCII case only; dates follow go-datemath (`now/d+1w`, quarters, business days, epoch milliseconds) with fallbacks, in `filter_timezone`, else the server's zone; saved filters use the owner's timezone setting.
    - **Scope:** a project view covers its project, archived tasks included; all tasks and saved filters cover the projects that are not archived plus the user's favourite tasks.
    - **Saved filters:** created, changed and deleted through `/filters` (v1 `PUT`/`POST`, v2 `POST`/`PATCH`/`DELETE`); their definition is only in `GET /filters/{id}`, not in the project list, which carries their `updated`.

- **Decision:**
  - **One engine in `vikunja_logic`:** `parseTaskFilter` and `matchesFilter` implement the server's rules exactly and pass every collected vector and observed result; contract tests on both API versions compare the engine's tasks with the server's for 62 filters, the dated ones in three timezones. Two deliberate differences: a date equal to a bound matches as written (on SQLite the server is off by one there), and filters the server answers with a 500 (`position`, range comparisons on people, business-day rounding) are refused with 4019. The expression reader is a translation of the server's fexpr library (BSD 3-Clause) and the date math follows go-datemath (ISC); both notices are in `packages/vikunja_logic/THIRD_PARTY_NOTICES.md`.
  - **Timezone:** a saved filter's own, else the user's timezone setting, else the device's zone, through `package:timezone`.
  - **Where it applies:** list views with any filter (the view's snapshot only orders a manual list), boards (matching tasks created or changed here show at once), saved filters and the Overview's saved filter, each with the server's scope. Filters that use `now` are evaluated again every minute and on resume, so "due today" turns over at midnight. A filter the engine refuses, one naming `bucket_id` or a saved filter whose definition is unknown keeps the downloaded list, with its notice; downloads of saved filters the device evaluates are no longer made and old ones are removed.
  - **Definitions in the sync:** the project phase keeps each saved filter's `updated` and reads the definition of new or changed ones only; a failed read keeps the previous definition.
  - **Saved filter management** online, applied at once: "New saved filter" ends the Saved filters section (and is in the Projects menu); a saved filter's screen offers Edit, Add to or Remove from favourites and Delete. The form: title, description (plain text; the web's HTML is shown as text and kept when untouched), the filter, "Include tasks which don't have a value set" (the web's wording) and favourite; new filters start with the web's defaults.
  - **The filter builder** (saved filters and the views form): the web's syntax with operators in bold and values underlined (no backgrounds, so selection and caret stay visible), suggestions under the text for fields, operators, labels, projects, people and named date shortcuts, kept in view above the keyboard; label and project titles are sent as ids, ids without a local title are kept; the engine's error appears after a short pause or on leaving the field and blocks saving; a live count of matching tasks on the device, read out when it changes.
  - **Global search:** a search action in the Overview, Upcoming and Projects app bars opens one field with results grouped as tasks (title or description with full Unicode case folding, `#12`, and `PROJ-12` as an app addition), projects, saved filters and labels, open tasks first; offline and instant from an index kept up to date as tasks change; a label opens its open tasks with the saved filters' scope; the last query comes back when Search opens again.
- **Rejected alternatives:**
  - **Keeping the server-only path for anything but the default filters:** the lists would stay stale and empty offline, and saved filters would cost a download per open.
  - **Parsing with a grammar of our own instead of the server's reader:** the left fold, the value scanning and the range merge only come out right by reading filters the way the server does.
  - **The web's defaults for case and time:** `like` and the timezone follow the server's observed behaviour; the web adds nothing there.
  - **A chip-based builder:** much more screen for the same language; a text field with suggestions keeps every filter the web can write.
- **Consequences:**
  - Every list, board and saved filter works offline and follows changes made here at once, as on the web while it is online.
  - A saved filter costs one request when it is created or changed elsewhere, instead of a download per open and per sync for the Overview.
  - Evaluating 5,000 tasks takes about 50 ms on the test machine; the search index rebuilds in about 50 ms and updates in a few.

## D52: Descriptions edited in a bundled TipTap page in a locked-down WebView with a native toolbar, checklists ticked in place, no silent overwrite of a description changed on the web

*Accepted 2026-10-20, step 25. Carries out [D18](#d18-tiptap-description-editor-in-a-webview); keeps the native read-only rendering of [D44](#d44-task-detail-complete-rich-text-from-an-own-parser-of-the-web-editors-schema-details-and-comments-online-on-demand-deep-links-on-the-app-scheme); keeps the promise of [D34](#d34-outbox-local-first-writes-serial-sender-coalescing-retry-classes-sync-interplay-pending-fields-win-until-sent-pending-deletes-hidden-v1-full-replace-emulation) that the description would not stay last-write-wins; adds the project description that [D50](#d50-project-management-and-views-online-applied-to-the-local-database-at-once-from-the-project-screens-menu) deferred.*

- **Context:**
  - Descriptions were read-only in the app; checklists in them could not be ticked, and a description change would have overwritten one made on the web meanwhile.
  - Verified facts (the web read at `e7d7f17`, probed on Vikunja 2.7.0 with both API versions on 2026-10-20): the web edits with TipTap 3.31.3 on ProseMirror; the order of its 21 extensions decides the schema; custom nodes for mentions, task links, task items with `data-task-id`, quotes of comments, attachment images (`data-src`) and coloured table cells; a WebView serialises like the browser. The web autosaves 5 s after a change, saves at once on Save and on a ticked checkbox, stores an emptied description as `<p></p>`, ticks by `data-task-id` and re-saves the whole description normalised. Mentions are suggested after `@` from the project's users; task links come from pasted task URLs. The server has no preconditions on writes.
- **Decision:**
  - **Our own bundle, the web's output.** `app/editor/` builds one self-contained page, `app/assets/editor/editor.html`, from the TipTap and ProseMirror npm packages at the web's versions with our own configuration of the web's extensions (written from its behaviour; the web frontend's AGPL code is not used). It leaves out what does not change stored HTML or belongs to later steps: code highlighting (also avoiding highlight.js), slash commands, Markdown paste, image upload, paste and drop, and floating popups. Acceptance: all 123 recorded web outputs of step 10 come out of our editor byte for byte (Node with jsdom). `tool/build_editor.sh --check` rebuilds it and fails on any difference; CI runs it. Everything bundled is MIT, listed in `app/assets/editor/NOTICES.md`.
  - **Locked down:** the page loads from the app's assets, a content security policy allows only its own hashed script and inline styles and no network at all (images are drawn as labelled placeholders and never loaded, so no token reaches the page), every navigation is refused, messages carry a per-load token both ways, file access and debugging are off. The bridge exchanges `init`, commands, `state`, mention queries and the HTML; a page that was not changed is never written back.
  - **The editor page:** a full-screen page over the task or project, opened from an Edit button by the description in the detail sheet ("Add description" when empty) and from a Description row on the task and project edit pages, not for archived projects. A **native toolbar** above the keyboard (bold, italic, underline, strikethrough, code, heading levels, bullet, numbered and check lists, quote, code block, link, table menu, divider, undo, redo, clear formatting) shows the active formatting; links are set in a native sheet; `@` opens a native list of the project's people (the locally known ones offline). Save is explicit; leaving with changes asks; the page follows the app's theme, dark mode, text size and language. An unsaved edit is kept as a draft when the app goes to the background and offered again next time. When the description changed underneath while editing, Save asks: Overwrite, Reload or Keep editing.
  - **Checklists ticked in place:** a tap on a checkbox in the detail sheet replaces only that item's `data-checked` value (and the input's `checked` in TipTap's exact shape) in the HTML the view was built from; it is queued through the outbox, so it works offline, with a haptic and an announcement; a tap on a view that is no longer current is refused. Comment checklists stay read-only (step 27).
  - **No silent overwrite:** a queued description change remembers the description it started from and, for ticks, which items it ticked (by `data-task-id`, else position and text). When it is sent, the app compares that with the server's current description (v1 from the read it makes anyway, v2 with one read): unchanged → sent as queued; changed and only ticks → the ticks are applied again to the server's description; changed after an edit → a sync problem "The description was changed on the web too" with **Compare versions**, **Keep my version** and **Use the web version**. Project descriptions are saved online with the same check and the same question.
- **Rejected alternatives:**
  - **The web's own editor code:** AGPL; and its popups and highlighting are not needed for the stored HTML.
  - **A native rich-text editor:** it would have to reproduce TipTap's schema and serialisation exactly, which only TipTap itself does.
  - **Autosave as on the web:** an explicit Save fits the app's edit pages and avoids writes while typing offline.
  - **Last write wins for descriptions:** a tick on the phone would erase a paragraph written on the web.
- **Consequences:**
  - Descriptions are edited with the web's formatting and saved in the web's form, offline too; ticking a checklist is one tap.
  - The app grows by the WebView plugin (which imports the legacy Material library, [D2](#d2-material_ui-and-cupertino_ui)) and a 0.5 MB page; Node is needed only to rebuild that page.
  - On v2 a web change landing between the check read and the write is still overwritten; the server offers no preconditions.
  - Not built: image upload, paste and drop (step 26), editing comments and their checklists (step 27), Markdown paste, slash commands, code highlighting, collaborative editing; the hardening review of the WebView is step 35. An in-app licences page that lists `NOTICES.md` and `packages/vikunja_logic/THIRD_PARTY_NOTICES.md` ([D51](#d51-one-filter-engine-on-the-device-with-the-servers-semantics-saved-filter-definitions-synced-on-change-and-managed-online-a-filter-builder-offline-search)) is still missing.
  - Tests: the Node tests (the 123 oracle vectors, the schema order, the bridge protocol with tokens, task-link rules, images untouched, the built page's policy); the tick and rebase helpers with fuzzing; the outbox, sender and conflict paths; the project description check; widget tests through a fake bridge and a fake WebView platform (toolbar, Save, leaving, drafts, mentions, the lockdown settings, entry points, ticks, the conflict sheet); the accessibility smoke test. Contract tests on both API versions: a description round trip, a tick round trip, a web change between queueing and sending (ticks rebased, an edit becomes a conflict, both answers), and the project description check. Checked on the Android emulator: a checklist item ticked with the server following, the editor showing every kind of content and saving an addition in the web's normalised form (a software-rendered emulator was too slow for the WebView; with host GPU rendering it ran smoothly).
